## Overview — the mental model

SuperGrok1.5 trains **3 model families** (transformer decoder, ViT, Mamba-3) under **11 optimizers**
= **33 cells**, each compiled as a **single fused persistent CUDA megakernel** on H100 (bf16 wgmma).
The defining decision: **one kernel launch runs the entire training step** — forward, backward,
gradient reduction, *and* the optimizer update — with phases separated only by an in-kernel,
hand-built grid barrier. No per-step relaunch, no cooperative launch, optimizer state stays resident.
This is the "one binary, one launch" thesis: it removes launch latency and HBM round-trips between
ops, at the cost of pinning **one CTA per SM** (the grid barrier needs all CTAs co-resident).

`compile.py` is a **superoptimizer / autotuner**: it JIT-builds, fp64-gates, and times flag / macro /
structural variants per cell and bakes per-TU winners, with a learned cost-model and an in-loop
correctness gate. Every change — by hand or by the autotuner — must clear the **HARD gate**: fp64
parity (rel 1e-4; SAM 2.5e-2) **and** A/A/A bit-determinism (identical across 3 runs). Legal rewrites
are **transport-only** (they may move data but must preserve the ascending-k fp32 reduction order, so
parity + determinism hold); anything that changes numerics is gate-arbitrated under a keep/revert ratchet.

**Performance posture (read §4 closely).** At small/medium scale the system is **latency /
serialization-bound** — the decoder runs at ~6.5% of the 989 TF/s bf16 roofline at d=2048. That gap is
*largely fixable* (grid-barrier serialization, sub-cuBLAS hand-rolled wgmma, non-GEMM work serialized
rather than overlapped, 1-CTA/SM occupancy), **not** a non-GEMM physics floor. The design goal is a
high roofline % at **every** scale; the files are meant to optimize for the project they are dropped into.

## The model megakernels (decoder / vit / mamba3) + the L3-TC substrate

This section documents the heart of the system: the three per-model persistent megakernels and the hand-built Hopper tensor-core substrate (wgmma + cp.async ring + grid barrier) they all share. Every concrete claim cites `file:line`.

### 1. The persistent-megakernel design — one `__global__` per train step

The defining structural decision is that an *entire training step* — forward pass, backward pass, gradient reduction, and the optimizer update — runs inside **one** `__global__` kernel launch, with phases separated only by in-kernel grid barriers. There is **no per-step relaunch** and **no cooperative launch**.

- **Decoder** entry point: `fused_decoder_megakernel_tc<Opt>` (`csrc/fused/sm_90/fused_decoder_megakernel.cuh:672-678`) launched by `launch_fused_decoder_megakernel_tc<Opt>` (`fused_decoder_megakernel.cuh:1511-1569`). The plain triple-chevron launch `fused_decoder_megakernel_tc<Opt><<<grid, block, dyn_smem, stream>>>` (`:1566`) is an ordinary kernel launch — **not** `cudaLaunchCooperativeKernel`.
- **ViT**: `fused_vit_megakernel_tc<Opt>` / `launch_fused_vit_megakernel_tc` (`csrc/fused/sm_90/fused_vit_megakernel.cuh:1178`).
- **Mamba3**: `fused_mamba_megakernel_tc<Opt>` (`csrc/fused/sm_90/fused_mamba_megakernel.cuh:527-532`), launched at `fused_mamba_megakernel.cuh:349`.

The host-side seams that wire these into the Python `_ops` extension are the `*_launcher.cu` TUs: `mega_decoder_real_adamw_tc_launcher.cu`, `mega_vit_real_adamw_tc_launcher.cu`, `mega_mamba_real_adamw_tc_launcher.cu`. Each exposes ONE non-template host launcher with a plain pointers/ints + `FusedScalars` POD boundary so `dispatch.cpp` can `extern`-declare it without any header-only types crossing the ABI (`mega_decoder_real_adamw_tc_launcher.cu:14-24`). The launcher TU exists specifically because the Fork-B TC cell driver (`mega_decoder_real_adamw_tc.cu`) owns its own `PYBIND11_MODULE` and is dropped from `_ops` by `setup.py`'s `_collect()` (PyInit collision) — so without this globbed-in seam the bf16 race path had no way to reach the TC kernel and silently ran eager (`:5-11`). The launcher is compiled per-TU with `-DSG_TUNED_GEMM_IMPL=1` (`mega_decoder_real_adamw_tc_launcher.cu:30`) to select the wgmma branch.

**Grid shape: gridDim.x == #SMs, one persistent CTA per SM.** The launcher reads the SM count via `cudaDeviceGetAttribute(..., cudaDevAttrMultiProcessorCount, ...)` and launches exactly that many CTAs: `launch_ctas = (unsigned)n_sms; ctx.n_ctas = launch_ctas` (`fused_decoder_megakernel.cuh:1547-1549`). The optional `ncta_cap` argument (default 0 = full saturation; the race always passes 0) lets a memory-constrained test launch fewer CTAs (`:1504-1510`).

**Why one CTA/SM.** The grid barrier (below) rendezvouses all `n_ctas` CTAs at every phase boundary; this can only complete if every launched CTA is *simultaneously resident*. So the launcher hard-gates occupancy ≥ 1 with the *actual* dynamic smem and **refuses to launch otherwise** rather than risk a hang: `cudaOccupancyMaxActiveBlocksPerMultiprocessor(...); if (occ < 1) return cudaErrorLaunchOutOfResources` (`fused_decoder_megakernel.cuh:1540-1545`). The scalar fallback launcher makes the rationale explicit in its assert: "0 blocks/SM — GridBarrier would hang" (`fused_decoder_megakernel.cuh:317-321`). Pinning one CTA per SM (via `sm_id()` reading `%smid`, `megakernel_common.cuh:65-73`) also keeps that SM's optimizer-state slice warm in its L2 partition across the whole step (`megakernel_common.cuh:57-63`).

**Why fusion instead of relaunch.** A conventional pipeline relaunches a kernel per op (fwd GEMM, bwd GEMM, dW GEMM, optimizer step), paying launch latency and round-tripping every activation/gradient through HBM between launches. The megakernel keeps activations and the reduced gradient resident in an HBM workspace it owns and never tears down the grid, so the only cross-phase synchronization cost is the in-kernel barrier — no launch overhead, no driver round-trips, and the optimizer state stays L2-resident on its owning SM.

**Why not cooperative launch.** Cooperative grid sync (`cooperative_groups::grid_group::sync()`) requires `cudaLaunchCooperativeKernel`, which caps the launchable grid at the number of CTAs that can be co-resident *and is itself subject to the cooperative-launch CTA ceiling*. The hand-built `GridBarrier` (below) needs no cooperative launch, so it "scales past the cooperative-grid CTA cap" (`megakernel_common.cuh:27-29`).

### 2. The hand-built GridBarrier (`megakernel_common.cuh`)

`GridBarrier` (`megakernel_common.cuh:147-255`) is a reusable arrive/wait grid barrier built from **two global atomics plus a sense-reversing generation counter**:

- `g_arrived` — count of CTAs that have reached the current barrier.
- `g_generation` — the sense-reversing generation, advanced once each time the barrier is crossed (`:148-150`).

All state is host-zero-initialized; the launcher re-zeros all three counters per launch with `cudaMemsetAsync` (`fused_decoder_megakernel.cuh:1557-1559`). `PersistentContext` bundles these device pointers + `n_tasks` + `n_ctas` into the uniform kernel signature (`megakernel_common.cuh:263-276`).

**The mechanism** (`GridBarrier::sync()`, `:157-210`):
1. `__syncthreads()` so the whole CTA reaches the barrier before its leader publishes.
2. Thread 0 samples `my_gen = *(volatile)g_generation` (the sense it is waiting to leave).
3. **§1.14 RELEASE**: `__threadfence()` makes this CTA's phase writes visible device-wide *before* arrival is announced (`:166-169`).
4. `prev = atomicAdd(g_arrived, 1)`. The CTA whose add completes the set (`prev+1 == n_ctas`) is the **last arriver**: it `atomicExch(g_arrived, 0)` to clear the count for the next phase, `__threadfence()`, then `atomicAdd(g_generation, 1)` — order matters so an observer of the new generation also sees `arrived==0` (`:173-182`).
5. **Everyone else spins** on `(volatile)g_generation == my_gen` (`:194-200`).
6. **§1.14 ACQUIRE**: after observing the generation advance, `__threadfence()` so peers' released phase writes are visible (`:203-205`), then a closing `__syncthreads()` releases the rest of the block (`:208-209`).

**Why sense-reversing beats a naive counter reset.** The classic hazard with a counter barrier is *reuse*: if you just reset `arrived=0`, a fast CTA can enter the *next* barrier and increment the counter before a slow CTA has even observed the release of the *previous* one (`:128-134`). The generation counter fixes this — a late CTA waits for the generation to *advance* (the consumer side never touches `arrived` for reset), so an early CTA cannot lap it.

**Why `__nanosleep` backoff.** A tight `volatile`-read spin hammers the L2/memory subsystem and steals issue slots from the still-arriving (laggard) CTAs. The waiter instead parks with `__nanosleep(backoff)` on an exponentially growing nap capped at 1024 ns: `backoff = (backoff < 1024u) ? (backoff << 1) : 1024u` (`:193-199`). This is behavior-preserving — it exits the instant the generation advances; only the *poll cadence* changes (sm_70+; a no-op fallback on older arches).

**The fused reset (`sync_reset`, `:222-254`).** The L3 phase loop needs the task-queue counter zeroed between the reduce phase and the optimizer phase. Rather than `sync → reset → sync` (which would cost 4 grid barriers + 2 standalone resets per step), the reset is folded into the last-arriver critical section: the last CTA does `atomicExch(g_arrived,0)` **and** `atomicExch(reset_counter,0)` *before* the release-store that bumps the generation, so any CTA that later observes the new generation is guaranteed to see `reset_counter==0`. This collapses 4 grid barriers → 2 per step with identical ordering/visibility (`:213-221`). It is invoked as `bar.sync_reset(ctx.g_next_task)` (e.g. `fused_decoder_megakernel.cuh:953`).

**Minimal fences (§1.14).** The doctrine is exactly one `__threadfence()` before the arrival publish and one after the wait — the minimum for a correct release/acquire pair (`:34, 136-142`). A loose extra fence here is "both a correctness and a >10% perf footgun" (`:32-34`).

**TaskQueue / work-stealing.** Alongside the barrier, `TaskQueue` (`:91-117`) is a single global atomic counter (`g_next_task`). `next_block(smem_slot)` has the leader thread do one `atomicAdd` and broadcast the claimed parameter-tensor index to the whole CTA via shared memory (`:108-116`). There is no static partition — an idle CTA simply calls `next_block()` again, so a CTA that drains its tensor early steals the next one; the atomic *is* the steal (`:75-90`). Determinism is preserved because the work-steal queue only picks *who* reduces an element range, never the *order* of the fp32 summation within it (see P2 below).

### 3. The in-kernel phase structure (decoder TC, the reference layout)

The decoder TC kernel body (`fused_decoder_megakernel.cuh:672-1502`) is the canonical 5-phase / 4-barrier layout (`:18-37`); the ViT and Mamba kernels mirror it. Phase-by-phase, with the staged-optimizer insertions:

- **P0 (zero + weight pre-stage)** — each CTA zeroes its own LN-vec partials and loss slot (`:810-811`), and converts the fp32 params to the bf16 weight cache `wbf_cache` (C1) grid-strided and element-owned (`dectc_wbf_convert`, `:814`). No host memset; each CTA owns its slice → no cross-CTA contention.
- **B0** (`bar.sync()`, `:818`) — fences the bf16 weight cache and zeroed partials before any P1 GEMM reads them.
- **(P1 window) embedding list build** — CTA 0 builds the counting-sort token lists *here*, overlapping the other CTAs' fwd/bwd (`dectc_embed_build_lists`, `:828-829`), so the already-present B1 barrier fences it for P2 with **no new barrier**.
- **P1 (token-tile fwd+bwd GEMMs)** — each CTA grid-strides over tiles of `kTileM` rows (`:840`); per tile it runs `dectc_forward_tile` → NLL, then `dectc_backward_tile` → writes activations X, output adjoints dY, embedding-input adjoint dh0, and LN-vec partials (`:847-868`). Barrier-free within a tile. Loss accumulated fp32 per CTA into `loss_part[cta]` (`:866, 869`).
- **B1** (`:877`) — all activations (X + dY) + LN-vec partials complete.
- **P2 (dW GEMM + grad assembly)** — builds the 9 dW specs into shared smem (thread 0; identical for all threads, keeping the spec array off every thread's stack, `:890-897`); runs the dW GEMMs (split-K or single-CTA, §6 below, `:919-931`); then assembles biases (`dectc_dw_biases`), the embedding owner-scan (`dectc_embed_owner_scan`), and the deterministic LN-vec reduce (`dectc_lnvec_reduce`) (`:937-939`). The loss is reduced in **fp64** by CTA 0 only — `double s = Σ loss_part[c]; mean = s/B` — because the 1e-5 loss rel-tol is the tightest gate and fp32-summing ~4191 terms can miss it (`:940-945, 33`).
- **B2** = `bar.sync_reset(ctx.g_next_task)` (`:953`) — reduced grad ready; task queue reset for the optimizer phase.
- **Optional P2.x staged-optimizer phases**, each `if constexpr`-gated so every other cell is byte-identical:
  - **P2.4 SAM 2nd backward** (LookSAM / SuperGrok11/15 / SuperGrok2, `:993-1110`): global ‖g‖ deterministic ascending-CTA reduce → `rho_over_norm`; back up params + perturb `p' = p + (ρ/‖g‖)·g`; re-convert the bf16 cache from `p'`; run a **full second in-kernel fwd+bwd + grad assembly** into a separate `sam_grad` buffer; write the side channel (`sam_dir = g_sam−g` for LookSAM, else `sharpness = (g_sam−g)²`) and restore params from backup. Gated to every-k SAM steps by `st.looksam_sam` (`:995`); on intervening steps the cached side channel is reused.
  - **P2.5 grad-norm clip** (GrokAdamW / NeuralGrok, `:1128-1167`): global L2 norm via per-CTA partial → CTA0 ascending sum → `clip_coef`, broadcast; grad is not mutated (the coefficient is applied per-element inside the apply).
  - **P2.6 Prodigy d-reduce** (`:1205-1251`): a **fixed-partition** (not work-steal) ascending reduce of the cross-all-tensors (r,s) estimator → EMA decay → `d = max(d_prev, d_coef·r_ema/|s_ema|)`. The fixed partition is deliberate: the older work-steal drain regrouped fp32 sums by timing, an A/A/A determinism violation by construction (`:1182-1203`).
  - **P2.7 Muon Newton-Schulz** (`:1268-1322`): grid-cooperative NS orthogonalization of the 11 2D weights, one matrix at a time across all CTAs, barrier-looped per NS iteration (`buf=μ·buf+g → ‖buf‖_F → X=buf·inv_norm → {A=XXᵀ, AX, AAX, orth=aX+bAX+cAAX, swap}×5 → apply`).
  - **P2.45 / P3-SG2** (SuperGrok11/15/2 meta-net mu precompute and the full SG2 CSA/HCA/PEER/GRU meta-net, `:1338-1409`).
- **P3 (optimizer tail)** — work-steal the parameter tensors from the (reset) queue; for each, `apply_optimizer<Opt>` over the reduced grad in-place (`:1411-1498`). No barrier after P3 — the kernel exits and the step is complete.

The scalar fp32 fallback kernel (`fused_decoder_megakernel<Opt>`, gated by `SG_DEC_SCALAR_MEGAKERNEL`, `:195-292`) shows the same P0→B0→P1→B1→P2→B2→P3 skeleton in its simplest batch-parallel form (each CTA owns a contiguous batch slice, accumulating into a per-CTA `[nCTA × total]` partial, then a deterministic ascending-CTA reduce). It is gated off at large `d` because its per-sample `DecSampleSmem` grows with `SG_DEC_D` and ptxas hard-stops (`:129-138`); the TC engine's `DecTcSmem` is `d`-independent.

The Mamba TC kernel uses the **same** P0/B0/P1/B1/P2/B2/P3 structure but in the batch-parallel scalar-engine form (each CTA owns a contiguous batch slice and writes a full `[total]` grad partial; the wgmma-projection dW machinery is bypassed — see §7) (`fused_mamba_megakernel.cuh:22-36, 533-539`).

### 4. The wgmma substrate (`csrc/backends/cuda/sm_90/wgmma.cuh`)

This is the hand-rolled in-kernel `ss`-wgmma (shared-shared: both operands in smem) for `wgmma.mma_async.sync.aligned.m64nNk16.f32.bf16.bf16`. It deliberately does **not** use CUTLASS — host-launched CUTLASS collectives are not device-callable and are rejected for the persistent-megakernel path (`wgmma.cuh:14-18`). Every asm sequence cites its PTX ISA section (`:28-29`).

**Descriptor bit-packing (`make_smem_desc`, `:219-241`).** The 64-bit shared-memory matrix descriptor (PTX §9.7.14.4.4) packs: start address in bits 13:0 (the smem byte address `>>4`, so the low 4 bits must be zero → 16-byte alignment is mandatory or they are silently dropped, `:174-189`), LBO in bits 29:16 (`>>4`), SBO in bits 45:32 (`>>4`), base-offset in 51:49, and the swizzle/layout mode in 63:62 (`:231-235`). The canonical Major-K builders `make_desc_A_kmajor<MN>` / `make_desc_B_kmajor<N>` compute `LBO = MN*16` bytes (one core-matrix block) and `SBO = 128` bytes (8 MN-rows × 16 B/row) for the no-swizzle INTERLEAVE layout, verified against `cute::make_gmma_desc<Major::K>` (`:261-288`).

**LayoutType / swizzle encoding (`SwizzleMode`, `:167-172`).** A documented footgun: the layout-type field bits 63:62 are **not** size-ascending — the correct CUTLASS encoding is `NONE=0, SWIZZLE_128B=1, SWIZZLE_64B=2, SWIZZLE_32B=3` (an earlier draft had 32B/128B swapped, `:151-155`). The correctness path ships `kSwizzleNone` (a fully legal mode and the layout the gates validate against torch); 128B-swizzle is a dormant perf-phase template arg (`:156-165`).

**Required smem operand layout (`:250-259`).** For an `MN×16` bf16 operand, element `(mn,k)` lives at bf16 index `idx(mn,k) = (k/8)*(MN*8) + mn*8 + (k%8)` — i.e. K=16 is two stacked 8-wide core matrices, each an `MN×8` row-major block of 128-bit rows. The staging loops everywhere (model headers, self-test, tile_pipeline) must write this exact layout.

**Fragment decode (`WgmmaAccum<N>` + `wgmma_frag_decode`, `:314-364`).** The per-thread fp32 accumulator holds `N/2` registers (PTX §9.7.14.4.3). The authoritative decode maps `(tid_in_wg, reg i)` → `(row, col)`: the M=64 rows are partitioned warp-major (`row = 16*warp + lane/4 + 8*row_half`), and the N columns are held as n8 column slabs (`col = (lane&3)*2 + col_par + 8*slab`) (`:357-362`). Keeping ONE decode shared by the epilogue store and the gate's reference comparison eliminates the chance of a mismatched private decode (`:310-312`).

**Fence/commit/wait choreography (`:366-403`).** `wgmma_fence()` (§9.7.14.4.2) makes prior non-wgmma writes to the accumulator/operand-smem visible before the first issue; `wgmma_commit_group()` (§9.7.14.4.5) batches issued MMAs into a group; `wgmma_wait_group<N>()` (§9.7.14.4.6) blocks until ≤N groups remain — the epilogue must `wait_group<0>` before reading the accumulators.

**The ascending-k mainloop (`wgmma_mainloop_kchain`, `:617-644`).** Runs `k_steps` ss-wgmma issues in **fixed ascending k-order** (the DESIGN §3.1 determinism rule: one CTA owns the tile end-to-end, no work-steal split, no float atomics → bit-reproducible). The first issue uses `ScaleD=0` (overwrite, so a fresh accumulator needs no zeroing), the rest `ScaleD=1` (accumulate); one `wgmma_fence()` before the group, one `commit_group()+wait_group<0>()` after. The descriptor generator is a callback `gen(k)`, which is what lets the *same* mainloop serve both the unpipelined gate (fixed pre-staged array) and the pipelined gate (ring-buffer stage) with bit-identical numerics (`:603-609`). The per-N issue overloads (`wgmma_issue_n8/16/32/64/96/128`, `:441-561`) each name exactly `N/2` `+f` accumulator registers; N=128 (default tile, 64 regs) is the in/out/ff GEMM shape.

### 5. The cp.async multi-stage ring (`tile_pipeline.cuh` + the PIPE/STAGES macros)

`tile_pipeline.cuh` adds the producer/consumer ring choreography on top of the wgmma engine, reusing `Mbarrier`/`cp_async_cg_16`/`cp_async_wait_group` rather than redefining them (`tile_pipeline.cuh:9-17`). It uses **cp.async (`.cg.16`), not TMA** — TMA is explicitly phase-2 (`:199-200`). A `TilePipeline<N,Depth>` (`:142-189`) manages a Depth-stage ring of `(A 64×16 + B N×16)` bf16 tiles plus `2*Depth` mbarriers — a `full[s]` (producer arrives via `arrive_expect_tx` when a stage's loads are issued; consumer waits before wgmma) and an `empty[s]` (consumer arrives when done; producer waits before overwriting, WAR-safe) per stage (`:117-135`). Each barrier expects a **full warpgroup (128) of arrivals** — a per-warp `elect_one` would give 4 arrivals on a count-1 barrier and deadlock the parity wait, a bug called out explicitly (`:170-179`). `tc_pipelined_gemm_m64nNk16` (`:271-364`) splits the 256-thread CTA into WG0 (producer: cp.async-stages each K-tile, `:296-312`) and WG1 (consumer: wgmma in ascending k, `:313-360`), with the `setmaxnreg` register rebalance (producer few regs, consumer many) via `SG_TUNED_PROD_REGS=40 / SG_TUNED_CONS_REGS=232` (`:92-97, 289-294`). Determinism: the consumer issues the SAME ss-wgmma sequence in the SAME ascending-k order, so the pipeline only changes *when* an operand becomes available, not the math (`:265-269`).

**The decoder's PIPE/STAGES macros** (`model_stage_decoder_tc.cuh`) wrap this into a tunable 3-way selector:
- `SG_TUNED_DEC_GEMM_STAGES` (the base K-loop double-buffer depth; default 2, `:90-92`).
- `SG_TUNED_DEC_FWD_PIPE` — master 3-way selector, **baked at 1** (`:185-187`): `0` = the shipped S=2 ring verbatim (byte-identical PTX); `1` = entry (a), the SAME all-threads-stage/WG0-compute ring **deepened** to `SG_TUNED_DEC_FWD_STAGES` slots (more cp.async groups in flight); `2` = entry (b), the full producer/consumer mbarrier engine transcribed from `tile_pipeline.cuh` (`:227-252`). The comment records the tournament verdict: **entry-a deeper ring won (+1.49×); entry-b PIPE=2 LOST (857 vs 618 ms)** (`:186`).
- `SG_TUNED_DEC_FWD_STAGES` (2..4), **baked at 4** with PIPE=1 (`:188-190`).

`kDecFwdStages = kDecFwdPipe ? FWD_STAGES : kDecTcStages` (`:261`), and `kDecRingStagesMax = max(fwd-ring, dW-ring)` sizes the smem allocation (`:268-269`). The three ring bodies are in `tc_gemm_block_unpipelined`: the producer/consumer mbarrier engine (`:860-987`), the original S=2 double-buffer ring (`:988-1016`), and the deeper RS=3..4 ring (`:1017-1062`). The deeper ring keeps `RS-1` cp.async groups in flight via `cp_async_wait_group<RS-2>` in the steady region (drains the oldest tile) and `<0>` in the tail (`:1032-1061`). At S=2 the deeper loop collapses to `wait_group<0>` exactly, which is why PIPE=0 is byte-clean (`:173-175`).

**The dynamic-smem path (`SG_DEC_TC_DYNAMIC_SMEM`).** The static `__shared__ DecTcSmem` is hard-capped at 48 KB on H100 (`fused_decoder_megakernel.cuh:478-485`); the deeper fwd/dX ring's `sA`/`sB` grow ∝ ring depth (`:386-387`) and the legal-max tile reaches 49.64 KB at S=4 (`:460-463`). The preprocessor gate `SG_DEC_TC_DYNAMIC_SMEM = PIPE && (STAGES>2)` (`:464-468`) routes those configs to **dynamic smem** instead: `DecTcSmem` is placed in an `extern __shared__ char[]` pool (`:688-689`), the func is opted into `>48 KB` via `cudaFuncSetAttribute(..., cudaFuncAttributeMaxDynamicSharedMemorySize, sizeof(DecTcSmem))` (`:1533-1535`), and occupancy ≥1 is certified against the real size against the **228 KB/SM** budget (`:476-477`). This is an allocation change only — identical layout / access pattern / fp32 accumulation order / wgmma issue sequence → parity by construction (`:439-442`). The dW path always keeps the synchronous (lambda-source) staging — it is staging-bound, not drain-bound, so a ring would be the wrong lever (`:782-783`).

**The producer/consumer PIPE=2 variant** adds `2*kDecRingStages` mbarrier words `pipe_bars[]` to `DecTcSmem`, but `#if`-gated on the macro so on the shipped PIPE=0|1 builds the member is *entirely absent* and `sizeof(DecTcSmem)`/PTX is byte-identical (`:390-408`). The `SG_DEC_PIPE_BARS_ARG` macro expands to `, sm.pipe_bars` only under PIPE=2 and to nothing otherwise (`:420-424`), so the shipped tile-call sites are textually unchanged. The engine body (`model_stage_decoder_tc.cuh:860-987`) makes WG0 the consumer (wgmma into `acc[]`, owns the epilogue) and WG1 the pure producer, with `bar_full`/`bar_empty` mbarriers each expecting 128 arrivals; the consumer issues `issue_k(g_atoms,k,RS)` in ascending k → the wgmma issue sequence and fp32 accumulation are bit-identical to PIPE=0 (`:876-887`).

### 6. Decoder specifics

- **Causal attention** — `dectc_forward_tile` runs per-sample causal self-attention (`model_stage_decoder_tc.cuh:1433`); the head is masked `kj > qi`, in contrast to ViT's bidirectional attention. The final-norm + head + CE run on the **last** position (`kSeq-1`).
- **Embedding counting-sort owner-scan** — the embedding gradient is a scatter-add of `dh0` into a small set of vocab rows. The H2 design (`:2418-2446`) uses a deterministic integer counting sort: `dectc_embed_build_lists` (`:2469-2527`) builds CSR offsets `row_start[V+1]` + a permutation `perm[T]` (token positions bucketed by vocab row, ascending-t within each row) once on CTA 0 in the P1 window. The consume `dectc_embed_owner_scan` is a flat grid-stride over all `V·d` output elements where element `(r,j)` walks only row r's tokens in ascending-t order, reading `dh0[perm[i]·d+j]`. This collapses work to `O(d·T)` with coalesced reads and keeps all 132 CTAs busy. **Determinism**: per-row accumulation is the same fixed ascending-t order as the old scan → bit-identical fp32, no atomics (`:2435-2439`). The build's per-(worker,row) cursor uses an ascending-worker prefix within a row so lower-t chunks land first — globally ascending t per bucket (`:2501-2513`).
- **dW split-K (`SG_TUNED_DEC_DW_SPLITK`)** — chunks the dW `K=T` contraction across CTAs so the ~62% idle SMs in P2 do real work (`:86-88`). `dectc_dw_run_tile_splitk<N>` (`:2295-2339`) computes a PARTIAL over K-chunk `kc` of `G` into a per-(tile,chunk) scratch slot with a **floor-balanced partition** `k0=floor(kc·KS/G), k1=floor((kc+1)·KS/G)` — near-equal, summing to KS exactly for any KS≥G (a ceil split would leave a trailing empty chunk whose unwritten slot sums garbage; the floor never empties one, `:2288-2294`), with an explicit empty-chunk guard zeroing the slot (`:2318-2322`). `dectc_dw_reduce_splitk` (`:2343-2366`) then sums the G chunk-partials in **ascending kc** → deterministic. The default is now **G=1** (`:101`): with DW_STAGE=1 the single-CTA dW is 2.05× faster than G=2-scalar, making split-K (a scalar-dW grid-fill mitigation) obsolete (`:98-100`).
- **The DW_STAGE staging method (`SG_TUNED_DEC_DW_STAGE`, default 1)** — the dW GEMM is **staging-bound, not drain-bound**: ~97% of each K-step was the scalar transposed-strided operand gather, only ~3% the wgmma (`:117-124`). So the lever is faster *staging*, not pipelining the MMA. `SG_TUNED_DEC_DW_STAGE=1` does a cheap grid-cooperative pre-transpose (`dectc_dw_transpose_operands`, `:2088`) writing each weight's dY/X once per step into a **contiguous K-major** scratch (`dYt[Nout,K], Xt[Kin,K]`, K-contiguous + 16B-aligned), so the dW then builds `DecGmemTileSrcA/B` over it and reuses the existing cp.async ring's 16-byte coalesced copies instead of the 2-byte strided gather (`:132-143`). It changes transport only — fp64 parity + A/A/A by construction. `kDecDwTransposeActive = (DW_STAGE==1) && (DW_SPLITK==1)` (`:1994`); when active, an extra B1b barrier fences the transposed operands before any dW GEMM read (`fused_decoder_megakernel.cuh:910-915`).

### 7. ViT specifics

ViT is a genuine rewrite (separate header `model_stage_vit_tc.cuh`) with four deltas vs the decoder twin (`:21-32`): (1) **full bidirectional attention** — no causal mask, every key contributes for every query (`:22-24, 764`); (2) patch-proj `Linear(49→128)` replaces token embedding, with a learned CLS token prepended at position 0 and a `pos[17]` table; (3) the CLS pos-0 head (final-norm + head + CE run on position 0, not the last); (4) `kSeq=17` forces `kTileM = LCM(17,64) = 1088` (17 stacked m64 atoms = 64 samples × 17 positions).

**The B1 sub-tile lever (`SG_TUNED_VIT_P1_SUBTILE_S`, baked at 8).** Because the GEMM tile is locked at 1088 rows, at B=1024 there are only `n_tiles=16` P1 tiles, so **116 of 132 CTAs do zero P1 work and spin at B1** the whole fwd+bwd — tile-count-vs-SM quantization, the #1 ViT cost (51.2% of the step) (`:125-131`). This knob decouples the P1 *scheduling* granularity from the 1088 GEMM lock: P1 grid-strides over sub-tiles of **S whole samples** (`kSeq·S` rows) instead of whole 1088-row tiles, growing `n_tiles` ~`64/S`× so the idle CTAs pick up work and the B1 spin collapses (`:133-137`). S must stay a *whole-sample* count — never split a 17-row sample across CTAs, which would corrupt attention (`:137-141`). The sub-tile row count `kSeq·S` is generally not a multiple of 64, so the small GEMMs pad M up to `ceil(rows/64)·64` atoms with a runtime `m_real` row-guard making the pad rows inert and race-free (`:139-141, 373-391`). **Default 64** (== `kSamplesPerTile`) makes the build byte-identical (the `m_real` guard + runtime-m_atoms code is `#if`'d out at S==64, `:143-147`). The P1 loop using `kVitP1SubtileRows` is at `fused_vit_megakernel.cuh:588-613`. **Parity**: dW/biases/cls/pos grads are byte-identical (P2 reads acts by global token row, contracts ascending-k independent of P1 tiling); the LN-affine γ/β grads + loss are valid fp32 reassociations absorbed by the 1e-4 reorder tol; A/A/A holds because S is a fixed deterministic partition (`:150-162`). The baked verdict: **S=8 is parity-clean (11/11 ViT cells × 3 seeds) and fastest — 4.02× vs S=64 OFF at d=2048/B=1024** (`:164-169`).

ViT P2 is dW-output-stationary (`vittc_dw_run_tile` or split-K, `:642-648`) plus biases, the cls/pos owner-scan (`vittc_clspos_owner_scan`, `:656`), and the LN-vec reduce (`:657`).

### 8. Mamba3 specifics

Mamba3 (`model_stage_mamba3.cuh`) is the genuine Mamba-3 SISO architecture (arXiv 2603.15569, ICLR 2026) transcribed line-for-line from the fp64-verified oracle (`:8-15`). The mixer is a complex **exponential-trapezoidal selective scan** (Eq 25, the heart of the kernel):

`v_t = Bbar_t ⊙ x_t; h_t = alpha_t·(R_t@h_{t-1}) + beta_t·(R_t@v_{t-1}) + gamma_t·v_t; y_t = Σ_{c,d} Cbar_t[c,d]·h_t` with `alpha=exp(dt·A), gamma=lam·dt, beta=(1-lam)·dt·alpha` per head and a 2×2 rotation `R(phi)` per complex coord (`:41-46`).

**Per-coord state / the seq=8 register exploit.** Parallelization is batch-parallel (Option B, identical to the decoder scalar design): each CTA owns a fixed contiguous batch slice and the whole CTA cooperates on one sample at a time (`:52-62`). The scan exploit: **one thread owns SSM channel `j ∈ [0,d_inner)`**, and within its head holds the complex state `h[Nc][2]` in **registers**, unrolling `t=0..kSeq-1` (`mb_scan_fwd`, `:521-568`). Because seq=8 is tiny, the backward recomputes the forward keeping the full `h_hist`/`v_hist` in registers — **no checkpointing** (`:56-58, 570-574`). A subtle constraint: the per-coord arrays (`hr/hi/vpr/vpi`, `kStateC=64` each) are runtime-indexed local memory, and the c-loop is intentionally *not* `#pragma unroll`'d — a full unroll would force >255 registers and the carried state wouldn't persist across the t-loop (the documented "t=0 right, t>0 wrong" bug, `:527-531`).

**Why MambaSampleSmem caps placement at ~d=142.** The per-CTA `MambaSampleSmem` (`:142-202`) caches **both layers'** forward activations (`x_in`, `z`, `Bbar`, `Cbar`, `y_scan`, SwiGLU internals, etc.), and these widths scale with `d`/`d_inner`. The struct exceeds the 48 KB static cap, so it must live in **dynamic smem** opted-in via `cudaFuncAttributeMaxDynamicSharedMemorySize(kMambaSmemBytes)` (`:64-68`; `mamba3_layout.cuh:257-264`). At the production `d=128` it is `kMambaSmemFloats=53961` → `kMambaSmemBytes=215844` (~215 KB), pinned by a `static_assert(sizeof(MambaSampleSmem) == kMambaSmemBytes)` (`:206-208`) and bounded by `static_assert(kMambaSmemBytes <= 228*1024)` (`mamba3_layout.cuh:275-278`). Since the live set scales with `d` and is already at ~215 KB of the ~228 KB/SM opt-in budget at `d=128`, the maximum placeable `d` is only marginally above it — roughly `d≈142` before one CTA/SM can no longer place (which would hang the GridBarrier). This is why the `d=1024` bench variant (`SG_MB_BENCH_LAYOUT=1`, `d_inner=2048`, `kMambaSmemFloats=329481` ≈ 1.3 MB, `mamba3_layout.cuh:158-159`) **cannot run on the megakernel** — its smem far exceeds the SM budget. Scaling Mamba to `d=2048` would require draining a cached `LayerAct` buffer / chunking the live set (`mamba3_layout.cuh:275-278`).

**The Mamba-3 TC rewrite that dropped the dW machinery.** The Mamba-3 mixer is **scan-dominated** — the projections are a tiny share of the wall — so the "TC" Mamba megakernel deliberately runs the validated **scalar** per-sample fwd+bwd (`mb_forward_sample`/`mb_backward_sample`) batch-parallel into a per-CTA **full-grad** partial, then the deterministic ascending-CTA reduce + the canonical optimizer tail. The wgmma-projection dW machinery (the output-stationary dW GEMMs, split-K partials, dW specs of the decoder/ViT twins) is **bypassed** (`fused_mamba_megakernel.cuh:533-539`). Consequently the workspace carve keeps `acts`/`scratch`/`dw_part` zero-width: `part_base` is the full `[nCTA × total]` partial, not the dW-output-stationary split (`:554-563`). The legacy wgmma Fork-B dW path survives only as commentary; the production Mamba TC path is the scalar scan engine wrapped in the persistent megakernel + grid-barrier substrate.

## The optimizer files (the 11 optimizers + the fused P3 tail)

### The central perf thesis: the optimizer is the megakernel's tail, not a separate kernel

The single most important design fact in this directory is that **the optimizer update is not a kernel at all** — it is the final phase (P3) of the *same* persistent megakernel that ran forward and backward. One binary, one `<<<>>>` launch per training step, optimizer state HBM-resident, zero kernel round-trips. The phase structure of the decoder megakernel makes this literal: P0 zeroes per-CTA grad partials, P1 does batch-parallel fwd+bwd, P2 deterministically reduces the cross-CTA grad, and **P3 runs the optimizer over the reduced grad in the same grid** (`fused_decoder_megakernel.cuh:216-291`, with the P3 block at `275-291`). There is no grid teardown between the gradient and the weight update — the same CTAs that summed the gradient in P2 work-steal the parameter tensors and apply the update, separated only by one grid barrier (`bar.sync_reset(ctx.g_next_task)` at `:273`, comment "B2: reduced grad ready; reset queue for P3").

The P3 tail is a templated work-steal loop over the model's parameter tensors. Each CTA pulls a tensor id `t` from the persistent `TaskQueue`, reads its numel/offset from the `__constant__` `kDecSizes`/`kDecOffsets` tables (so no layout tensors cross the host ABI), rebases the optimizer state pointers to that tensor's slice, and calls `apply_optimizer<Opt>` per element (`:280-290`). The fwd+bwd+reduce is *optimizer-independent* — only this tail differs across the 11 optimizers — which is exactly why the launcher can take a single runtime `opt_id` and pick the kernel instantiation (`mega_decoder_real_adamw_tc_launcher.cu:80-98`).

**How state is bound (no separate state kernel, no round-trip).** The optimizer's persistent state lives in one flat caller-owned buffer laid out `[m | v | extra]` over `3*total` floats plus a trailing loss slot. The launcher slices it once and binds the slices into a `FusedOptState` POD that is passed by value into the kernel (`mega_decoder_real_adamw_tc_launcher.cu:135-185`): `st.exp_avg = state` (m), `st.exp_avg_sq = state + total` (v), `st.ema = state + 2*total` (the `extra` slice). The "extra" slice is overloaded per optimizer — it is the grokfast/grokadamw slow-grad EMA, OR Prodigy's `s` trajectory accumulator, OR LookSAM's cached `sam_dir`, OR SG11/15's per-element `mu` — all aliasing the same region because no optimizer uses more than one of them (`:144-175`). Staged optimizers that need more than `3*total` (Prodigy, SG11/15, SG2) extend the buffer past the loss slot; the host sizes it per-cell in `dispatch.cpp` (`min_state` at `:780-782`: `4*total+4` for Prodigy, `4*total+1+kSgPhiPack` for SG11/15, else `3*total+1`).

Inside the kernel, `rebase_state<Opt>` (`fused_decoder_megakernel.cuh:142-163`) takes the base `FusedOptState` and adds the tensor's flat offset to every *per-element* pointer (`exp_avg`, `exp_avg_sq`, `ema`, `sam_dir`, `s_track`, `mu`, `orth`, `smart_grad`, `param_init`, `sharpness`), leaving scalars and *per-tensor* weight sets (the NeuralGrok psi pointers, the SG11/15 phi pointers) un-rebased because those are the same for every element of the tensor (`:159-161`). This is the seam that makes "one resident state buffer, work-stolen by tensor" work.

### opt_id dispatch wiring and the no-silent-fallback contract

The optimizer name → integer mapping is `wgmma_tail_opt_id` in `csrc/bindings/dispatch.cpp:591-616`, a local int map deliberately kept in lock-step with `OptId` in `opt_components.cuh` (comment at `:580-583`): `adamw=0, lion=1, grokfast=2, grokadamw=3, looksam=4, prodigy=5, neuralgrok=6, muon=7, supergrok11=8, supergrok15=9, supergrok2=10`. The enum it mirrors is `enum class OptId : int` in `opt_components.cuh:53-57`. This is a hand-maintained cross-language contract (Python verdict sets ↔ C++ `OptId` ↔ `dispatch.cpp` int map); the test-coverage audit flags the lack of an automated drift-guard on it as a standing gap (`.perf/test_coverage_gap_audit.json`, rule (e)).

The host gate that decides whether the L3-TC decoder fires is `dec_l3_real` (`dispatch.cpp:752-754`): `(optimizer=="adamw" || (want_wgmma && dec_opt_id >= 0)) && optimizer != "supergrok2"`. SuperGrok2 is excluded because it needs a different ABI (its dedicated entry), even though its `wgmma_tail_opt_id` is 10 (`:749-751`).

The integer is then turned into a kernel template instantiation by a **`switch (static_cast<OptId>(opt_id))`** in each model's launcher TU. For the decoder this is `mega_decoder_real_adamw_tc_launcher.cu:199-264`: a case per OptId, each calling `launch_fused_decoder_megakernel_tc<OptId::X>(...)` over the same bound `st`. The mamba launcher has the same shape (`mega_mamba_real_adamw_tc_launcher.cu:184-263`). The **no-silent-fallback rule** is the `default:` arm: `return cudaErrorInvalidValue` (`mega_decoder_real_adamw_tc_launcher.cu:262-263`, `mega_mamba_real_adamw_tc_launcher.cu:262-263`), which `dispatch.cpp` turns into a thrown `std::runtime_error` (`dispatch.cpp:850-853`). An unsupported optimizer can never quietly run AdamW (the file header at `opt_components.cuh:7-17` exists precisely because an earlier path *did* template 7 optimizers off the AdamW tail — "the breadth-faking this stage eliminates").

### apply_optimizer<Opt>: the real per-element math, single-sourced

`apply_optimizer<Opt>` (`opt_components.cuh:380-520`) is a compile-time `if constexpr` ladder; **every branch calls the canonical device function in `csrc/algorithms/<opt>.h`** — there is no re-implementation in the megakernel (the `#include`s are at `opt_components.cuh:33-42`). The scalars an optimizer reads come from `FusedScalars` (`:271-336`), a POD the host fills and `apply_scalars` (`:342-376`) folds into `FusedOptState`. The C2-gap comment (`:248-262`) is load-bearing history: before this struct existed, every cell left `bc1/bc2/gate/d_factor` at their `1.0` struct defaults, silently freezing the math at t=1; `FusedScalars` is the ABI seam that un-freezes them, with defaults chosen to reproduce the old inert behavior exactly so unset fields are byte-identical.

**adamw (OptId 0).** `algo::adamw_step` with `bc1`/`bc2` (`:385-388`). The bias corrections are host-computed: `bc1 = 1 - beta1**step`, `bc2 = 1 - beta2**step` (`dispatch.py:_opt_scalars_from` `:1047-1048`), passed un-inverted (the apply divides). One `(bc1,bc2)` pair per call is correct only because the grokking race steps every tensor together — the megakernel treats the whole flat param as one task (`opt_components.cuh:263-269`).

**lion (OptId 1).** `algo::lion_step` (`:389-391`); uses `m` only (`v`/`extra` are bound harmlessly but unread — the audit notes this as dead VRAM, `phase1_status_audit.md:29`).

**grokfast (OptId 2).** `algo::grokfast_fused_step`, but with a cold-start reseed: `if (step == 1) st.ema[idx] = grad[idx]` (`:392-407`). The persistent state cache zero-inits `ema=0`, but eager grokfast seeds the slow-grad EMA with the *first* gradient (`grokfast.py` `state["ema"]=grad0.clone()`), so step 1 must reseed `ema=grad` on this thread's own element — no race/barrier needed because the P3 tail owns each element once (`:398-402`).

**grokadamw (OptId 3).** The only tail that legitimately re-inlines (not just calls) (`:408-466`). Three eager mechanisms land: (i) per-tensor layer-wise β1 = β1·(1-γ)^t, with bc1 *also* rebased to 1-β1ᵢ^step — done at the P3 call site (`fused_decoder_megakernel.cuh:1437-1441`) because the work-steal task id `t` *is* the eager `named_parameters()` layer index; (ii) global grad-norm clip, whose coefficient `clip_coef` is computed *on-device* in P2.5 (the deterministic ascending-CTA grad-norm reduction) and applied here; (iii) adaptive α, an in-context no-op because no loss signal is fed. The cold-start seeds the *unclipped* grad0 while the EMA filter uses the clipped grad (`:440-451`) — a documented bit-faithful re-inline vs `grokadamw.h:48-52`. The drift audit flags this EMA/amplification re-inline as the strongest case for extending the guard (it is the same re-inline *class* as the SG11 bug, currently correct but unguarded).

**prodigy (OptId 5), the d-reduce phase.** The apply tail is `algo::prodigy_apply_step` reading `st.d_factor` (`:472-476`), but `d_factor` is produced by an **in-kernel staged phase P2.6** between B2 and P3 (`fused_decoder_megakernel.cuh:1205-1251`). This is a global d-adaptation reduction over *every element of every tensor*: each CTA owns a fixed contiguous flat element range `[pe0, pe0+pecnt)` (deliberately NOT the work-steal queue, for determinism by construction — `:1182-1203`), calls the canonical `algo::prodigy_partials_step` accumulating `r = Σ d²·<g, p0−p>` and `s = Σ d²·|g|`, publishes per-CTA `(r,s)` slots, then CTA0 owner-sums ascending, decays the persisted EMAs by `beta3=√β2`, runs `prodigy_update_d` (d = max(d_prev, d_coef·r_ema/|s_ema|)), persists `[r_ema|s_ema|d_lr]`, and broadcasts (`:1234-1250`). Step-1 cold-starts `d_prev = st.d0` (the zero-init state slot would give d=0 → frozen params). The trajectory anchor `p0` is `st.param_init`, bound at `loss_out+1` (`mega_decoder_real_adamw_tc_launcher.cu:159-161`).

**muon (OptId 7): Newton-Schulz, the 2D-weight table, the NS phase.** Muon auto-splits parameters by `ndim`: 2D matrices get Newton-Schulz orthogonalization, everything else gets AdamW with *independent* `adamw_lr/adamw_betas` (the `aux_*` fields). The set of 2D matrices is a per-model `__constant__` table — for the decoder, `kDecMuon2D[11]` (`model_stage_decoder_tc.cuh:362-376`), giving each matrix's tensor index, rows, and cols (e.g. ff.0 [512,128], the largest). The NS itself is the **in-kernel P2.7 phase** (`fused_decoder_megakernel.cuh:1253-...`): grid-cooperative, looping the table, all CTAs cooperating per matrix (buf=μ·buf+g momentum, then the NS combine via `algo::muon_ns_combine_step` in `opt_stages_precompute.cuh:416-429`, scratch in the workspace). P3 then routes each tensor: 2D matrices were already applied in P2.7 (`if (dec_is_muon_2d(t)) continue;` at `:1427-1428`), and the 1D/non-2D weights take a *direct* `adamw_step` with the `aux_*` hyperparameters and on-device-computed `aux_bc1/bc2 = 1-aux_beta^step` (`:1474-1492`) — NOT `apply_optimizer<Muon>` (which would deref `st.orth`, valid only for 2D). The `apply_optimizer<Muon>` branch itself (`opt_components.cuh:496-500`) is just `algo::muon_update_step` (the momentum-decayed scaled apply of the precomputed orth direction).

**neuralgrok (OptId 6).** `algo::neuralgrok_apply_step` driven by a per-element `psi = neuralgrok_psi_forward(|grad·clip_coef|, ...)` (`:477-495`). The psi-net is a small *per-tensor* MLP whose weights are packed into the head of the `extra` slice — `extra[0..kPsiHidden)=W1`, then `b1`, `W2`, scalar `b2` (`:63-79`); `st.psi_W1/b1/W2` bind to those offsets (`mega_decoder_real_adamw_tc_launcher.cu:148-150`). `psi_b2` is read *on-device* from `psi_W2[kPsiHidden]` because a host scalar cannot deref a device pointer (`:478-484`). NeuralGrok also runs the same on-device global grad clip as grokadamw.

**looksam (OptId 4): the SAM 2nd backward.** Model-coupled: the apply tail (`algo::looksam_apply_step`, `:467-471`) blends `g_adj = (1−α)g + α·sam_dir`, but `sam_dir = g_sam − g` is produced by an **in-kernel P2.4 SAM 2nd backward** (`fused_decoder_megakernel.cuh:958-...`). On an every-k SAM step (gated by `st.looksam_sam`), the kernel computes `rho_over_norm = rho/‖g‖_global` (same deterministic ascending-CTA reduction as GrokAdamW's P2.5), perturbs `p' = p + rho_over_norm·g`, runs a *second* in-kernel fwd+bwd at `p'` to get `g_sam`, writes `st.sam_dir = g_sam − g`, then restores params (`:962-976`). On intervening steps the cached `sam_dir` (persisted in the `extra` slice) is reused verbatim and no 2nd pass runs. This is why LookSAM's parity gate uses the looser SAM tolerance (2.5e-2).

**The SuperGrok family.** *supergrok11 (OptId 8)* and *supergrok15 (OptId 9)* share the LookSAM SAM-2nd-backward machinery but write `sharpness = (g_sam−g)²` instead of `sam_dir`, then run a **per-tensor meta-net mu precompute (P2.45)**: `mu = sg_rescale·phi(g, sharpness)` over each tensor, where φ is a per-tensor SharpnessMetaNet (W1[H,2]/b1/W2/b2, H=32, `kSgPhiHidden`, `:81-100`) whose weights ride a dedicated state slice (`mega_decoder_real_adamw_tc_launcher.cu:167-183`). The apply is `algo::sg11_sweep_b_step` / `sg15_sweep_b_step` (`opt_components.cuh:501-510`). **SG11's distinguishing feature is the cosine gate** `gate = sigmoid(gate_temp · cos(grad, momentum))`, finalized per tensor in `sg11_precompute_mu_and_gate_for_tensor` (`opt_stages_precompute.cuh:523-561`) and consumed at the P3 call site (`fused_decoder_megakernel.cuh:1449-1462`). The **51098e0 correctness fix** is here: the staged gate had re-inlined the cosine with the *wrong* second operand, `cos(grad, MU)` instead of the canonical `cos(grad, MOMENTUM)`; the fix routes the canonical `sg11_sweep_a_step` + `sg11_finalize_gate` and passes `st.exp_avg` (the start-of-step momentum, written only later by `sg11_sweep_b_step`) as the cosine's second operand (`fused_decoder_megakernel.cuh:1452-1460`; canonical math in `supergrok11.h:22-30, 72-83`). SG15 has no cosine stage — its gate is the host scalar `sigmoid(accuracy)` (`opt_stages_precompute.cuh:595-611`; `dispatch.py:1203-1218`).

*supergrok2 (OptId 10): the CSA/HCA meta-net.* SG2 is a different beast — its `apply_optimizer<SuperGrok2>` branch is only an Adam-on-smart_grad stub (`opt_components.cuh:511-519`); the real optimizer is a **full CSA/HCA/PEER/GRU meta-net run as the P3-SG2 phase instead of the per-element apply** (`fused_decoder_megakernel.cuh:1362-1408`). It is architecturally DeepSeek-V4-derived NSA (per project memory). Per work-stolen tensor it runs `sg2_meta_stages` end-to-end: STAGE -1 in-kernel segmented sort (|grad| ascending, index tie-break) → S0 input-proj → S1 CSA context → S2 HCA → S3 matrix-GRU → S4 PEER routing+experts → S5 unsort + `sg2_apply_step` (smart_grad = g + α·mu + lamb_eff·slow, then Adam) (`opt_stage_supergrok2.cuh:73-89`; per-element S5 is bit-identical to canonical `supergrok2.h:395`). Because the meta-net needs more than `FusedScalars` can carry, SG2 has a **dedicated launcher** (`mega_decoder_sg2_tc`, `mega_decoder_real_adamw_tc_launcher.cu:283-371`) and a **dedicated dispatch entry** (`ops.sg2_fused_step`, wired in `dispatch.py:1973-1988`). It binds the **26-pointer meta-net weight bundle** (input_proj W/b, CSA q/k/v/out/compress/idx_DQ/idx_K, HCA q/k/v/out, GRU Wz/bz/Wr/br/Wh/bh, PEER query_Ws/prod_keys_A/prod_keys_B, expert W1/b1/W2/b2) into `FusedOptState`'s `sg2_*` fields (`mega_decoder_real_adamw_tc_launcher.cu:336-347`), plus per-tensor scalar *arrays* (alpha/gru_decay/lamb_eff/beta1/bc1/bc2, length P — they don't fit the POD) at `:348-350`, and reuses the SAM 2nd-backward machinery for `st.sharpness` (the meta-net's 2nd MLP input). The state slices are `[m|v|mu|loss|sharpness|slow|gru_state]` (`:325-334`). The bundle is staged to HBM, not smem, because it does not fit alongside `DecTcSmem` under the 48KB cap (`opt_components.cuh:218-219`).

### optimizer_math_manifest.json and the check_math machinery

The single-source-of-truth for the per-element math is `csrc/algorithms/<opt>.h`; every CUDA consumer derives from it by `#include`. `scripts/optimizer_math_manifest.json` is the committed drift guard: it records the normalized content hash of each canonical header (`"hashes"` block, one per the 11 optimizers; `binding_regions` is `{}` since the per-op pybind entrypoints were removed in Task #10). `scripts/check_math_single_source.py` enforces three teeth (header docstring `:1-39`): (1) **structural** — each consumer (`opt_components.cuh`, the per-op `<opt>_sm90.cuh`) must still `#include` the canonical header (reimplementation is the only drift path); (1b) **re-inline detection** — consumers are scanned for re-typed Adam moment-update/bias-corrected-apply expressions, plus a cosine-specific scan added for the SG11 case (`den_m += x*x`/`den_g += x*x` in `opt_stages_precompute.cuh` must coexist with the `supergrok11.h` `#include`); (2) **content-hash** — recompute the header hashes and fail on any diff, forcing a deliberate `--update-manifest`. The verify/update modes are `:518-...`; `compile.py --self-test` runs the verify path plus a prove-it-triggers perturbation test (`OPTS` list at `:51-54`).

The drift audit (`.perf/optimizer_drift_audit.json`) is the human-trust companion: 23 agents, refute-by-default, **0/11 confirmed active drifts**. It records the SG11 bug as *historically remediated* and enumerates the guard's residual blind spots: (A) narrow-token cosine patterns (only literal `den_m`/`den_g`), (B) the general Adam-reinline scan covers only `opt_components.cuh`, NOT the staged headers `opt_stages_precompute.cuh` / `opt_stage_supergrok2.cuh`, (C) no call-argument check (the SG11 root cause is *semantic* — `sg11_sweep_a_step(...,momentum,...)` vs `(...,mu,...)` both satisfy "calls the canonical fn"), and (D) the recommended closure: register every staged precompute with an *independent, de-mirrored* fp64 oracle run *warmed up* (multi-step). The CSA/HCA softmax + GRU + grokfast-EMA math in the SG2 stage is currently scanned by nothing (it is exempted as a separate launch via a WARN).

### The PERF reality: the fusion is maxed; the tail kernels are not

The fusion thesis is fully realized: all 33 cells run fwd+bwd+optimizer in **one persistent `__global__`, one launch, zero intermediate launches** (`phase1_status_audit.md:22-23`). 1 CTA/SM, hand-built sense-reversing GridBarrier, no cooperative launch, no CUDA graph; the only host bubble is the one mandatory `.item()` D2H sync per step (`dispatch.py:2005`).

But the optimizer **tail kernels are un-autotuned**. The P3 tail is **~5.9% of the decoder critical path (~38ms/618ms)** — the canonical "max the optimizer kernels" target (`PLANNING_INPUT.md:30`, `phase1_status_audit.md:24`). The readiness table (`phase1_status_audit.md:26-42`) marks `perf_maxed:yes` only for adamw/lion/grokfast and flags even those as "thin" — the autotune that would give real optimizer perf data produced zero winners. There is a documented earlier framing collision: a vec4 AdamW-tail experiment was NEUTRAL (+0.05%) at the *d=2048* scale where the model GEMM dominates and the tail is <1% (`OPTIMIZATION_LEDGER.md:38`, `PHASE1_CAMPAIGN.md:401`) — but the freshest audit re-anchors the production-config tail share to 5.9%, so the "<1%" framing is stale (`phase1_status_audit.md:40`). Net: the *fusion/launch-elimination* is maxed; the *tail apply kernels themselves* are not perf-optimized.

### The CORRECTNESS reality: 3 green, 8 gate-COVERAGE caveats (not confirmed math drift)

The readiness table (`phase1_status_audit.md:26-42`) is the authority. Three optimizers are **green** — **adamw, lion, grokfast** — passing the committed 33/33 × 3-seed pytest gate (at d=128). The other eight carry **gate-coverage caveats, NOT confirmed math drift** (the drift audit confirms 0/11 active drifts; the verifier net at `:40-42` is explicit: "Caveats are mostly MISSING/toy-scale GATES, not active math drift"). Precisely:

- **grokadamw** — `caveat`: the multi-step gate is MISSING for the vit/mamba cells (`phase1_status_audit.md:31`). The clip and layer-wise-β1 mechanisms only *fire* multi-step (at step 1, ‖g‖≈0.72<1 → clip_coef=1, inert), so a single-step gate cannot catch a divergence in them.
- **prodigy** — `caveat`: the d-adaptation is not CI-guarded (`:32`). d-adaptation is identity at step 1 (d=d0 cold-start), so the staged P2.6 reduction is exercised only in the regime where buggy and correct coincide.
- **muon, neuralgrok** — `green` on math but **blocked by BUG-04** (`perf_maxed:no`, `ready:N`, `:33-34`).
- **looksam** — `caveat`: BUG-04 + the earned (looser SAM 2.5e-2) tolerance (`:35`).
- **supergrok11** — `caveat`: the warm-up gate exists but is **CLI-only, not CI-collected** (`run_sg11_warmup_gate` is `@pytest.mark`-less / CLI-invoked, `.perf/test_coverage_gap_audit.json`). The 51098e0 fix is *in* the tree and faithful, but its regression guard stays blind for two compounding reasons recorded in the drift audit: (1) the fp64 oracle *mirrored* the kernel (computed `cos(grad,mu)` too → CO-WRONG parity passed), and (2) at step 1 the start-of-step momentum `exp_avg` is ~0, so `cos(grad,momentum)` degenerates and both operands give near-identical gates — defeating a single-step gate. Re-gating requires a de-mirrored, first-principles fp64 oracle AND a multi-step warm-up across 3 seeds.
- **supergrok15** — `caveat`: **no warm-up gate at all** (`run_sg11_warmup_gate` hard-asserts `supergrok11`, so SG15 has no warm path, `:37` + `test_coverage_gap_audit.json`).
- **supergrok2** — `caveat`: the **CSA oracle is co-wrong (HIGH)** — the SG2 tie-probe validates the oracle's *own* perm builder, and the N>64 oracle uses the same low-rank indexer as the kernel (a co-derived oracle hides bugs); plus a non-voting probe (`:38`).

**BUG-04** (the blocker behind muon/neuralgrok/looksam being `ready:N`): the mamba **staged-opt scratch is un-gated**, so at d≥1024 the mamba bench layout over-allocates ~199 GiB vs the expected ~13.4 GiB and OOMs (`PLANNING_INPUT.md:39`, `.perf/author_queue1_report.json`). The mamba launcher *does* have `case OptId::Muon/NeuralGrok/LookSAM` wired (`mega_mamba_real_adamw_tc_launcher.cu:184-263`), so this is a **VRAM scratch-sizing bug, not a missing optimizer** — at d=128 these run; at scale they OOM until the staged_opt_scratch gate lands (the fix: gate each staged sub-sizer to early-return 0 when the runtime opt does not consume that region, mirroring the decoder/vit `kDecStagedOptScratch`).

The systemic shape behind every caveat (per `test_coverage_gap_audit.json`) is the SG11 bug's shape recurring: the gate suite is blind along four axes at once — single-step-from-zero-init (every momentum/EMA/clip/d/SAM mechanism exercised only where buggy and correct coincide), tiny-scale-only (p=97, d=128, single-CTA-degenerate reductions), a hand-transcribed-mirror-or-co-derived-oracle correctness anchor, and ungated/uncompiled ON-paths for new knobs and the warm/firing/SAM-off branches. These are coverage gaps in the *gate*, not confirmed errors in the *math*.

## compile.py — the superoptimizer / autotuner (and the Level-2 work)

### What it is

`grokking_optimizers/compile.py` (32,900 lines) is a **per-`(optimizer, model, arch)` autotuner and superoptimizer**: it JIT-builds, fp64-correctness-gates, and times a large space of flag / macro / structural kernel variants, then bakes the per-translation-unit winner into the shipped extension. It is the development-time companion to `setup.py` — where `pip install -e .` builds the whole `_ops` extension with default flags, `compile.py` compiles a *focused, maximally-optimized* build for one cell (`compile.py:6-12`). It is invoked as `python -m grokking_optimizers.compile --optimizer <opt> --model <model> --arch <arch>` (`compile.py:96-112`).

**Two-phase AOT/JIT pipeline** (`compile.py:14-70`). The work is split so a CPU-only host can do the heavy AOT compile and ship a cache, and the GPU host does the timing sweep:

- **AOT phase** (`build_aot`, `compile.py:17409`): resolve sources, hash `(source_set, host_cflags, device_cflags, search_space, pgo_state)`, look up the cell in the on-disk cache (JSON, `CACHE_VERSION == 4`, `compile.py:72-89,195`); on a miss, build with `torch.utils.cpp_extension.load` (ninja, `MAX_JOBS=$(nproc)`, arch-tuned codegen + LTO), record artifact path/size/mtime/SHA-256, mark `aot_completed_at`. No GPU needed.
- **JIT phase** (`build_jit`, `compile.py:17693`): load the search space, prefilter, run the autotune driver, pick the winner, write `csrc/algorithms/tuned_configs.h`, persist the winner to the canonical `_kernel_tuned.json`, and rebuild the artifact with the winning macros baked in.
- `--runtime {aot,jit,both}` (default `both`) spawns an AOT subprocess (CPU env) then a JIT subprocess (GPU env), each re-entering `main` on the same on-disk cache, so AOT and JIT can be tuned with independent env/library settings (`compile.py:62-70`).

**PGO** is optional and AOT-side: with `--pgo`, `build_aot` runs the 3-pass *instrument → workload → use* loop (`compile.py:17412-17413`, host-side LLVM PGO via `instrument_flags`/`-fprofile-generate` at `compile.py:3491-3520` and `-fprofile-use` at `compile.py:3531-3554`); the PGO state (workload hash) is recorded so subsequent runs short-circuit when the workload matches.

**The resumable Optuna-TPE search.** `--mode bayesian` (default) drives an Optuna TPE study (`TPESampler`, `compile.py:6549`) that **persists to a SQLite DB** at `<out_dir>/optuna_<opt>_<model>_<arch>.db` (`compile.py:16703-16704`) and is created with `load_if_exists=True` (`compile.py:6554-6556`) — so a Ctrl-C'd or cross-run sweep resumes its prior trials. `n_trials=None` means **no fixed budget**: a `BayesianEarlyStopper` (plateau Δ, EI floor, coverage-growth floor, wall-clock cap) governs convergence and `max_trials` is only a safety rail (`compile.py:16608-16624`). `--mode exhaustive` instead streams *every* prefilter survivor uncapped (`compile.py:16330-16346`). After TPE, a refine stage perturbs the top-K with ±2-step neighbours (elbow-detected when `top_k=None`, `compile.py:16917-16930`).

**The learned cost-model pruning** (`CostModel`, `compile.py:5551`) is **default-ON** and genuinely prunes: an XGBoost regressor (with sklearn → numpy-ridge fallback chain, `compile.py:5595-5647`) is retrained every `cost_model_retrain_every` completed trials (`compile.py:16632-16635`, retrain hook wraps the timer at `compile.py:16838`) and rejects predicted-slow TPE suggestions *before building* them — each skip saves a ~5-min compile. Two independent gates with their own rejection caps: an absolute-threshold gate vs `best_so_far`, and a multi-fidelity cheap-proxy gate against the rolling-window timing quantile (`compile.py:16410-16427,16898-16915`). It can warm-start from a persisted sibling-optimizer model (transfer learning, `compile.py:16653-16676`).

**`pick_winner`** (`compile.py:6824`) is the selection authority — covered next.

### The fp64-gate-in-loop correctness hook

This is the marquee correctness fix (task #28). The sweep's *timing* objective uses a cheap **same-dtype strict-fp32 self-consistency** oracle (variant-vs-strict-build of the same source). That oracle is unsafe to *select* on: two kernels sharing a rounding error agree, and an IL=4 reduction-order config can clear `np.allclose` yet be non-deterministic. So the winner is additionally gated against the **fp64 ground truth + A/A/A bit-determinism**:

- `_default_correctness_hook(spec)` (`compile.py:7215`) builds a callable `hook(candidate_trial) -> bool` that calls `run_cell_gate(cell_key)` from `tests/hw/test_l3tc_tail_gate.py` (`compile.py:7261-7277`). It returns `None` (→ historical timing-only selection) unless a GPU + built extension are present *and* the `(optimizer, model)` maps to a registered gate cell (`correctness_cell_key`, `compile.py:7253-7268`).
- `_jit_autotune` **installs** the hook on `spec.correctness_hook` on the GPU path just before dispatching the driver, unless the caller supplied one (`compile.py:16303-16319`).
- `pick_winner` then **re-checks the top-`correctness_top_k` (default 3) candidate winners** by ascending timing; the first candidate the hook accepts wins, a failure is **demoted** to the next-best, and a hook that *raises* is treated as a failure (fail-closed) (`compile.py:6928-6974`). If no top-K candidate clears it, the winner is left **UNSET** rather than shipping an unchecked one (`compile.py:6968-6974`). It is wired through at the call site with `strict_numerics`/`allow_nondeterministic`/`correctness_hook` (`compile.py:16957-16962`).

The hook ultimately reaches `_build_cell(model)` (`tests/hw/test_l3tc_tail_gate.py:551`), which builds the live race model from `g.DEFAULT_CONFIG` (`:561-569`).

> **RG4-scale caveat (a real, load-bearing discrepancy).** The compile.py hook comments repeatedly claim the re-check runs "at PRODUCTION scale (d=2048)" (`compile.py:7222`, `:6857`, `:8745`). It does **not**. `_build_cell` uses `grokking_race_v2.DEFAULT_CONFIG`, whose model is `dim_model: 128, num_layers: 2` (`grokking_race_v2.py:261`) — the small modular-arithmetic grokking-race ("RG4") scale, *not* the 1B-scale preset (decoder `dim_model 1600`, mamba `2048`, `grokking_race_v2.py:251-253`). So the in-loop fp64 oracle certifies correctness at d=128, and a winner whose tile/split-K geometry only manifests at production scale is **NOT** re-gated at d=2048 by this hook. The authoritative d=2048 check still lives only in the out-of-band hardware gate. **A senior engineer resuming this work should re-gate any non-default shape winner at d=2048 before shipping**, and treat the "production-scale" comments as aspirational. (The roofline %-of-peak secondary *does* use `_PRODUCTION_ROOFLINE_D = 2048`, `compile.py:7002` — but that is a reported number, not the parity gate's model size.)

`pick_winner` enforces several other filters unconditionally: drop `numerical_fail`; drop `non_deterministic` unless `--allow-nondeterministic` (the IL=4 trap, closed by default, `compile.py:6873-6883`); a generated/transformed `origin` in `_VALIDATION_REQUIRED_ORIGINS` is ineligible unless it recorded a strict-oracle PASS (`compile.py:6884-6892`); and **tiered-spill re-rank** — trials whose parsed ptxas-v report shows nonzero local-memory spill (`_trial_spill_breach`, `compile.py:7029`) are demoted *below* all clean trials in the sort key (re-rank, not hard-exclude, so correctness can still reach a spilling-but-correct trial, `compile.py:6898-6927`). Spill reaction (#23) and the roofline %-of-peak / sub-ceiling flag (#24, `_SUB_CEILING_PCT=0.10`, `compile.py:6977-7002`) are now *implemented* — the COMPILE_AUDIT listed them as gaps, but the current tree has the code.

The **dead-dim discipline** is central (`compile.py:1248-1303`). A producer→consumer audit found that of the ~22 emittable macros, only a handful are ever `#ifdef`'d by a committed kernel. `_kernel_source_macros()` (`compile.py:1348`) scans the device trees once to auto-detect which `SG_TUNED_*` macros kernels actually read; `_LIVE_TUNING_DIMS` (`compile.py:1300-1303`) is the explicit floor for the degenerate "no kernel tree visible" case. `_is_dead_dim`/`_pin_dead_dims` (`compile.py:1546`, used in `_sm90_full_space:2127`) **pin each dead dim to a single value** so it stops expanding the Cartesian product (which would inflate it ~10⁴× and waste TPE budget) and **drop it from `config_key`** so two binary-identical configs collapse to one cache entry (avoiding false cache misses). The first value of every macro dim equals the in-kernel `#ifndef` default so the no-JSON build is byte-identical (`compile.py:2160-2164,2202-2203`).

### The macro-injection floor (`_tuned_inject`) and byte-identical no-JSON builds

`compile.py`'s autotuner produces winners; **`grokking_optimizers/_tuned_inject.py`** is the *single source of truth* for making those winners ACTIVE in the shipped `_ops*.so` (lever (b)). It is **pure-stdlib** by design (`_tuned_inject.py:25-31`) so `setup.py` and a CPU-only unit test can import it by file path without triggering `grokking_optimizers/__init__.py` (which imports torch + probes CUDA).

- **Producer:** `build_jit` calls `_export_kernel_tuned_json` → `export_winner` the moment a JIT winner is decided (`compile.py:17763`, `_tuned_inject.py:610`), atomically read-merge-writing the canonical `grokking_optimizers/_kernel_tuned.json` (`_tuned_inject.py:725,731`). Schema is **nested per-model** `{arch: {model: {optimizer: combo}}}` (`#12`, `_tuned_inject.py:17-23`) so tuning the same optimizer on a second model no longer last-wins; an old flat `{arch:{optimizer}}` block is migrated in place on the next write and still *read* for back-compat (`_tuned_inject.py:330-363,669-689`).
- **Consumer:** `setup.py`'s `TunedBuildExtension` reads the JSON and, per CUDA TU, appends `-DSG_TUNED_*` macros (+ `--maxrregcount=N` when nonzero) by monkeypatching torch's ninja writer and rewriting each build edge's `cuda_post_cflags` (`_tuned_inject.py:758-818`). TU→optimizer mapping is filename-based: `launch_<opt>.cu` and `mega_<model>_<opt>.cu` get their optimizer's flags; everything else (bindings, model-only TUs) gets none (`optimizer_for_source`, `_tuned_inject.py:228-257`; `model_for_source` selects the per-model winner, `:260-295`).

The **SAFE floor** is the `MACROS` table (`_tuned_inject.py:151-161`): `mega_block`, `tile_m`, `tile_n`, `dec_dw_splitk`, `vit_dw_splitk`, `prod_regs`, `cons_regs` (each `-D<macro>=<v>`) plus `maxrregcount` (real ptxas flag, `0`=unset=emit nothing). Each entry records its **in-source `#ifndef` default** (e.g. `SG_TUNED_PROD_REGS=40`, `SG_TUNED_CONS_REGS=232`, `dec_dw_splitk=1`, `vit_dw_splitk=4`) so:

1. a **no-JSON build is byte-identical** to the committed kernel (no `-D` emitted at all when there is no winner; `load_tuned` returns `None` → `[]`, `_tuned_inject.py:520-535`), and
2. the **drift guard** `header_default_macros()` (`_tuned_inject.py:198-208`) lets the CPU-only test `test_macro_drift_against_header` (`tuning/test_build_injection.py:411`) assert the table's defaults still match the committed `#ifndef` guards in `csrc/` without a GPU. (This is precisely how the audit-noted `dec_dw_splitk` default-4→1 drift was caught and corrected.)

`_EMIT_ORDER` (`_tuned_inject.py:165-167`) keeps flag emission deterministic for stable `build.ninja` diffs. **Review-fix P0.2:** the exporter also persists *every other* winner dim that carries a macro in the live space, together with the producer-derived `{dim_name: SG_TUNED_MACRO}` map (`_live_macro_map`, `compile.py:17238`) recorded under the arch block's `_macros` key, so the stdlib consumer can emit `-D<macro>=<v>` for dims it has no hardcoded entry for — *without* importing compile.py (`_tuned_inject.py:366-449`, `export_winner` macro_map at `:697-707`). Tuple dims (`cluster_shape`) emit nvcc-safe per-axis `<MACRO>_0/_1/_2` + `<MACRO>_VOLUME` exactly as compile.py's `resolve_macros` does (a single `-Dfoo=2,1,1` is rejected by the `-D` lexer; `_tuned_inject.py:452-473`, mirror at `compile.py:3293-3308`). An unknown dim with no map entry is **ignored with a one-line warning** so a stale `setup.py` degrades gracefully.

### The Level-2 superoptimizer (#27, owner chose option (b))

`SUPEROPTIMIZER_SCOPING.md` (#25) measured a **no-go** for a full generative superoptimizer; the owner overrode the *recommendation* (not the *constraints*) and chose **(b): make Level-2 REAL, correctness-gated** (`SUPEROPTIMIZER_L2_PLAN.md:1-8`). Level-2 = Level-1's flag/macro search *plus* a generative structural-rewrite layer that emits new *sources* (synth, polyhedral, native-wgmma, CUTLASS/CK) rather than just new `-DSG_TUNED_*` values (`SUPEROPTIMIZER_L2_PLAN.md:46-48`).

**Current state: the scaffold is structurally wired but non-functional on the real path.** All five generative origins have honest origin-tagging (`ORIGIN_SYNTH`/`POLYHEDRAL`/`CUTLASS`/`CK`/`FASTMATH`, `compile.py:6791-6796`), the `_VALIDATION_REQUIRED_ORIGINS` winner gate (`compile.py:6806-6808`), and the source-swap are real and **fail-closed** — but:

- **The C0 fragment-emitter blocker is the real obstacle.** The emitter seam routes through `grokking_optimizers.codegen.emit_variant_source` when `spec.enable_emitter` is on (`compile.py:14630-14647`) — but **that module does not exist** (verified: no `grokking_optimizers/codegen.py`). The import hits the `except`, emits a loud warn-once (MED.6, `compile.py:14648-14661`), and falls back to a macros-only build; `_emitted_sources` is never populated. Worse, even the synth/polyhedral lowerers that *do* emit compilable CUDA emit a **standalone host-launch `__global__` kernel** with its own grid — `synth_elementwise_*` / `_emit_reduce_cuda` / `_emit_scan_cuda` all emit `__global__ void` (`compile.py:30039,30156,30490`) and polyhedral emits `launch_polyhedral_kernel` (`compile.py:29234`). This is **the C2 constraint** (`SUPEROPTIMIZER_SCOPING.md:120-133`): the persistent fused megakernel owns its grid and runs fwd+bwd+dW+optimizer between hand-built grid barriers; a host-launched collective cannot run device-side inside it. The fix (Phase C0, `SUPEROPTIMIZER_L2_PLAN.md:129-139`) is to **re-target the emitter to emit a device-inlinable `__device__` tile/epilogue fragment** spliced between barriers, NOT a launchable kernel — the genuine prerequisite the scoping no-go was pricing.
- **Native wgmma/tcgen05/mfma/wmma mainloop is a hard-OFF zero-fragment stub.** `_MMA_NATIVE_LOADS_WIRED = False` (`compile.py:30179`): the native bodies never stage real A/B tiles (cp.async dest is a literal `0` / explicitly-zeroed register fragments), so on the target arch they would compute on zeros. Until the loads are wired, `_gemm_native_mma_mainloop` returns `None` with a loud warn-once and the caller emits a numerically-correct **scalar triple-loop** fallback (`compile.py:30202-30232`). This deliberately avoids the silent-zero numerical bug. Per the re-spec, Phase C **sidesteps the GEMM synth entirely** (the hand engine is near-maximal) and synthesizes the *fusion* (the fp32 epilogue passes) on the real elementwise/reduce lowerers (`SUPEROPTIMIZER_L2_PLAN.md:118-127`).
- **Polyhedral** is opt-in (`enable_polyhedral=False`, `compile.py:8622,17964`) and gated on `spec.config["polyhedral"]["enable"]`; the hook reads the `_emitted_sources` the dead emitter never sets (so unreachable today), and `libclang`/`islpy` are soft deps — when absent, legality is heuristic and **every** polyhedral variant is forced behind the strict on-device oracle (`compile.py:15733-15766`). It only stamps `ORIGIN_POLYHEDRAL` when a transformed source actually lands on disk and is built (`compile.py:15794-15802`) — the prior fake-green (template wearing a polyhedral tag) was fixed.

**Correctness-gating is what makes this safe.** Because `pick_winner` makes any generated origin ineligible without a strict-oracle PASS, today's toy outputs would be correctly *rejected* — no fake-green. The remaining fake-green (#2 in the audit) — `build_jit`'s final source-swap checking only `== ORIGIN_SYNTH` and shipping the template for a polyhedral winner — has been **fixed**: it now swaps for any `origin in _SOURCE_GENERATING_ORIGINS` (= `_VALIDATION_REQUIRED_ORIGINS − {fastmath}`, `compile.py:6820-6821`), recovering the stashed generated source from `spec._emitted_sources["<ckey>:<origin>"]` and warning-and-falling-back-to-template if it cannot (`compile.py:17828-17872`). The fp64 oracle-in-loop (A2) is **landed** for the flag/macro path; the per-generated-candidate rebuild-before-fp64-gate is Phase-C0-coupled (there are no generated candidates today, so A2 is correct as-is, `SUPEROPTIMIZER_L2_PLAN.md:188-199`). The binding constraints — **C1** transport-only legality (ascending-k fp32 reduction order is non-associative; any reassociation fails the determinism gate), **C2** no-IR-expresses-the-megakernel, **C3** fp64-in-loop, **C4** the pattern library must contain the lever — are documented at `SUPEROPTIMIZER_L2_PLAN.md:49-74` and `SUPEROPTIMIZER_SCOPING.md:111-133,222-235`.

### Portability, the `--self-test` harness, and the build env

**The `tune_hook` seam** (`BuildSpec.tune_hook`, `compile.py:8611`) is the schema-agnostic portability seam: a project declares `[project] tune_hook = "pkg.module:fn"` in `compile_config.toml`, and the autotuner invokes that callable in a fresh subprocess per built `.so` with the contract `fn(*, so_path, model, optimizer, arch, regime, seed) -> {"output": np.ndarray, "elapsed_ms": float}` (`compile.py:8599-8623`, `_hook_capture` at `:14376-14417`). compile.py compares `output` (variant vs strict-math reference build) for correctness and uses `elapsed_ms` for timing — knowing nothing about the op. This is how the persistent megakernel (reached via a pybind `fused_step`, not a discoverable `torch.op`) plugs in. When no `tune_hook` is set but `capture_workload` is, a lighter portable reference-capture path is used (`compile.py:15175-15180,15455-15469`).

**Multi-arch dispatch** is table-driven: `ArchEntry` (`compile.py:434`) is the single source of truth per arch (vendor cuda/hip/pallas, gencode flags, smem/reg/warp limits, features, `l2_bytes`, and the `peak_tf`/`peak_bw` roofline constants added for #24, `compile.py:475+`). Per-arch space builders (`_sm90_full_space`, `_build_cuda_space`/`_build_cdna_space`/`_build_rdna_space`/`_build_pallas_space`) dispatch on vendor; `get_arch_entry` (`compile.py:1163`) routes pallas → `PallasTimer` and cuda/hip → the variant-`.so` timer. (Caveat the audit raised: Blackwell `sm_100a/103a/120a` route through the generic `_build_cuda_space`, so the rich TC tile surface is really sm_90-only today.)

**The `--self-test` harness** (`compile.py:18698-18701` intercept → `_self_test`, `compile.py:26864`) runs ~33 section helpers (`_self_test_search_space` … `_self_test_e2e_smoke`, `compile.py:26889-26921`) and ends with a **count-consistency guard**: it asserts the total cases run equals `_SELF_TEST_EXPECTED_COUNT = 265` (`compile.py:26861,26925-26935`) so the documented count can never silently drift from the real count. CPU-only, no GPU required. The separate stdlib injection test is `python -m tuning.test_build_injection` (`AUTOTUNE_LINKAGE.md:184`).

**The build env (`.fast_build_env.sh`)** must be sourced before any build/gate/compile command. It wires caching + parallelism (`.fast_build_env.sh:1-2`):
- `PYTORCH_NVCC=$ROOT/.build_tools/nvcc-cached` routes nvcc through **sccache** (torch calls nvcc directly, so sccache otherwise sees 0 requests) — the device cu→cubin cache (~200s/TU). The wrapper also adds `--threads 0` (auto-detect CPU count) (`.fast_build_env.sh:5-13,33`).
- `CXX=$ROOT/.build_tools/g++-cached` routes the host C++ through **ccache**; a 2026-06-17 fix symlinks the wrapper into a PATH dir because torch's `check_compiler_ok_for_platform` probes the *basename* `g++-cached -v` (not the full path), which had killed the `--jit-only` ABI probe for every cell (`.fast_build_env.sh:24-34`).
- Caches are volume-backed (persistent across instance close): `SCCACHE_DIR`/`CCACHE_DIR` under `$ROOT/.build_cache` (`.fast_build_env.sh:35-39`).
- **The SKIP_GENDEPS gotcha:** torch's `--generate-dependencies-with-compile` makes the nvcc command non-cacheable for sccache; `TORCH_EXTENSION_SKIP_NVCC_GEN_DEPENDENCIES=1` strips it (`.fast_build_env.sh:18-19,32`). Cache-hit correctness is unaffected — the caches hash the *preprocessed* source, so any header/macro change forces a real recompile (a stale hit is impossible, `.fast_build_env.sh:20-21`).

## Why it is latency-bound + the roofline reality + the perf methods

This section is the project owner's primary concern: an honest accounting of *where the time actually goes* at the roofline scale, *why* the megakernel sits far below the bf16 tensor-core peak, and *which perf levers won or lost and why*. Every number below is from the fresh re-profile (`/workspace/SuperGrok1.5/.perf/batch/decoder_reprofile_coarse.txt`, `decoder_reprofile_fwdfine.txt`) and the verdict ledger (`OPTIMIZATION_LEDGER.md`), cross-checked against the source.

### The measured roofline (honest, derived-from-time, not formally scored)

Peaks assumed throughout (H100 SXM): bf16 tensor-core dense **989.4 TF/s**, HBM3 **3.35 TB/s**, roofline **ridge ≈ 295 FLOP/byte** (`tuning/roofline.py:47`; `.perf/phase1_status_audit.md:7`; `grokking_optimizers/compile.py:686-688`). The roofline % is **derived from measured wall-time**, not a formal hardware score — that formal objective is the still-pending `#24` (`PLANNING_INPUT.md:16`). Two honesty caveats apply to every number below and the owner has insisted they be stated plainly:

1. The FLOP **numerator counts dense GEMMs only** (`tuning/decoder_bench.py:231`). The fused step is *mostly non-GEMM fp32 CUDA-core work* (attention, LayerNorm, GELU, bias/residual, embedding, cross-entropy) that fills the wall-clock denominator but contributes nothing to the numerator — so the roofline % **understates** true silicon utilization, especially at these tiny-d / short-seq grokking shapes (`.perf/phase1_status_audit.md:17`).
2. The % is per-step wall, one persistent kernel, **not** a sum of sub-kernel rooflines (`.perf/phase1_status_audit.md:16`).

| model | config | ms/step | achieved TF/s | % of 989 peak | arithmetic intensity | real bound |
|---|---|---|---|---|---|---|
| decoder | d=2048, B=16384 | **618** (fresh 616.4) | 64.0 | **6.48%** | ~12,239 FLOP/B | latency / phase-serialization |
| vit | d=2048, B=1024 | **~1434** (post-S=8, was 5759) | ~7.3 | **~0.74%** | ~3,252 FLOP/B | was B1 load-imbalance (fixed) |
| mamba3 | d=128, B=4096 (cannot scale past ~d142, smem-capped) | 221.6 | 0.30 | **0.0303%** | ~3,492 FLOP/B | scan-dominated (GEMM numerator near-meaningless) |

Sources: `.perf/phase1_status_audit.md:9-13`; `PLANNING_INPUT.md:16-21`. The decoder GEMM FLOPs/step = **3.961e13** (`decoder_reprofile_coarse.txt:7`). ViT's 4.02× from S=8 is the baked B1 sub-tile win (`OPTIMIZATION_LEDGER.md:149-158`, `SESSION_STATE.md:9`); mamba3 cannot place at d=2048 because the megakernel is smem-bound at one CTA/SM (`mamba3_layout.cuh:275-277`, `OPTIMIZATION_LEDGER.md:43`), so its roofline is permanently pinned at d=128.

### The phase breakdown of the 618 ms decoder step

From `decoder_reprofile_coarse.txt:10-21` (clock64 critical-path, median of 3 reps; the summed-phase total 646.1 ms slightly exceeds the 616.4 ms wall — the gap is host/launch + un-stamped slack, `decoder_reprofile_coarse.txt:9`):

| phase | ms | % of summed | what it is |
|---|---|---|---|
| **P1_fwd** | 178.5 | 27.6% | token-tile forward GEMMs (the cp.async-ring engine) |
| **P1_bwd** | 176.7 | 27.3% | dX backward GEMMs (same ring) |
| **B1_barrier** | 108.4 | 16.8% | grid-sync between P1 (fwd/bwd) and P2 (dW) |
| **P2_dW_GEMM** | 106.7 | 16.5% | weight-gradient GEMMs (operand-staging-bound) |
| **P3_opt_tail** | 38.0 | 5.9% | the fused optimizer update |
| **B2_barrier** | 20.1 | 3.1% | grid-sync into the optimizer tail |
| **P2_grad_asm** | 16.8 | 2.6% | gradient assembly |
| **B0_barrier** | 0.9 | 0.1% | initial grid-sync |

Two aggregates the owner tracks: the **GEMM phases P1_fwd + P1_bwd ≈ 55%** (and adding P2_dW the GEMM-engine phases reach **74.9%** of the wall — verified: (178.5+176.7+106.7)/616.4); and the **grid-barriers B0+B1+B2 = 256.2M cyc ≈ 129.4 ms = 20.0% of summed** (`decoder_reprofile_coarse.txt:21`), which is *pure serialization idle* — the persistent grid-barrier waits on the slowest CTA, so every fast CTA stalls. P3 the optimizer tail is **5.9%**, *not* the "<1%" the early ledger claimed — a real (if minor) headroom item, and the reason the "max the optimizer kernels" surface is non-trivial (`.perf/phase1_status_audit.md:21-24`, `OPTIMIZATION_LEDGER.md:38` documents the earlier mis-framing that the vec4-AdamW lever exposed).

### WHY it is latency-bound — the three mechanisms

This is the load-bearing claim and it is honest: the gap is **fixable inefficiency, not an Amdahl wall of unavoidable non-GEMM compute.**

**(a) The GEMM phases are ~11× slower than the ideal tensor-core time, and the gap is fixable, not compute-Amdahl.** The matmuls' *ideal* TC time is 3.961e13 FLOPs / 989.4 TF/s = **40.0 ms** (verified). Yet the GEMM-engine phases (P1_fwd + P1_bwd + P2_dW) take **~462 ms**. That ~420 ms gap is NOT "the rest is non-GEMM work the roofline can't count" — these phases *are* the GEMM phases. The gap decomposes into four fixable inefficiencies:
- **~20% barrier serialization** — slowest-CTA-gated grid-syncs (above), pure idle, attackable by phase overlap / fewer barriers / async.
- **The hand-rolled persistent wgmma running well below cuBLAS-class efficiency.** The engine lives in the persistent megakernel, so it cannot call a host-launched collective: `csrc/backends/cuda/sm_90/mma.cuh` is a real Sm90 TMA+wgmma collective but is "explicitly REJECTED for the persistent-megakernel path" (`PERF_ANALYSIS.md:49-50`) — a host collective can't run device-side inside the persistent grid. So the fix is bringing CUTLASS-class *technique* (multi-stage pipeline, TMA, swizzle, warp-specialization) into the hand-rolled engine, whose primitives already exist.
- **Non-GEMM work serialized rather than overlapped under the matmuls** — the ~10 `__syncthreads`-separated fp32 epilogue passes per layer (bias, GELU, residual, LN) run *between* GEMMs instead of hiding under them (`PERF_ANALYSIS.md:38`, the P1-epilogue-fusion lever).
- **1 CTA/SM giving low occupancy to hide HBM latency.** The persistent grid-barrier *requires* ≥1 CTA/SM — the launcher REFUSES to launch (`cudaErrorLaunchOutOfResources`) if occupancy < 1 (`model_stage_decoder_tc.cuh:180-181`; mirrored in `fused_mamba_megakernel.cuh:330`, `model_stage_vit.cuh:68`). At exactly one resident CTA/SM there is little latency-hiding slack; this is the structural cost of the no-cooperative-launch / hand-built GridBarrier design.

**(b) It is NOT bandwidth-bound either.** Arithmetic intensities are **3,252–12,239 FLOP/byte** (table above), far past the ~295 FLOP/byte ridge — and HBM traffic is only 0.003–0.16% of 3.35 TB/s (`.perf/phase1_status_audit.md:18`). Both the compute roof (6.48%) and the bandwidth roof are far away, so the step sits in a **third LATENCY regime below both roofs**: it is gated by serialization, drain/wait stalls, and single-CTA occupancy, not by either roofline edge.

**(c) The fwd/dX rings are now WGMMA-COMPUTE-bound, not drain-bound — the deeper-ring KEEP already hid the cp.async drain.** This is the freshest and most important refute. The `--fwd-fine` sub-profiler (`decoder_reprofile_fwdfine.txt:23-37`) splits the GEMM ring into ISSUE(cp.async) / WAIT(drain) / WGMMA(mma) / EPI / BARRIER:
- P1_fwd ring: WGMMA **46.6%** vs WAIT(drain) only **9.9%** → "COMPUTE/EPI-bound → deeper ring unlikely to help" (`:30`).
- P1_bwd(dX) ring: WGMMA **40.2%** vs WAIT **5.8%** → same verdict (`:37`).

Before the deeper-ring KEEP the same profiler showed fwd WAIT 43% vs WGMMA 31% and dX WAIT 56% vs 20% — i.e. it *was* drain-bound, deeper prefetch *was* the right lever, and it worked (`OPTIMIZATION_LEDGER.md:64-67`). Now the drain is hidden, so **S>4 buffering is measured-unlikely to help on the decoder** (`PLANNING_INPUT.md:13-14`, `.perf/phase1_status_audit.md:19`). The remaining fwd/dX headroom is in GEMM *efficiency* (tiling / TILE_M / interleave / occupancy / register pressure), not more buffering (`PLANNING_INPUT.md:26-28`).

### The design goal (owner directive): high % of roofline at EVERY scale

The directive is a high roofline fraction at *every* scale, and the diagnosis says that is largely achievable at the large shapes. At d=2048 the decoder's 6.48% is **mostly fixable inefficiency** (barrier serialization, sub-cuBLAS engine, un-overlapped epilogues, one-CTA occupancy) — the realistic target is 30–50%+, established by the proof point that the "~2% roofline was a STAGING artifact, not a hardware ceiling" (`OPTIMIZATION_LEDGER.md:61`, the dW-staging win that *doubled* the fraction). The residual **hard floor** is only at the very smallest shapes — d=128 tiny matmuls (mamba3, and the toy gate configs) — where the GEMMs are genuinely too small to fill the tensor cores. Crucially, **the fusion-vs-occupancy trade-off flips sign with scale**: the megakernel's aggressive fusion (one persistent kernel, 1 CTA/SM) pays off at large shapes where the GEMMs dominate and grid-barrier serialization is amortizable, but the same one-CTA/SM constraint that enforces the grid barrier *starves* latency-hiding at the smallest shapes where there isn't enough GEMM work to fill an SM.

### The perf levers + the empirical method

The method is the **keep/revert ratchet** (`OPTIMIZATION_LEDGER.md:1-11`): apply → build → **fp64 parity HARD-gate (rel 1e-4; SAM 2.5e-2) + A/A/A bit-determinism** → 3-seed timing at the roofline scale → **KEEP iff faster on 3+ seeds AND parity-clean, else REVERT**. Parity is a *gate, not a tiebreaker*; "neutral" counts as not-positive; every revert is root-caused so the mechanism redirects the next move. This is paired with the **relevance gate / profiling doctrine** — wire each model's per-phase profiler and confirm a lever targets a meaningful share *before* building it (the front-load-profiling that killed a wrong ViT excursion at zero cost, `OPTIMIZATION_LEDGER.md:142-158`).

Levers that **WON**:
- **decoder PIPE=1 / STAGES=4** — deepen the proven cp.async ring: **+1.49× (920 → 618 ms)**, roofline 4.35% → 6.475%, fp64+A/A/A green on 11/11 cells × 3 seeds. Mechanism: fwd/dX were *drain*-bound (confirmed by `--fwd-fine` first, per doctrine), so more in-flight loads hid the WAIT. Unblocked by converting `DecTcSmem` static→dynamic smem (the S=3 ring busts the 48 KB static `__shared__` cap; the 227 KB dynamic cap fits). `OPTIMIZATION_LEDGER.md:63-78`; baked default `model_stage_decoder_tc.cuh:185-186`.
- **dW contiguous-layout staging (`SG_TUNED_DEC_DW_STAGE=1`)** — **+2.05×** (1889.8 → 920.7 ms), the campaign's first major structural win, doubling roofline 2.08% → 4.35%. A cheap grid-cooperative pre-transpose writes dY/X once per step into K-contiguous scratch so the dW reuses the proven cp.async ring instead of the scalar transposed-strided gather. **SUPERSEDES** the earlier Track-C split-K=2 KEEP (split-K was a scalar-dW grid-fill mitigation; with fast staging the single-CTA dW wins). `OPTIMIZATION_LEDGER.md:60-61`. Cumulative decoder: 1889 → 618 ms ≈ **3.05× from session start** (`OPTIMIZATION_LEDGER.md:73-74`).
- **ViT B1 sub-tile S=8** — **4.02×** (5768 → 1434 ms), B1_barrier 51.2% → 41.9%, the #1 ViT lever; 36/36 gate calls clean (`OPTIMIZATION_LEDGER.md:149-158`, `SESSION_STATE.md:9`).

Levers that **LOST** (each root-caused — the mechanistic lessons are the payoff):
- **P0 producer/consumer pipelined dW GEMM (PIPE=2)** — fp64 gate PASSED but perf **REGRESSED −11.6%** (920 → 857-class; the older absolute pair was 1921.8 → 2144.8 ms), and depth-3/4 wouldn't even launch (occupancy < 1 vs the ≥1-CTA/SM grid-barrier invariant). **Root cause: the dW is STAGING-bound (~97% staging, ~3% MMA), not drain-bound** — you cannot hide a 97% staging cost behind a 3% MMA, and the producer/consumer split *reduced* the threads doing the already-slow staging. This is the OPPOSITE of the fwd/dX drain-bound regime, and it redirected the campaign to fix *staging* (the +2.05× DW_STAGE win) instead of pipelining the MMA. `OPTIMIZATION_LEDGER.md:52`. (The producer/consumer PIPE=2 also lost its head-to-head tournament against the deeper-ring STAGES=4, 857 vs 618 ms — `OPTIMIZATION_LEDGER.md:78`, `SESSION_STATE.md:11`.)
- **GEMM interleave IL 2→4** — bench −9.3% (the *fastest* lever found) but **A/A/A determinism FAILED** on all 10 decoder cells at d=128 (4-wide dW group-reduce is non-deterministic on ragged atom counts). It ran fine and faster at d=2048 where atoms divide evenly, so the bench *missed* it; the gate caught it. **KEY LESSON: bench-first is necessary but NOT sufficient — every winner must clear the full A/A/A gate.** `OPTIMIZATION_LEDGER.md:37`.
- **ViT dW staging twin** — the verbatim decoder-2× port to ViT: only **+4.5%** (ViT dW is just 3% of its step → not dW-bound) AND fp64+A/A/A gate-RED on supergrok2/vit; reverted. This + the mamba M0 defer crystallized the **META-LESSON: the decoder GEMM-staging win does NOT generalize** — ViT is non-GEMM-surface / B1-load-imbalance-bound, mamba is scan-bound; profile each model's actual bottleneck before picking its lever. `OPTIMIZATION_LEDGER.md:80-105, 142-147`.

Confirmed dry wells (do not re-pursue): optimizer P3-tail micro-opts (vec4 NEUTRAL, the tail is a small share), GEMM-tile knob cycling (converged — TILE_N=64 +51% slower, IL=4 broke A/A/A), and further batch/d scaling on the current code (decoder is the same ~2% at d=1024 and d=2048 → scale-invariant cap; the wins live in the structural levers, not in scaling). `OPTIMIZATION_LEDGER.md:39-44`, `PERF_ANALYSIS.md:46`.

## The correctness methodology (the HARD gate, transport-only rewrites, the ratchet)

This system is an aggressive performance project — a hand-built persistent megakernel, an autotuner that rewrites kernels, and a long series of structural perf levers — bolted onto a correctness contract that *never* moves. The discipline that makes that safe is a single non-negotiable **HARD gate** plus a **keep/revert ratchet** layered on top of it, and a hard-won catalogue of *fake-green* hazards that the gate machinery is specifically shaped to catch. Everything below is the "how do we know a change is correct, and how do we decide whether to keep it" half of the project.

### The HARD gate: fp64 parity + A/A/A bit-determinism

Every change must clear two checks, ANDed together, before it can be considered at all. The canonical statement of the verdict rule is in the ledger header: *"apply → build → fp64 parity HARD-gate + A/A/A determinism → 3-seed timing at the roofline scale → KEEP iff faster on 3+ seeds AND parity-clean, else REVERT. Parity/determinism is a gate, not a tiebreaker"* (`OPTIMIZATION_LEDGER.md:5-8`).

**(1) fp64 parity.** The bf16 wgmma megakernel is compared against a *pure-fp64* ground-truth oracle, run at the same shape, with the kernel's bf16 stays the compute precision and fp64 used only as the yardstick (`tests/hw/test_l3tc_tail_gate.py:11-13`). The per-cell harness `run_cell_gate` (`test_l3tc_tail_gate.py:1062`) runs one production L3-TC step through the exact route the race takes (`fused_train_step(..., gemm_impl="wgmma")`, `:1103-1105`), captures the TC-reduced grad and post-step params, and compares against the **canonical fp64 transcription** of the same single source the kernel compiles from (`csrc/algorithms/<opt>.h` → `ref_<opt>_step` in `test_reference_parity.py`, imported at `:1133-1135`). The comparison is structured in two surfaces:
- **(1a) params**, max-relative, default tolerance **1e-4** (`param_tol`, `:1346-1347`). 1e-4 is the *fp32-reorder band*: the kernel's elementwise tail rounds in fp32 in a different association order than the fp64 reference, and 1e-4 is the documented envelope for that (`:1336-1337`). Cells whose update goes through a non-tail numeric path widen it deliberately and document why: Muon's 2D weights run a 5-iteration Newton–Schulz that accumulates ~2e-3 fp32-vs-fp64, so muon uses `param_tol=2e-3` (`:399,408,1342-1345`).
- **(1b) state**, the *decisive* check, tolerance **1e-4** on `[m|v|extra]` (`:1369`). The docstring at `:1352-1359` explains why state, not params, is load-bearing: at step 1 every Adam-family tail collapses to ≈sign(g_amp) in the param update, so (1a) is blind to per-layer β1, amplification magnitude, and *state initialization* — all of which live in the state, not the sign. The grokfast `ema=g0` cold-start is the worked example: a kernel that inited `ema=0` matches params but diverges ~50× in the ema slice (`:1356-1359`).

The SAM-tier surfaces carry a *floor* tolerance instead of the reorder band, because a second backward through a bf16 kernel cannot reach fp32 reorder: **SAM sharpness/sam_dir use 3e-2 / 2.5e-2** (`test_l3tc_tail_gate.py:27-28`, `:439,445,476`). These are explicitly the bf16-TC-vs-pure-fp64 *measured floor* (~2.2e-2 sharpness / 1.87e-2 sam_dir), with the tol set above it (`:634,730`). The looksam sam_dir check is fed the kernel's *own* cached direction and validated against a pure-fp64 second backward perturbed by `ron·g` (`:1161-1224`), with a liveness assert that the oracle direction is `>1e-6` so the parity can never be vacuously satisfied by a skipped SAM phase (`:1222-1224`).

**(2) A/A/A bit-determinism.** The production step is re-run 3× from the same init with fresh state, and loss/grad/params must be **bit-identical** under `torch.equal` (`:1396-1411`). This is `torch.equal` exactly — not a tolerance — across `(L1==L2==L3)`, `equal(G1,G2)`, `equal(P1,P2)` (`:1410-1411`); the SAM cells extend it to `mu` and `sharpness` slices (`:866-869`). Determinism is achieved by *construction*, not luck: fixed batch→CTA ownership and ascending-CTA / ascending-k fp32 reduction order (`tests/hw/test_l3tc_tail_gate.py:6-7`; the mechanism is spelled out in `csrc/fused/sm_90/dec_weights.cuh:59-79` — fixed contiguous batch slices, single-writer per-element owner, one grid barrier, then a cross-CTA reduce summing partials *in ascending CTA index*).

The two checks are ANDed (`ok = tail_ok and det_ok`, `:1417`), and that conjunction is the HARD gate. The autotuner is wired to the *same* gate: `_default_correctness_hook` (`compile.py:7215`) builds a `pick_winner` hook that re-runs `run_cell_gate` and demotes any candidate that fails either leg, fail-closed (a raising hook is treated as a demotion, `:7250-7251,7277`). This was added precisely because the tuner's own timing oracle is fp32 self-consistency, which two co-wrong kernels can both pass — see the IL=4 hazard below.

### Transport-only legal rewrites vs NEEDS-PARITY changes

The rewrite rule that lets the project move fast: **a rewrite may reorder data movement freely, but it must PRESERVE the ascending-k fp32 reduction order.** If it does, bit-determinism and parity hold automatically and the change is *transport-only* — no re-gating drama. If it changes the numeric association, it is **NEEDS-PARITY**: it produces a valid-but-different fp32 reassociation that the gate must arbitrate against the 1e-4 reorder band.

Concrete examples the codebase ships:

- **ViT B1 sub-tiling (`SG_TUNED_VIT_P1_SUBTILE_S`)** is the canonical worked case. Decoupling P1 *scheduling* granularity from the 1088-row GEMM tile changes which global rows land in which CTA. The kernel comment classifies the surfaces precisely (`model_stage_vit_tc.cuh:150-162`): dW / biases / cls / pos grads are **byte-identical** (P2 reads activations by global token row and contracts ascending-k independent of P1 tiling, and each row is a sample-local function preserved by the whole-sample invariant), but the 10 LN-affine γ/β grads and the loss are **valid fp32 REASSOCIATIONS** — regrouping which rows sum into which CTA shifts the low bits — *"absorbed by the gate's 1e-4 fp32-reorder tol (the decoder already ships TILE_M 64/256 through the same gate)."* A/A/A still holds because S is fixed across the 3 runs (a fixed deterministic partition). The explicit conclusion: *"OFF = byte-identical; ON = a NEEDS-PARITY swept dim, the GPU fp64 + A/A/A gate is the arbiter"* (`:161-162`). The whole-sample invariant is a hard `static_assert` (`:239`).

- **decoder `SG_TUNED_TILE_M` 64/256** is the named precedent the ViT comment leans on: changing the token-tile row count is a valid fp32 reassociation of the same reduction, lands inside 1e-4, and the decoder already ships those alternates through the same gate (`OPTIMIZATION_LEDGER.md:40` records TILE_M→256 as SKIP +27.7% *on perf*, i.e. it was parity-legal and only lost on speed).

- **split-K dW (`SG_TUNED_*_DW_SPLITK`, factor G)** is the transport-only case that *does* preserve order. Splitting a tile's K-contraction across G CTAs adds parallelism, but the partials are summed by *"a deterministic ascending-chunk reduce ... no float atomics, fixed order → parity + A/A/A bit-determinism hold"*, and `G==1` routes to the byte-identical single-CTA path (`model_stage_vit_tc.cuh:97-104`; `fused_vit_megakernel.cuh:394`). Because the summation order is preserved, split-K is a transport-only rewrite — which is why it could be *kept* (decoder DW split-K 4→2, `OPTIMIZATION_LEDGER.md:36`).

The same "order lives in the summation, not who computes it" principle governs the cross-CTA optimizer reductions (Prodigy's global-d, GrokAdamW's grad-norm clip, Muon's Frobenius norm): they were deliberately moved off the *work-stealing task queue* (whose claim order varies run-to-run → non-associative fp32 regrouping → A/A/A violation) onto a **fixed contiguous element range per CTA + ascending-CTA owner-sum** (`fused_vit_megakernel.cuh:874-888`). The IL=4 reject (below) is the cautionary case where this discipline was violated.

### The keep/revert ratchet (the P-series discipline)

Once a change is parity-clean, perf decides its fate, and the rule is asymmetric on purpose: **parity is a hard gate; perf must be better on 3+ seeds to KEEP, else REVERT** (`OPTIMIZATION_LEDGER.md:5-8`). "Neutral" (no measurable gain) counts as not-positive and reverts. On any revert, the *mechanism* is root-caused and used to redirect the next decision (`:8`). The ledger is the canonical record of every KEEP / REVERT / NEUTRAL / SKIP with its why; representative entries:
- **KEEP**: decoder cp.async-ring −14.2% across all decoder cells (`Track A` 0005, `:24`); decoder DW split-K 4→2 −2.5% (`:36`); the Track-E dW staging fix 2.05× (`:61`).
- **REVERT**: vit SAM-scoped outline +5% slower (`:22`); the P0 decoder dW pipelined GEMM — *fp64 gate PASSED (correct), but perf regressed −11.6%*, root-caused to the dW being staging-bound not drain-bound, which then *redirected* the campaign to staging (`Track E` P0, `:52`).
- **REJECT** with the sharpest lesson: decoder GEMM interleave 2→4 was the **fastest** lever found (bench −9.3%) but **A/A/A FAILED** on all 10 decoder cells (IL=4 makes the dW M-atom groups 4-wide and the ragged atom counts make the 4-wide group-reduce non-deterministic). It ran fine and faster at d=2048 where atoms divide evenly, *so the bench missed it; the gate caught it.* The recorded takeaway: *"bench-first is necessary, NOT sufficient — every winner must clear the full A/A/A gate"* (`OPTIMIZATION_LEDGER.md:37`).

The structural safety net under the ratchet is **byte-identical OFF defaults for risky knobs**: a NEEDS-PARITY knob must `#if`-erase to the exact pre-knob kernel when off, so a never-engaged lever is provably inert. ViT subtile-S at the default value compiles the m_real row-guard and runtime-m_atoms code out entirely → *"the OFF build is BYTE-IDENTICAL"* (`model_stage_vit_tc.cuh:143-146`, guarded by `#if SG_TUNED_VIT_P1_SUBTILE_S < 64` at `:391`); split-K `G==1` takes the no-scratch single-CTA path (`model_stage_vit_tc.cuh:103-104`); the GEMM interleave width 1 is the bit-for-bit serial path (`:117`). This is what lets the autotuner expand the search space without risking the shipped default.

### Fake-green / oracle-trust hazards (and how they are caught)

The recurring failure mode this project keeps hitting is not a wrong kernel that *fails* a gate — it is a **fake-green**: a gate that passes while the thing it claims to verify is broken, usually because the oracle co-derives with the kernel or the discriminating instrument never runs. The standing audits (`.perf/oracle_trust_audit.json`, `.perf/test_coverage_gap_audit.json`) exist to hunt this class. The catalogue:

- **The macro-drift guard (table-vs-header).** The autotuner emits `-DSG_TUNED_*` flags from a hand-maintained `MACROS` table; if that table drifts from the kernels' `#ifndef SG_TUNED_*` guards, the tuner emits a `-D` no kernel reads (a silent no-op) or misses one. `header_default_macros()` (`_tuned_inject.py:198-208`) declares the asserted defaults, and `setup.py:_verify_macro_names` (`:944-970`) programmatically scans *all* of `csrc/` for the `#ifndef` guards and warns on any table macro not guarded anywhere. The audit note at `_tuned_inject.py:949-953` records *why* this had to become a tree-walk: the old single-file check pointed at a header (`kernels/sm_90/adamw_sm90.cuh`) deleted in the L3-TC-only cut, so it silently early-returned and *could never fire* — itself a fake-green.

- **The SG11 co-wrong oracle (cos operand).** The historical incident class: the kernel computing `cos(grad, MU)` instead of canonical `cos(grad, MOMENTUM)` as the gate's second cosine operand (`oracle_trust_audit.json` finding 2). The cold step-1 gate is *structurally blind* to it: at step 1 `m0=0 ⇒ cos=0 ⇒ gate=sigmoid(0)=0.5` regardless of the operand (`test_l3tc_tail_gate.py:798-803`), and at the default `rescale=0.1` the gate-dependent surfaces are damped below the 1e-4 param tol by Adam v-normalization. The catching instrument is `run_sg11_warmup_gate` (`:882`), which runs warm-up steps so `momentum≠0 ∧ mu≠0` genuinely diverge, pumps `rescale=2.0` so the term is above tolerance (`:919`), recovers the kernel's gate and asserts it matches `cos(grad,momentum)` AND *not* `cos(grad,mu)` — `gate_ok = (err_vs_momentum < 1e-2) and (err_vs_mu > 1e-1)`, two regimes separated by ~3 orders of magnitude (`:1009-1013`), with a non-vacuity assert that the warm-up actually exercised the divergence (`gate_div > 1e-4`, `:1054-1057`). The oracle-trust audit's *open* finding is that this discriminating test is **CLI-only (`--sg11-warmup`)** and never collected by pytest/CI (`oracle_trust_audit.json` finding 2; `test_coverage_gap_audit.json` RG1), so the CI path is still structurally pinned to gate=0.5 — a live coverage gap, not yet closed.

- **The autotune-hook d=128-vs-d=2048 scale lie.** `_default_correctness_hook`'s docstring promises *"PRODUCTION-scale (d=2048)"* validation (`compile.py:7220-7222`) and the inner comment repeats *"the SAME cell gate at production scale"* (`:7271-7274`), but the body calls `_run_cell_gate(cell_key)` (`:7277`) → `_build_cell` at the toy grokking scale (p=97, baked d=128, `test_l3tc_tail_gate.py:551,564`). There is no d=2048 rebuild anywhere in the hook. The audit flags this as exactly the SG11 shape — the validator's *claimed* scale and *actual* scale disagree — so a winner that is fp64-correct at d=128 but breaks at d=2048 (occupancy spill, tile-count-dependent reduction) is accepted and published (`test_coverage_gap_audit.json` RG4).

- **The SG2 mirrored-oracle (real-rank de-mirror + voting fidelity probe).** SG2's B1 anchor is `sg2_kernel_mirror.oracle_step`, which re-implements the *kernel's low-rank* CSA lightning-indexer (drops `idx_UQ`, normalizes `/sqrt(rank)`) rather than the *canonical full-rank* path (`(x@idx_DQ)@idx_UQ`, `/sqrt(d)`) — so `kernel == oracle` by construction for the indexer top-k and B1 cannot distinguish a correct low-rank indexer from a buggy one (`oracle_trust_audit.json` finding 1). The required fix is to **de-mirror** the reference back to the canonical full-rank indexer, and to make the only divergence-detecting instrument — the **N>64 CSA fidelity probe** — *vote* in the verdict. Today that probe only `print`s under `if verbose` and sets no `_ok` flag (`_sg2_l3tc_gate.py:320-333`), and the gate verdict is `ok = b1_ok and aaa_ok and tie_ok` (`:335`) — so an indexer regression consistent with the low-rank mirror passes silently. The same toothlessness afflicts the SG2 tie-probe, which validates the *oracle's own* strategy-A perm builder (a property of the test helper) rather than the kernel's segmented sort (`:290-318`; `test_coverage_gap_audit.json` RG16).

- **The `_emitted_sources` keying bug (polyhedral fake-green).** `build_jit`'s final source-swap checked *only* `origin == ORIGIN_SYNTH`, so a polyhedral/CUTLASS/CK winner left `final_sources = sources` (the un-optimized **template**) yet reported `origin=polyhedral` at the *winning* timing — a fake-green where the published artifact is not the thing that was timed. The fix generalizes the swap to any `origin in _VALIDATION_REQUIRED_ORIGINS` with a stashed `spec._emitted_sources[ckey:origin]` (`COMPILE_AUDIT.md:35-41`; the keyed stash is at `compile.py:6812,14645,8538`). The companion `_VALIDATION_REQUIRED_ORIGINS × {ok,deterministic}` winner gate is otherwise real and fail-closed (`COMPILE_AUDIT.md:15,165`).

- **The IL=4 / atomicAdd determinism trap** (the origin of the autotune fp64-hook): the fp32 self-consistency oracle the sweep uses for timing cannot catch a non-deterministic reduction order, so a `non_deterministic` config that merely clears `np.allclose` could win unless `strict_numerics` was on. The fix rejects `numerical_status=="non_deterministic"` unconditionally by default (`COMPILE_AUDIT.md:43-47`; `compile.py:6873,19195,23667`), and the fp64 `_default_correctness_hook` was added so the tuner re-checks winners against the *out-of-band* hardware gate that originally caught it.

The systematic prevention rules distilled from these incidents (`oracle_trust_audit.json` notes; `test_coverage_gap_audit.json` notes) are the project's standing oracle-trust doctrine: (1) **anchor direction** — every oracle's expected value derives from the canonical *algorithm* source, never from a restatement of what the kernel does; (2) **no two same-file twins** — an fp64 "oracle" and fp32 "mirror" differing only in precision/reduction shape fall to a single co-edit; (3) **operand-discrimination** — for any cosine/dot/selection, include a closed-form case where the correct and plausible-wrong operands give *different* answers and assert both equality-to-right and inequality-to-wrong; (4) **liveness = CI-collected and non-vacuous** — a discriminating instrument behind a CLI flag is not a guard; (5) **no silent reports** — any probe that surfaces a known divergence must set an `_ok` flag that votes in the boolean verdict.

### The recurring full-codebase audit discipline

The hazard catalogue is kept current by a *process*, not a one-off. The owner directive (`CODEBASE_AUDIT.md:3-6`) is: **after every landed step, run a comprehensive line-by-line analysis of the entire codebase** — modeled on the compile.py audit but tree-wide — hunting (1) bugs, (2) dead code to clean, (3) dead files to clean. "A step" is a landed commit (a KEEP/REVERT, a fix batch, a perf lever), and the audit runs *after* it is committed and gate-green, because auditing a mid-flight tree is wasteful (`:8-11`). Each run is an Opus swarm: contiguous range agents over `csrc/`, `grokking_optimizers/`, `tuning/`, `scripts/`, `tests/`, top-level, plus three cross-cutting agents — a **dead-file reachability graph** (import/include/build/test reachability), a **dead-code** symbol-never-called pass, and a **consistency** pass for duplicated/diverged logic (`:13-24`). Findings accumulate, deduped against prior runs, in `CODEBASE_AUDIT_FINDINGS.md` (`:25`). Deletion is conservative — *prove* a path is dead before removing, **flag-and-keep** anything ambiguous or not self-authored, and re-validate after every deletion, reverting anything that goes red (`:29-34`). Per-step runs re-sweep with deduped output but always re-run the cheap reachability graph to catch files newly orphaned by the step (`:37-39`). This is the loop that produced the two audit JSONs above and continues to surface the open coverage gaps (the SG11 warm-up gate not collected by CI, the autotune-hook scale lie, the non-voting SG2 probes) that future work must close.
