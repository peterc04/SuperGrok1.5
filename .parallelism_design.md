## 0. Ground truth — what is actually on disk (the things every choice below rests on)

Read these before changing anything; the design is shaped to them, not to a generic transformer.

### 0.1 The single-GPU megakernel (the asset we wrap, never split on the inside without NVSHMEM)
`csrc/fused/sm_90/fused_decoder_megakernel.cuh` — two kernels:
- **scalar** `fused_decoder_megakernel<Opt>` (default, fp32 owner-computes), launcher `launch_fused_decoder_megakernel<Opt>` (`:272`).
- **wgmma** `fused_decoder_megakernel_tc<Opt>` (`:431`), launcher `launch_fused_decoder_megakernel_tc<Opt>` (`:1081`), compiled only under `-DSG_TUNED_GEMM_IMPL=1`.

Phase/barrier layout of the **TC** kernel (the production path), all separated by the hand-built `GridBarrier` (`csrc/fused/megakernel_common.cuh:147`, CTA-count-agnostic, NO cooperative launch):
- **P0** zero per-CTA LN-vec partials + loss slot → `bar.sync()` (B0).
- **P1** token-tile-parallel **fwd+bwd through ALL layers, barrier-free within a tile** (`dectc_forward_tile`/`dectc_backward_tile`, `model_stage_decoder_tc.cuh`). Each CTA grid-strides over `kTileM=128`-row token tiles. Per-token linear inputs `X` and output adjoints `dY` are streamed to an **HBM bf16 `DecActs` buffer** (`model_stage_decoder_tc.cuh:180`), NOT kept resident. → `bar.sync()` (B1).
- **P2** deterministic grad assembly: dW **output-stationary** (`tile_id % nCTA` owns a weight-matrix tile, contracts full token dim `K=T`, ascending-`t`, **no float atomics**), optional **split-K G=4** over the ~62% idle SMs (`dectc_dw_run_tile_splitk`, ascending-chunk reduce), biases folded into the dY stream, embeddings owner-scan, LN-vec ascending-CTA reduce. → `bar.sync_reset(ctx.g_next_task)` (B2) — **this is the seam.**
- **P2.4 / P2.5 / P2.6 / P2.7 / P2.45 / P3-SG2** the optimizer-specific in-kernel stages (see §0.4).
- **P3** the optimizer apply tail: work-steal the 30 tensors, `apply_optimizer<Opt>` (the canonical `csrc/algorithms/<opt>.h` math).

**Why this matters for parallelism:** B2 is a clean cut. Everything before it is **fwd+bwd → reduced local grad in `grad[total]`**; everything after is **optimizer-over-grad → updated `params`**. The owner's locked multi-GPU decomposition (`/workspace/.campaign_plan.md:133-134`) cuts **exactly here**: `[fwd+bwd megakernel]  →  reduce-scatter(grad)  →  [sharded optimizer kernel]  →  all-gather(params)`.

### 0.2 The grad/param/state ABI (what reduce-scatter & all-gather move)
- `params` = flat `float[total]` concat of `named_parameters()` order. `total = kDecTotalElems` (`decoder_layout.cuh:31`; at the d=2048 benchmark scale = 25,401,443; the small race scale is `kDecoderTotalElems` mirrored host-side in `dispatch.cpp:518`). **Regenerated per size-ladder tier** by the campaign's codegen.
- `grad` = flat `float[total]`, parallel to `params`. Returned through the ABI tensor (`dispatch.cpp:531`).
- per-tensor `kDecOffsets[30]` / `kDecSizes[30]` live in `__constant__` tables (`decoder_layout.cuh:34/41`), read directly by P2/P3 — **the host passes no layout tensors.**
- optimizer state = `state` tensor, layout `[m | v | extra] + loss` = `3*total+1` for most; **larger** for prodigy (`4*total+4`), SG11/15 (`4*total+1+phi_pack`), SG2 (`(5+GH)*total+1`, `GH=4`) — see `dispatch.py:1845-1856`. The per-element shards (`exp_avg`, `exp_avg_sq`, `ema`, `mu`, `sharpness`, `sg2_slow`, `sg2_gru_state`, `param_init`) are flat blobs parallel to `params`; `rebase_state<Opt>` (`fused_decoder_megakernel.cuh:123`) offsets them per tensor.

### 0.3 The orchestration entry to make rank-aware
`grokking_optimizers/dispatch.py::fused_train_step(...)` (`:1714`) is the one-step entry: packs params→`flat`, packs inputs, calls `ops.fused_step(..., opt_only=False, gemm_impl=...)` (`:2196`), scatters `flat`→`p.data`, reads loss from `state[3*total]`. ## 1. The compile-time parallelism config (the metaprogrammed template)

### 1.1 The config struct + template parameter pack
New header `csrc/fused/sm_90/parallel_config.cuh` (device+host, header-only, included by every megakernel TU):

```cpp
namespace sg { namespace fused { namespace par {

enum class ZeROStage : int { Z0 = 0, Z1 = 1, Z2 = 2, Z3 = 3 };

// Compile-time parallelism point. ALL fields are constexpr so every branch that
// reads them folds at compile time -> the degenerate config emits ZERO comm code.
template <int DP, int TP, int PP, int SP, ZeROStage Z>
struct ParConfig {
    static constexpr int  kDP = DP;   // data-parallel replicas
    static constexpr int  kTP = TP;   // tensor-parallel ranks (Megatron col/row split)
    static constexpr int  kPP = PP;   // pipeline stages
    static constexpr int  kSP = SP;   // sequence-parallel (kept EXPRESSIBLE, fixed 1)
    static constexpr ZeROStage kZeRO = Z;

    static constexpr bool kIsSingleGPU = (DP==1 && TP==1 && PP==1 && SP==1);
    static constexpr bool kEmitComm    = !kIsSingleGPU;       // gate ALL NVSHMEM/NCCL
    static constexpr bool kShardParams = (Z == ZeROStage::Z3);
    static constexpr bool kShardOptGrad= (Z >= ZeROStage::Z2);
    static constexpr bool kTPComm      = (TP > 1);            // in-kernel allreduce
    static constexpr bool kPPStage     = (PP > 1);

    static_assert(SP == 1, "SP axis is expressible but must be 1 this campaign "
                           "(seq 4-17 makes a seq split moot; #14 / PARALLELISM-FINAL).");
    static_assert(DP>=1 && TP>=1 && PP>=1 && SP>=1, "degrees must be >= 1");
};

// THE single-GPU guarantee, named once so the static_assert reads cleanly.
using SingleGPU = ParConfig<1,1,1,1, ZeROStage::Z0>;

}}}  // sg::fused::par
```

The megakernel template gains a second type parameter:

```cpp
template <OptId Opt, class Par = par::SingleGPU>
__global__ void __launch_bounds__(SG_TC_MEGA_BLOCK)
fused_decoder_megakernel_tc(PersistentContext ctx, float* params,
                            DecoderTokenCtx tok, float* grad,
                            float lr, int step, FusedOptState st,
                            par::CommCtx comm /* default-constructed, unused when !kEmitComm */);
```

### 1.2 The BIT-IDENTICAL single-GPU specialization (the hard guarantee)
**Contract:** `fused_decoder_megakernel_tc<Opt, par::SingleGPU>` must be **byte-for-byte identical** to today's `fused_decoder_megakernel_tc<Opt>`. Enforced structurally, three ways:

1. **Default template arg** `Par = par::SingleGPU` → existing call sites (`mega_decoder_real_adamw_tc_launcher.cu`, all `tests/hw/*`) instantiate the single-GPU point unchanged with no source edit.
2. **All comm is `if constexpr (Par::kEmitComm)`-gated.** When `kEmitComm==false` (single-GPU) the compiler emits **no NVSHMEM symbols, no extra barriers, no `comm` reads**. The `comm` param is an empty POD; the ABI of the `<Opt>`-only overload is preserved by keeping the old non-`Par` launcher as a thin `=> <Opt, SingleGPU>` forwarder.
3. **A compile-fingerprint gate** (new `tests/hw/test_parallel_identity.py`, CPU-side via `nvcc -ptx`/SASS diff): assert the PTX of `<Opt, SingleGPU>` equals the PTX of the legacy `<Opt>` for adamw decoder. This is the mechanical proof the owner's "single-GPU stays MAXED, no overhead" rule (`/workspace/.campaign_plan.md:133`) holds. **[SPEC]** PTX may differ in symbol names only; the gate diffs the instruction stream modulo mangling.

Why `if constexpr` and not `#ifdef`: the campaign needs **both** points in **one** fat binary (the single-GPU artifact ships alongside the multi-GPU flagship), so the discriminator must be a template parameter, not a TU-wide macro. `SG_TUNED_GEMM_IMPL` stays a TU macro (scalar vs wgmma); `Par` is per-instantiation.

### 1.3 Host-side config plumbing
- Python: extend `ParallelConfig` (already in `distributed.py`) — **add `sequence_parallel: int = 1`** (currently absent; the docstring at `distributed.py:13` says "no 4th dim" — update to "expressible-but-1"). The `(DP,TP,PP,SP,ZeRO)` tuple maps 1:1 to the C++ template point.
- C++: `dispatch.cpp` gains a `ParConfig`-selecting switch. Because templates can't be runtime-selected, the build **instantiates a fixed allow-list of points** (see §7.2) and `dispatch.cpp` routes `(dp,tp,pp,zero)` → the matching explicit instantiation via a small `switch`. Unsupported points throw (no silent fallback — same discipline as the wgmma path, `dispatch.cpp:300`).

## 2. The multi-GPU step decomposition (cut at the B2 seam)

### 2.1 The decomposed step (DP + ZeRO-2/3, the first increments — NO TP/PP yet)
```
per rank r, per step:
  [0] (ZeRO-3 only) all-gather params for the layers this rank will run  ── §3
  [1] fused_decoder_megakernel_tc<Opt, Par> launch  ── runs P0..B2, produces grad[total] LOCAL (this rank's batch shard)
        ── the kernel STOPS at B2 if kShardOptGrad (do NOT run P3 in-kernel under ZeRO)  ── §2.2
  [2] reduce-scatter(grad)  over the DP group  ── each rank ends with reduced grad for its OWNED shard only
  [3] sharded optimizer kernel  ── apply_optimizer<Opt> over the OWNED shard  ── §2.4
  [4] all-gather(params)  over the DP group  ── every rank gets full params for next step's fwd  (ZeRO-3)
                                                or no-op (ZeRO-2, params already replicated)
```

The whole `[1]..[4]` sequence is **CUDA-graph captured** as one replayable unit (§2.6).

### 2.2 Where the kernel is cut: a compile-time early-exit at B2
The megakernel does **not** physically split into two binaries. Instead, P3 (and the P2.x optimizer stages) become **`if constexpr (!Par::kShardOptGrad)`**-gated: when ZeRO≥2, the fused kernel **returns right after B2** (the reduced *local* grad is in `grad[total]`), and a **separate sharded-optimizer kernel** consumes the reduce-scattered grad. When ZeRO≤1, P3 runs in-kernel exactly as today (full fusion preserved for the DP+ZeRO-1 baseline).

```cpp
// in fused_decoder_megakernel_tc, right after B2:
if constexpr (Par::kShardOptGrad) {
    // ZeRO-2/3: the optimizer runs in a SEPARATE kernel over the reduce-scattered,
    // SHARDED grad. The fused kernel's job ends at "local grad assembled".
    return;
}
// else: ZeRO-0/1 -> fall through to P2.4..P3 exactly as today (full fusion).
```

This keeps the **single-GPU and DP+ZeRO-1 paths fully fused** (the novel artifact) while the ZeRO-2/3 multi-GPU path takes the clean cut. The owner's rule (`:133` "multi-GPU splits the opt off after the grad reduce-scatter — a clean cut at the existing opt barrier") is realized literally as this `if constexpr return`.

### 2.3 The sharded-optimizer kernel (new, small)
New header `csrc/fused/sm_90/sharded_optimizer_kernel.cuh`:
```cpp
template <OptId Opt, class Par>
__global__ void sharded_optimizer_kernel(
    float* __restrict__ params_shard,   // [shard_numel] this rank's owned param slice
    const float* __restrict__ grad_shard,// [shard_numel] reduce-scattered grad
    float lr, int step, FusedOptState st_shard /* state ptrs pre-rebased to the shard */);
```
For **elementwise** optimizers this is a trivial grid-stride `apply_optimizer<Opt>` over `[0,shard_numel)` — reuses the *exact same* `csrc/algorithms/<opt>.h` math (no new math, no parity risk). It is essentially P3 with the work-steal-over-30-tensors loop replaced by a flat grid-stride over the shard, and **no GridBarrier** (single phase). This is why the elementwise cells are the first increments: the sharded optimizer is ~30 lines and reuses validated math.

**The per-TENSOR optimizers (muon/SG11/SG15/SG2) need the GridBarrier substrate** (their P2.x stages cooperate across CTAs per matrix/tensor) → the sharded-optimizer kernel for them is the *full* persistent kernel restricted to the tensors this rank owns. **This forces the ZeRO-3 shard to be tensor-granular for those cells (§3.4), not element-granular.**

### 2.4 Which optimizer state shards trivially vs needs care (the §0.4 taxonomy applied)
- **Trivial (elementwise, shard the flat `[0,total)` by `_even_partition`):** adamw, lion, grokfast, neuralgrok (psi pack replicated tiny), and the *elementwise core* of grokadamw/looksam/prodigy.
- **+ tiny extra all-reduce of a GLOBAL scalar** (do it on the **full** grad before reduce-scatter, OR all-reduce the partial across DP):
  - **prodigy**: `Σ d²·<g,p0−p>` and `Σ d²·|g|` — 2 floats. The in-kernel P2.6 already does an ascending-CTA reduce to 2 scalars; under DP, each rank computes its partial over its batch shard, then **one `all_reduce` of the 2-float pair across DP** before `update_d`. **Determinism:** fixed 2-element all-reduce, summed in a fixed rank order (NCCL ring is not order-deterministic across runs at the bit level for floats — **use a tree/`ncclAllReduce` with a fixed reduction or reduce to rank-0 + broadcast** to preserve A/A/A; **[SPEC]** this is the cross-rank analogue of the in-kernel ascending-CTA fix that resolved decoder/vit prodigy, `dispatch.py:805-824`).
  - **grokadamw**: global grad-norm `Σg²` → 1 float, same treatment (P2.5, `:710`).
  - **looksam**: global `‖g‖` → 1 float, same; **plus** the 2nd fwd+bwd must run on each rank's batch shard (it's a model recompute, naturally DP-parallel).
- **Per-MATRIX (muon):** the NS chain runs one 2D weight at a time across all CTAs (`:862`). Under ZeRO-3 the **whole matrix must live on one rank**; momentum `m` (the persistent buffer NS reads) must be **co-located with its matrix**. → tensor-granular shard.
- **Per-TENSOR (SG11/SG15/SG2):** meta-net mu (and SG2's segmented sort + CSA/HCA/PEER/GRU) consume a whole tensor's elements (`:923`, `:944`). → tensor-granular shard; `mu`/`sharpness`/`slow`/`gru_state` co-located with their tensor.

### 2.5 Bucket / overlap strategy — can reduce-scatter overlap P2 dW?
**Yes, partially, and this is the highest-value overlap.** `#14 FINDING` (`/workspace/.campaign_plan.md:142`) established P2 (dW) leaves **~62% of SMs idle** at production batch (forward is SM-saturated, dW is not). The reduce-scatter is **comm**, not SM work, so it overlaps P2's compute for free on a separate stream/CUDA graph node. Concretely:
- **Per-tensor grad readiness:** P2 assembles grads **output-stationary per weight tile** in `kDecOffsets` order. As soon as a tensor's grad is fully assembled in `grad[off:off+n]`, it can be **bucketed and reduce-scattered** while later tensors are still being assembled. This is the megakernel analogue of DDP's per-bucket backward hooks (`distributed.py:595` already implements the hook pattern for the framework path — reuse the bucketization `_bucketize`, `distributed.py:188`).
- **Implementation [SPEC]:** because the megakernel is one launch, the cleanest first cut does **not** interleave comm inside the kernel — it lets the kernel finish (grad[total] complete at B2), then fires **one bucketed reduce-scatter** of ~`reduce_bucket_size` (25M elems default, `distributed.py:103`) on the comm stream, overlapping the **next** micro-batch's fwd if pipelined, or P3 if ZeRO-1. True intra-kernel comm/dW overlap is the **NVSHMEM frontier** (§5) — deferred.
- **Bucket recommendation:** at the d=2048/25.4M-param scale, the whole grad is ~one bucket (100 MB fp32). Reduce-scatter of 100 MB over NVLink (~400 GB/s effective) ≈ 0.25 ms; step wall at B=16384 is ~119 ms (`roofline.py:83`) → comm is **<0.3% of step**, so **bucketing/overlap is a second-order optimization at single-node scale.** It becomes load-bearing only at the 20-30B multi-node ceiling the owner targets (`:132`). **Build it, but don't gate the first increments on it.**

### 2.6 The CUDA-graph capture boundary
The owner **lifted the "No CUDA graphs" hard rule for the multi-GPU step only** (`/workspace/.campaign_plan.md:134`): single-GPU megakernel = NO graph (it IS the anti-graph); multi-GPU step = graph-captured.
- **Capture unit:** the `[1]..[4]` sequence (kernel launch → reduce-scatter → sharded-opt kernel → all-gather), captured once after warmup, replayed every step. This kills CPU launch jitter so the NCCL collectives issue back-to-back.
- **Boundary:** capture **excludes** the Python host work in `fused_train_step` (param pack-in/scatter-out, loss readback). Those become **pre/post-graph** copies; the graph operates on the persistent `flat`/`state`/`grad_out` buffers already cached across steps (`dispatch.py:1821`, the persistent-buffer discipline is **exactly what graph capture needs** — buffers must be stable-addressed). **This is a happy alignment: the existing state_cache reuse makes the step graph-capturable with no buffer-lifetime redesign.**
- **NCCL + graphs:** NCCL collectives are graph-capturable since NCCL 2.9 / CUDA 11.3; capture on the same stream the kernels use, with the comm stream joined via events. **[SPEC]** the first increment can ship **without** graph capture (correctness first); add capture as a measured optimization once DP+ZeRO-2 is green — it should mainly help the small-model/high-step-rate regime where launch overhead dominates.
- **Portability note** (`:134`): graph / hipGraph / XLA-compiled per backend; the capture is conceptually portable, the API is per-backend. H100-only this campaign.

### 2.7 Determinism across the decomposition (the A/A/A contract extends to N ranks)
The single-GPU kernel is A/A/A-clean by construction (ascending-CTA reductions, no float atomics — the whole `dispatch.py:805-833` saga). The decomposition adds **two** non-determinism surfaces:
1. **reduce-scatter / all-reduce float summation order across ranks.** NCCL's ring/tree reduction order is **not guaranteed bit-identical run-to-run** for floats. → for the **global scalars** (prodigy d, grokadamw norm, looksam ‖g‖) use **reduce-to-rank-0 + broadcast** with a fixed ascending-rank fp64 sum (mirrors the in-kernel CTA-0 ascending fp64 sum, `fused_decoder_megakernel_tc:545`). For the **grad reduce-scatter**, bf16/fp32 ring order differs but the *downstream optimizer* tolerates it within the existing parity tol **only if** every rank uses the SAME reduced grad — which reduce-scatter guarantees per-shard. **Cross-rank bit-determinism of the final params requires a fixed-order grad reduction** → see §6.4 (the cross-rank A/A/A gate) and the **fixed-order reduce** recommendation.
2. **shard boundary placement** must be deterministic (it is: `_even_partition` is pure, `distributed.py:717`).

## 3. ZeRO stages on this kernel

### 3.1 ZeRO-2 (state+grad shard, params resident) — fits the INTACT megakernel
- params replicated on every rank → **the fused kernel runs unchanged** (it reads full params, produces full local grad).
- grad: reduce-scatter over DP (each rank keeps its shard).
- opt state (m/v/...): each rank allocates only its `1/DP` shard.
- params after step: **no all-gather needed** (params are replicated; each rank updated only its shard, so a **`all_gather` of the updated param shards** IS needed to re-replicate — wait: ZeRO-2 keeps params replicated but each rank only *computes* its shard's update, so it must all-gather the updated params too). **Correction:** ZeRO-2 shards *grad + opt-state* but **not params**; to keep params replicated after a sharded update, you all-gather the updated param slices. The only ZeRO-2 vs ZeRO-3 difference is **whether params are sharded in HBM between steps** (ZeRO-3) or replicated (ZeRO-2). For our megakernel both still do the reduce-scatter(grad) + sharded-opt + all-gather(params) dance; **ZeRO-2's win is smaller (only m/v/grad sharded), ZeRO-3 adds the param-resident shard.**
- **This is a BRING-UP CHECKPOINT, not a candidate end state** (deliverable = full 4D+ZeRO-3, locked): ZeRO-2 = the SAME ZeRO-3 code path with param-sharding off (params resident), booted first because the kernel body is untouched — only the host-side reduce-scatter/all-gather + sharded-opt kernel are new. A failure here is attributable to the collective dance, not param residency; ALL of this code carries into ZeRO-3 unchanged. The flagship ships ZeRO-3.

### 3.2 ZeRO-3 (param shard → per-layer all-gather) — the honest options
ZeRO-3 keeps only `1/DP` of params resident, so the fwd+bwd must **gather params on use**. The megakernel reads params throughout P1 (all layers, barrier-free) — so the gather granularity question is real:

- **(a) Full pre-gather before launch.** All-gather the entire param set into a full `params[total]` buffer, run the intact kernel, free the buffer after. **No memory win** (you reconstitute the full param set in HBM for the kernel's lifetime) — defeats ZeRO-3's purpose. **Reject** as the steady-state, but it is the **trivially-correct fallback** and the **first ZeRO-3 increment** (proves reduce-scatter/all-gather + sharded-opt correctness with the kernel literally unchanged; memory win deferred).
- **(b) Per-phase gather between barrier phases.** Gather layer-`L`'s params just before P1 needs them, free after. **Problem:** P1 is **barrier-free within a tile across ALL layers** (`model_stage_decoder_tc.cuh:22-24` explicitly rejects per-layer grid barriers — the whole tile flows through all layers with no barrier). There is **no per-layer seam** in P1 to hang a host-side gather on without reintroducing the rejected barrier. → **(b) is incompatible with the current fused fwd+bwd unless P1 is re-cut per-layer**, which sacrifices the barrier-free fusion (the asset). **Reject for the transformer megakernel** at small layer counts; **[SPEC]** could be viable at the 24-48-layer ladder depths where per-layer-block prefetch amortizes, but only if PP-style stage cuts already exist (§4).
- **(c) In-kernel NVSHMEM gather.** The kernel issues device-initiated `nvshmem_get` for a remote param shard exactly when a wgmma loop needs it (overlapping the get with compute on the resident shard). **[FRONTIER]** This is the same device-initiated-NVSHMEM machinery as TP (§5) and carries the same risk. It's the only option that gets ZeRO-3's memory win **without** cutting P1's barrier-free fusion.

**Recommended increment path for ZeRO-3:**
1. **(a) full pre-gather** — ship it first. Correct, simple, validates the collective dance. Memory win = 0 but it unblocks PP/TP development and the science runs at sizes that fit anyway.
2. Measure: does any **target-scale** model (the 20-30B ceiling, `:132`) actually OOM with full-pre-gather ZeRO-3? At ≤13B single-node it likely **fits without the memory win** (the owner's own dissent, `:138`, notes DP+ZeRO-3 fits ≤6.7B on 8×80GB). If it fits, **(a) is sufficient** and (c) is unnecessary complexity.
3. Only if a target size OOMs under (a): pursue **(c) in-kernel NVSHMEM param gather**, co-developed with TP's NVSHMEM (§5), behind the same go/no-go gate. **Do NOT build (c) speculatively** — it's frontier risk for a memory win that may not be needed at single-node scale.

### 3.3 The honest ZeRO-3 memory accounting [SPEC]
At d=2048/25.4M params the model is tiny; ZeRO is irrelevant. ZeRO earns its keep at the flagship (`#14`/PARALLELISM-FINAL targets 6.7B→20-30B). For a 6.7B lean cell (adamw, ~18 B/param state per `:101`): params 27 GB fp32 + m/v 54 GB = 81 GB → **OOMs one 80 GB H100 by itself**; ZeRO-3 over 8 → ~10 GB/rank state, fits with room for activations+batch. For a 6.7B **heavy** cell (SG2 ~44 B/param, `:101`): state alone ~295 GB → ZeRO-3/8 ~37 GB/rank — fits. **So ZeRO-3 is genuinely required at the flagship size; option (a) full-pre-gather reconstitutes 27 GB of params transiently per step — that's the one number to watch for the OOM that forces option (c).**

### 3.4 The shard partition must respect the per-TENSOR optimizer constraint
`ZeRO3Sharder._even_partition` (`distributed.py:717`) splits the **flat** param mid-tensor. **That breaks muon/SG11/SG15/SG2** (§0.4/§2.4): their P2.x stages need a whole matrix/tensor on one rank. → **Add a tensor-granular partition mode** to `ZeRO3Sharder`:
```python
def partition_tensor_granular(self, named_params):
    # assign WHOLE tensors to ranks (greedy by numel, balanced), so no tensor
    # is split across ranks. Required for muon/SG11/SG15/SG2 (per-tensor opt math).
    # Elementwise opts may use the finer _even_partition (better balance).
```
The shard mode is **keyed off the optimizer** (elementwise → flat-even; per-tensor → tensor-granular). This is a **new requirement the existing layer does not model** and is mandatory for the per-tensor cells. Balance: tensor-granular is lumpier (the embedding + ff matrices dominate), so DP efficiency for muon/SG2 is slightly lower than for adamw — **honest cost, measure it.**

## 4. Pipeline parallelism (PP)

### 4.1 Where the megakernel could cut into stages
PP splits the **layer stack** across stages. The decoder megakernel runs all `kLayers` layers inside one P1 (barrier-free per tile). To make stage `s` own layers `[L_s, L_{s+1})`:
- **The cut is between layer blocks.** Unlike ZeRO-3's per-phase gather (§3.2(b), rejected), a PP cut is **coarser**: stage `s`'s kernel runs fwd for its layers, **sends activations** to stage `s+1` (host-NCCL P2P or NVSHMEM), which runs the next layers. The bwd reverses. Each stage is **its own megakernel launch** over its layer subset.
- **Crucially, PP breaks the fwd+bwd fusion** (`:138` foresaw this): a pipeline interleaves micro-batches' fwd and bwd (1F1B), so a stage's kernel can no longer do fwd-then-bwd-in-one-launch for a micro-batch — it does **fwd-only** launches and **bwd-only** launches, scheduled by the 1F1B driver. → **PP requires splitting the fused megakernel into a fwd-only and a bwd-only kernel** (the activations checkpoint to HBM, which the TC path **already does** via `DecActs`, `model_stage_decoder_tc.cuh:180` — the acts are already in HBM, so a fwd-only kernel that stops after writing `DecActs` + a bwd-only kernel that reads them is a **natural cut the current acts-to-HBM design enables**).
- **Per-layer-block boundaries already separated by grid barriers?** **No** — P1 is barrier-free across layers by design. PP's cut is therefore **per-launch** (one kernel per stage's layers), not per-in-kernel-barrier. The acts-to-HBM design (every layer's `X_in/X_ctx/X_x1/X_gact/dY_*` already staged to HBM) makes the stage boundary clean: stage `s+1` reads stage `s`'s `X_in[L_s]` from HBM (locally or via P2P).

### 4.2 Microbatch scheduling (1F1B)
Standard 1F1B (Megatron). The `DistributedContext.pp_group` + `is_pipeline_first_stage`/`is_pipeline_last_stage` (`distributed.py:527`) already exist; the **schedule driver is new** (Python, host-side): warmup fwds, steady 1F1B, cooldown bwds, with `pp_group` P2P sends. This is **conventional** — the novelty/risk is entirely in splitting the fused kernel into fwd-only/bwd-only halves (§4.1).

### 4.3 Honest cost analysis at race scale vs ladder depths
- **At 4-17 seq / 2-layer race models:** PP is **pure overhead** — 2 layers can't fill a 2+ stage pipeline (the bubble is the whole thing), and the activation send dominates the tiny compute. **PP buys nothing below ~GPT2-medium depth.** Do **not** PP the science/race runs.
- **At ladder depths (24-48 layers, the flagship):** PP becomes worthwhile **only when** the model doesn't fit even under TP+ZeRO-3, i.e. at the 20-30B ceiling (`:132`). The bubble fraction ≈ `(PP-1)/(microbatches + PP-1)`; at 48 layers / PP=2-4 with enough micro-batches it's amortizable. **[SPEC]** at ≤13B single-node, the owner's own dissent (`:138`) is correct that DP+ZeRO-3 likely beats anything with PP on throughput; PP's payoff is the multi-node / absolute-ceiling regime.
- **Verdict (owner-locked):** PP is the **3rd bring-up increment** (after ZeRO-3) and **SHIPS in the flagship regardless** — full 4D (DP×TP×PP) is the locked deliverable. The measurement plan still quantifies PP's per-size contribution honestly (expected: pure overhead at race scale; amortizing at 24-48-layer ladder depths; load-bearing at the 20-30B ceiling) and reports the measured crossover — but PP's inclusion in the flagship config is NOT contingent on the number.

## 5. Tensor parallelism via device-initiated NVSHMEM (the FRONTIER piece — LAST increment, explicit go/no-go)

### 5.1 Where the all-reduce lands (Megatron col/row split)
TP splits each linear's weight matrix across `kTP` ranks. Megatron pattern for the decoder block:
- **Attention:** `in_proj` (QKV) is **column-parallel** (each rank owns `3d/TP` output cols → its own heads), `out_proj` is **row-parallel** (each rank owns `d/TP` input rows). The **all-reduce lands after `out_proj`** (sum the partial attention outputs across TP) — i.e. right where the current kernel finishes the attention block and adds the residual.
- **FFN:** `ff0` (d→dff) column-parallel, `ff2` (dff→d) row-parallel. **All-reduce after `ff2`**, before the residual add.
- So **two all-reduces per layer** (post-attn, post-FFN), exactly Megatron. In the megakernel these land in `dectc_forward_tile` after the `out_proj` GEMM (`model_stage_decoder_tc.cuh:712`) and after the `ff2` GEMM (`:743`); the **backward** mirrors with all-reduces on the input-grad (dX) of the column-parallel pieces.

### 5.2 Device-initiated NVSHMEM inside the wgmma loops
The owner locked **device-initiated NVSHMEM** to keep the fusion (`/workspace/.campaign_plan.md:131`): instead of ending the kernel to do a host-NCCL all-reduce, the kernel itself issues `nvshmemx_float_sum_reduce` (or a hand-rolled `nvshmem_put` + barrier ring) at the two reduce points, **inside the persistent kernel**, between the GridBarrier phases.
- The all-reduce sits on a **new in-kernel grid barrier** boundary: after the row-parallel GEMM writes its partial, `bar.sync()` → NVSHMEM all-reduce the partial across the `tp_group` → `bar.sync()` → continue. The GridBarrier substrate (`megakernel_common.cuh`) already gives the cross-CTA rendezvous; NVSHMEM gives the cross-**GPU** rendezvous.
- **Determinism (A/A/A) implication:** the cross-rank reduce **must be fixed-order**. A naive `nvshmem_float_sum_reduce` does not guarantee a fixed float summation order across ranks → ULP drift run-to-run → A/A/A failure (the exact class the in-kernel ascending-CTA fix cured locally, `dispatch.py:805`). → **implement a fixed-order ring reduce** (rank 0 += rank 1 += ... ascending, fp32 or fp64 accumulate) so the order is structural, not timing-dependent. This is the cross-rank analogue of `fused_decoder_megakernel_tc`'s ascending-CTA fp64 sum (`:545`). **This is non-negotiable for the A/A/A gate (§6.4).**

### 5.3 The host-NCCL fallback (if device-TP proves infeasible)
If device-initiated NVSHMEM TP can't hit parity/determinism/perf, **fall back to host-NCCL TP with the kernel split per-block**: cut the megakernel at the two reduce points into 3 sub-launches (pre-attn-reduce, attn-out→pre-ffn-reduce, post-ffn-reduce→end), host-NCCL `all_reduce` (the existing `DistributedContext.all_reduce_tp`, `distributed.py:536`, **already implemented**) between sub-launches. **This sacrifices the in-block fusion** (the whole point of device-TP) but is **conventional and low-risk** — it's literally Megatron with the megakernel as the per-block compute. The fallback is **always available** because `all_reduce_tp` already exists.

### 5.4 Scope it as the LAST increment with an explicit go/no-go gate
**Build order (locked, `:139`):** DP+ZeRO-2 → ZeRO-3 → PP → **TP(NVSHMEM) last**.
**Go/no-go gate for device-TP (author this as `tests/hw/test_tp_nvshmem_gate.py`):**
- **GO criteria (all must hold):** (1) device-TP all-reduce produces **bit-identical** params to host-NCCL TP on the same input (parity); (2) **A/A/A bit-exact** across 3 re-runs (the fixed-order ring works); (3) device-TP MFU **beats** host-NCCL-split TP at the target TP degree (else there's no reason to take the frontier risk — just use the fallback); (4) it **composes** with ZeRO-3 + DP without deadlock (NVSHMEM + NCCL + GridBarrier coexistence).
- **NO-GO:** ship the **host-NCCL TP fallback** (§5.3) and record device-TP as future work. The flagship still gets 4D (DP×TP×PP+ZeRO-3) — just with host-NCCL TP instead of in-kernel NVSHMEM TP. **The owner's "maximal accomplishment" goal is met either way; only the in-block-fusion bragging right is at stake.**
- **Honest risk register [FRONTIER]:** NVSHMEM device-init comm inside a persistent megakernel with a hand-built GridBarrier is genuinely unproven in this codebase (zero existing NVSHMEM usage — grep confirms). Risks: (a) NVSHMEM init/teardown vs the persistent-kernel + CUDA-graph lifetime; (b) NVSHMEM barrier vs the custom GridBarrier interaction (two barrier systems must not deadlock); (c) register/occupancy pressure (the TC kernel is already at 128-166 regs decoder / **255 regs occ-1 zero-margin on mamba/vit**, `:152` — NVSHMEM calls may spill and **kill occupancy → GridBarrier hang**, the launcher's `occ>=1` refuse-or-hang invariant, `:291`); (d) determinism (§5.2). **Recommendation: this is the one piece most likely to slip or get descoped to the host-NCCL fallback. Plan the instance-hours so the flagship is shippable WITHOUT it (4D via host-NCCL TP), and treat in-kernel NVSHMEM TP as the stretch goal.**

## 6. NCCL/NVSHMEM bootstrap + Python orchestration deltas

### 6.1 Bootstrap
- **NCCL:** via `torch.distributed` init — **already done** in `DistributedContext.initialize` (`distributed.py:331`, reads `WORLD_SIZE`/`RANK`, `init_process_group(backend="nccl")`, builds DP/TP/PP/EP subgroups). **Reuse as-is.**
- **NVSHMEM [FRONTIER]:** needs a separate `nvshmem_init` keyed to the same rank/world (bootstrapped off the NCCL uniqueId or MPI). New `csrc/bindings/nvshmem_bootstrap.cu` (host) exposed via a pybind `init_nvshmem(rank, world, tp_group_ranks)` called once per process after `init_process_group`, **only when `kTP>1` and the device-TP go-gate passed**. Teardown coordinated with CUDA-graph destroy. **This is new and is the riskiest bootstrap piece.**

### 6.2 `fused_train_step` → a rank-aware variant
New `fused_train_step_distributed(..., par_ctx: DistributedContext, sharder: ZeRO3Sharder, par_config)` in `dispatch.py`, wrapping the existing `fused_train_step` (`:1714`):
```
1. (ZeRO-3) all_gather_params -> full `flat`         [sharder.all_gather_params, exists]
2. pack params -> flat; pack THIS RANK's batch shard inputs   [existing pack code]
3. ops.fused_step(..., opt_only=(ZeRO>=2 ? "stop-at-B2" : False), gemm_impl, par_point)
      -> local grad in grad_out[total]               [the kernel early-exits at B2 under ZeRO>=2, §2.2]
4. (global-scalar opts) all_reduce the prodigy/grokadamw/looksam scalar(s)  [fixed-order, §2.4]
5. reduce_scatter_grads(grad_out) -> owned grad shard [sharder.reduce_scatter_grads, exists]
6. sharded_optimizer_kernel<Opt> over the owned shard [new, §2.3]   (or in-kernel P3 if ZeRO<=1)
7. all_gather_params(updated shards) -> full params   [sharder.all_gather_params, exists]
8. scatter flat -> p.data; read loss                  [existing]
```
Steps 3-7 are the **CUDA-graph-captured** unit (§2.6). Steps 2/8 (host pack/scatter) are outside the graph.
- **The race driver (`grokking_race_v2.py` / the science loop) gets a `par_ctx` argument**; single-GPU runs pass a degenerate `world_size=1` context (every collective no-ops — `distributed.py` already guarantees this), so **the single-GPU path is literally unchanged** (the no-op-collective degradation is the same property that keeps imports safe today).
- **Launcher:** `torchrun --nproc_per_node=8` (reuse `test_3d_parallel.py`'s `__main__` pattern, `:312`). A custom launcher is **not needed** — torchrun + the existing env-var bootstrap suffices. **[SPEC]** NVSHMEM may want MPI launch instead of torchrun; if so, a thin `mpirun` wrapper that also sets the torch env vars (so both NCCL and NVSHMEM bootstrap) — decide at the device-TP go-gate, not before.

### 6.3 wiring_check / tail-gate / A-A-A extended to N ranks
- `wiring_check.py` (the arbiter, asserts path==L3-TC via captured `LAST_L3_ENGINE=="wgmma"`, `wiring_check.py:14`) gains a **rank-aware mode**: under a launched job, **every rank** must report `engine=="wgmma"` and pass its **local** tail-gate; rank 0 aggregates. The per-rank check is the existing check; the new part is the **collective assertion that all ranks agree** (a `dist.all_reduce` of a pass/fail bit, fail-loud if any rank diverges).
- The tail-gate parity (`tests/hw/test_l3tc_tail_gate.py`) runs **per-rank on its shard** vs a single-GPU oracle restricted to that shard — the sharded-opt kernel must match the in-kernel P3 over the same elements (§7.3).

### 6.4 THE cross-rank bit-determinism gate (new, the load-bearing multi-GPU correctness check)
New `tests/hw/test_cross_rank_determinism.py`: run the **same** init + data on `N` ranks, A/A/A (3 re-runs), assert the **final all-gathered params are bit-identical across all 3 runs AND match the single-GPU reference within the existing parity tol** (SG-family ~3e-5 fp32, per `/workspace/.campaign_plan.md:12`). This is the gate that forces:
- fixed-order grad reduction (reduce-to-rank-0+broadcast for scalars; a fixed-order/tree reduce-scatter for grad, §2.7);
- fixed-order NVSHMEM ring for TP (§5.2);
- deterministic shard boundaries (already true).
**Without this gate the multi-GPU path is not trustworthy** — it is the N-rank extension of the A/A/A discipline that the entire single-GPU campaign already lives by. **This is the single most important new test.**

## 10. The honest bottom line (risks + the contract)

- **Lowest risk, do first:** the `SingleGPU` byte-identity gate (§1.2) + DP+ZeRO-2 (§3.1) + the entire 1-GPU-testable suite (§7). This is ~all authorable before the rental window and de-risks the orchestration + the B2 cut + per-optimizer sharding.

- **Highest risk [FRONTIER]:** device-initiated NVSHMEM TP (§5) — unproven in this codebase, register/occupancy + determinism + NVSHMEM-vs-GridBarrier-vs-CUDAgraph interactions. **Budget so the flagship ships as 4D-via-host-NCCL-TP without it; treat in-kernel NVSHMEM as the stretch.**
