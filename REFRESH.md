## 1. State of the project

SuperGrok1.5 is a multi-backend high-performance optimizer suite for PyTorch, with a parallel JAX/TPU implementation living in its own subtree. The repository is set up as an editable Python package (`grokking_optimizers/`) backed by a large native extension built from a tree of C++/CUDA/HIP source under `csrc/`. The native extension is built by `setup.py`, which detects whether the host has CUDA, ROCm/HIP, or only a CPU and selects sources accordingly. Everything is wired up so that the same Python API works on NVIDIA cards from Volta (sm_70) through Blackwell (sm_100), AMD MI100 through MI350X, and on plain x86 or ARM CPUs.

The current branch is `claude/custom-optimizer-analysis-HFYhg`. The working tree is clean. The most recent commits, in order from newest to oldest, are: a sweeping bug-fix-and-optimization pass across all optimizers, a fix for the `_single_param_step` paths in Muon, Prodigy, and GrokAdamW, a hardening of AMD `gcnArchName` parsing against three-digit codes, a nine-bug fix pass that included an FP32-skip optimization across the suite, and a rewrite that wired up several previously-dead fused kernels and removed a Python-side AdamW bottleneck. The trajectory is clearly maturation: the architecture is settled and recent work has been about correctness, instrumentation, and squeezing the last bits of overhead out of the hot paths.

Roughly: about sixty thousand lines of C++/CUDA/HIP across ninety-eight source files, eleven Python optimizers in `grokking_optimizers/`, a sibling JAX/TPU package, eight test files (the README still says six but the count has grown), three benchmark scripts, and a code-generation directory that produces some of the architecture-specific kernel variants from a YAML spec. There are two main documentation files at the repo root — `README.md` (user-facing, comprehensive) and `ANALYSIS.md` (an internal review with bug findings, design critiques, and a table of further optimization opportunities). Both are accurate as of the latest commits, though the test count claim in `ANALYSIS.md` is slightly outdated.

The project is essentially production-ready as a multi-backend optimizer library. There are no known correctness blockers; the remaining work is incremental performance tuning, expanding test coverage to an explicit Python-fallback-versus-fused-CUDA agreement check, and finishing some architecture-specific paths (Blackwell native FP4 expert kernels, deeper TMEM use, full FP4 / FP6 paths on CDNA4) that are presently scaffolded but conservatively delegate to higher-precision fallbacks.

## 2. The optimizer suite at a glance

There are eleven Python optimizers, roughly grouped into three tiers by ambition.

The flagship is **SuperGrok v2**. It is a meta-learning optimizer that sits on top of an Adam-style base step and modifies each parameter element using a per-element learned function: a bidirectional Mamba-3 selective scan over gradient elements sorted by magnitude, a per-element gated recurrent unit with a four-dimensional hidden state, and a four-headed Parameter-Efficient Expert Retrieval (PEER) routing into a pool of one hundred forty-four tiny expert MLPs. The smart gradient that comes out of all that is added back to the original gradient through a learned skip connection and then fed into Adam. The meta-net's own weights are trained by bilevel optimization on validation data.

The middle tier is the two SuperGrok 1.x optimizers. **SuperGrok v1.5** keeps the same overall architecture as v2 — sharpness-aware perturbation, momentum, learned per-element gradient correction, decoupled weight decay — but replaces the Mamba+PEER+GRU meta-net with a small two-layer MLP that takes only two inputs per element, the gradient and a sharpness measurement, and emits one corrective scalar. It is dramatically simpler than v2 and dramatically faster while retaining most of the qualitative grokking-aware behavior. **SuperGrok v1.1** is a sibling of v1.5 with one main difference: instead of using a sigmoid on training accuracy as the gate, it uses cosine similarity between the smart gradient and the slow momentum buffer, computed by a dedicated reduction kernel.

The bottom tier is eight reference and baseline optimizers, most of which are well-known in the literature, all of which have been ported to fused CUDA, HIP, and CPU kernels with feature parity. **GrokAdamW** is AdamW augmented with an EMA gradient filter and a multiplicative amplification of persistent gradient directions; it has a quantized-state variant that stores the first moment as INT8 per-block. **NeuralGrok** is AdamW with a learned MLP amplifier that produces a per-element multiplicative gradient scale. **Prodigy** is a self-tuning Adam variant that estimates the optimal learning rate from the cumulative parameter-space distance traveled, eliminating the need to tune the outer learning rate. **Grokfast** is the simplest grokking-aware optimizer — an EMA filter plus AdamW, with an amplified gradient update. **Lion** is the EvoLved Sign Momentum optimizer — interpolated momentum, sign-based update, decoupled weight decay. **LookSAM** is AdamW interleaved with a periodic sharpness-aware perturbation step rather than every-step SAM. **Muon** is a dual optimizer: it applies Newton-Schulz orthogonalization to two-dimensional weight matrices' momentum buffers and uses standard AdamW for one-dimensional parameters such as biases and norm scales.

All eleven optimizers expose the standard `torch.optim.Optimizer` interface and can be used as drop-in replacements in any training loop. All eleven have parity JAX/TPU implementations under `supergrok2_jax_tpu/`. All eleven dispatch through fused CUDA, HIP, or CPU kernels at runtime; the dispatch logic is centralized in `dispatch.py`. SuperGrok v2 is the only one with a robust full Python fallback for environments without a compiled extension; the others raise informative errors if the C++ extension is missing.

## 3. SuperGrok v2 — the flagship

The Python entry point lives in `grokking_optimizers/supergrok2.py`. The optimizer takes the standard parameter list and a long list of hyperparameters that fall into three groups: classical Adam settings (learning rate one millith, beta-one zero point nine, beta-two zero point nine nine nine, epsilon one tenth-millionth, decoupled weight decay scaled to one), grokking-aware schedule parameters (initial alpha for the slow-gradient EMA at zero point nine eight, lambda of two scaling the slow-gradient term, kappa of zero point one driving the exponential decay of the grokking signal, warm-up and ramp horizons of one hundred steps each, gradient clipping at norm one), and meta-net architectural parameters (model dimension eight, state dimension sixteen, Mamba inner-expansion factor two, four PEER heads, one hundred forty-four experts, expert-hidden dimension sixteen, GRU hidden dimension four, meta-net rescale factor zero point one, expert recycling every one hundred steps with threshold zero point one percent of total activations, alpha update frequency every hundred steps, SAM and bilevel scheduling thresholds, weight-decay ramp parameters, projection precision auto-detected, state precision either FP32 or the INT8-per-block "config-three" mode).

The state stored per parameter is, depending on configuration: the first-moment EMA `exp_avg` either as FP32 or as INT8 with a per-block scale every thirty-two elements, the second-moment EMA `exp_avg_sq` as FP32 or BF16, the slow gradient `mus` (an alpha-blended exponential running mean), the sharpness vector `sharpness` (the difference between the perturbed-point gradient and the normal gradient), the per-element GRU hidden state `gru_states` (size N by gru_hidden, defaulting to N by 4), and per-parameter Mamba forward and backward states each of shape d_inner by d_state. The meta-net itself is a separate `nn.Module` whose weights live outside the per-param state but are trained by the optimizer via bilevel update.

The step is structured as a sequence of layered transforms. First the optimizer updates its grokking-signal alpha based on training loss, validation loss, and training accuracy: alpha drifts higher (toward more slow-gradient influence) as the generalization gap shrinks. Second a ramp factor based on warm-up and ramp horizons is computed. Third a sigmoid-based gate is computed from current training accuracy: it becomes large when accuracy approaches the memorization threshold, which is when the optimizer starts amplifying the slow gradient and SAM signals. Fourth, an effective weight decay is computed from the same training-accuracy sigmoid; the maximum weight decay is applied only after the model has nearly memorized the training set, at which point aggressive decay is what drives the transition to generalization. Fifth, when CUDA is available, the optimizer caches the meta-net weights into device memory and calls `_ops.supergrok2_prepare_and_batched_step`, which is a single C++ entry point that runs the full pipeline — gradient clipping, NaN guard, bias correction, meta-net forward, effective gradient computation, Adam update, decoupled weight decay — for all parameters in one batched launch. Sixth, expert recycling and Mamba state synchronization happen at their respective intervals; in distributed settings, expert counts are all-reduced before recycling and Mamba states are broadcast from rank zero.

The optimizer has a full Python fallback that runs entirely in PyTorch for use on CPU or for testing the kernels' correctness. It is slower (orders of magnitude) but produces matching results.

The bilevel update is a separate method, `bilevel_step`, that takes the model, training input, validation input, criterion, and a meta-optimizer. It runs the meta-net forward on the training data, evaluates a validation loss, backpropagates through the meta-net to compute meta-gradients, and applies them through the meta-optimizer. In CUDA mode this is also batched through a dedicated forward-save and backward kernel pair that uses bilevel checkpointing (see Section 22) to keep memory tractable.

The hooks for distributed training are unobtrusive but thorough. There are private helpers `_is_distributed`, `_allreduce_meta_grads`, `_allreduce_expert_counts`, `_sync_mamba_states`, `exclude_meta_net_from_fsdp`, and `_gather_full_grad_fsdp`. When DDP is active, meta-net gradients are summed across ranks and divided by world size before the meta-step. Expert counts are aggregated via all-reduce so all ranks see the same usage statistics before deciding which experts to recycle. Mamba states are broadcast from rank zero so every rank progresses through the same meta-net trajectory. In FSDP, the meta-net itself is excluded from sharding (it is small and replicated), and a context manager temporarily gathers full per-parameter gradients before the meta-net forward pass.

The compiled-step variant `CompiledSuperGrok2` from `cuda_graph_optimizer.py` records the optimizer step as a CUDA graph after a configurable number of warm-up steps and replays it thereafter, avoiding kernel launch overhead. It invalidates the graph automatically when hyperparameters or tensor shapes change.

## 4. The Mamba-3 + PEER MetaNet inner module

The meta-net is a small learned function that, given a parameter's gradient and its current sharpness signal, produces a corrective scalar per element. It lives in `grokking_optimizers/mamba3_peer_metanet.py` and is composed of four named sub-blocks plus an input projection.

The input projection is a tiny linear layer that maps each (gradient, sharpness) pair into a `d_model`-dimensional embedding. After projection, the per-parameter gradient elements are sorted by gradient magnitude. This sort is the hidden trick that turns a per-element function into something that benefits from sequence modeling: by ordering the elements by magnitude, the resulting "sequence" carries information about the gradient distribution, and the Mamba scan can encode where in that distribution any particular element sits.

The first major block is the **Mamba-3 selective scan**. It is an architecturally faithful Mamba-style state-space model adapted for this purpose. The model dimension is eight, the inner expansion is two (so d_inner is sixteen), and the state dimension is sixteen. There are four projection matrices: an input projection that produces both the x-branch and the z-gate, a dt projection that produces a per-element timescale via softplus, a B projection that gates how the input enters the state, and a C projection that gates how the state contributes to the output. There is a learned `A_log` parameter that, after exponentiation, gives a strictly negative state decay matrix, plus a learned skip-connection vector `D` and a paired RoPE frequency table for rotary modulation of the state. The recurrence at each timestep is a trapezoidal discretization of a continuous-time linear ODE, with paired RoPE rotation applied between consecutive states. The scan is run twice per parameter — once in forward order and once in reverse — and the two results are concatenated to give every element a bidirectional context.

The second block is a **per-element mini GRU**. It is a four-dimensional gated recurrent unit; its hidden state persists across optimizer steps and is stored in the optimizer state per parameter element. The input to the GRU at each step is a concatenation of the current gradient, the current sharpness, the forward Mamba context for this element, and the backward Mamba context for this element. The GRU performs the standard update: a sigmoid update gate, a sigmoid reset gate, and a tanh candidate, blended into a new hidden state.

The third block is the **four-headed PEER (Parameter-Efficient Expert Retrieval) router**. PEER is a product-key attention mechanism designed for routing into a very large set of tiny experts at very low cost. The expert pool is one hundred forty-four experts arranged as a twelve-by-twelve grid. For each PEER head, a query is computed by linearly projecting a feature vector that includes the GRU hidden state, the bidirectional Mamba context, the gradient, and the sharpness. The query is split into two halves; each half is scored against a per-head set of twelve product keys. A top-k of size four is taken in each half, the four-by-four outer product yields sixteen expert candidates per element, the top-four (by combined score) are kept, and a softmax over the kept four gives the routing weights. The router is therefore performing top-four selection out of one hundred forty-four experts at the cost of two top-fours of size twelve, which is dramatically cheaper than scoring all one hundred forty-four. There are four such heads working in parallel; their outputs are averaged.

The fourth block is the **expert MLP**. Each of the one hundred forty-four experts is a tiny two-layer MLP: a Linear(1 → 16), a ReLU, and a Linear(16 → 1). The active expert per (head, element) takes that element's gradient as its scalar input and produces a scalar correction. Each PEER head produces a routing-weighted sum of its top-four experts' outputs; the four heads' outputs are averaged. The result is multiplied by a learned rescale factor and added to the original gradient as a skip connection. That sum is the meta-net's output, the so-called smart gradient.

Expert recycling is built into the meta-net but driven by the optimizer. Every recycle interval (one hundred steps by default), the optimizer counts how often each expert was activated. Experts whose activation count is below a threshold are considered dead. They are replaced by clones of the most-active experts plus small Gaussian noise. If an entire row or column of product keys is dead, the corresponding product-key row/column is reset, breaking dead zones in the routing space.

The whole module is a single `nn.Module` that runs forward in pure PyTorch on CPU (and serves as the fallback) and is replaced by fused CUDA, HIP, or TPU kernels in production.

## 5. SuperGrok v1.5

SuperGrok v1.5 is the simpler ancestor of v2 and lives in `grokking_optimizers/supergrok15.py`. The architectural skeleton is the same — momentum, Adam moments, sharpness-aware perturbation, decoupled weight decay, sigmoid-gated grokking signal, ramp and warmup schedules — but the meta-net is replaced by a tiny shared two-layer MLP. The MLP takes two scalars per element (the current gradient and the current sharpness measurement), passes them through a single hidden layer of configurable size (sixteen, thirty-two, sixty-four, or one hundred twenty-eight, with thirty-two as the default), applies a fast GELU approximation, and produces one corrective scalar. That correction is added to the gradient through a learned skip connection, weighted by a rescale factor. Everything else — Adam moments, weight decay, SAM, bilevel — is identical to v2 in character.

The state per parameter is four FP32 vectors of length N: `exp_avg`, `exp_avg_sq`, `mus`, and `sharpness`. There is no Mamba state, no GRU state, and no expert state, which makes v1.5 dramatically cheaper than v2 in both memory and compute. The meta-net's weights are the same shape across all parameters; they are stored once and broadcast.

The step is a single C++ kernel call (`supergrok15_fused_step`) that runs the entire pipeline in one launch. The kernel evaluates the MLP per-thread per-element, with the MLP weights loaded cooperatively into shared memory (they are tiny — about a kilobyte for hidden=32). The MLP output never touches global memory; it is produced as a register value and immediately consumed by the Adam step in the same kernel. This register-resident smart-gradient pattern is one of the larger throughput wins in the codebase: it cuts the bandwidth requirement of the optimizer step roughly in half compared with the obvious two-kernel implementation.

The MLP uses fast GELU (a sigmoid approximation, `z / (1 + exp(-1.702 * z))`) instead of the true GELU. The error is small (a few thousandths) and the throughput gain is substantial because the approximation reduces to two PTX-level fast intrinsics (an `ex2.approx` for the exponential and a multiplication-add) rather than the multi-cycle hardware GELU. Sharpness-aware perturbation is implemented via `torch.func.functional_call` so that the model parameters themselves are never mutated; the perturbed weights are passed through the model's forward pass as a functional argument.

Bilevel meta-learning is supported through the same mechanism as v2: a separate `bilevel_step` evaluates the MLP on training data, computes a validation loss, and backpropagates through the MLP. The MLP is small enough that backprop is cheap.

Schedules in v1.5 are sigmoid-gated by training accuracy. As accuracy approaches a threshold (typically zero point nine), the gate signal rises, which causes effective weight decay to grow toward its peak and SAM frequency to increase. There is no Mamba and no expert recycling, so the scheduling is simpler than in v2.

There is no Python fallback for v1.5 — if the C++ extension is missing, instantiation fails. This is acceptable in practice because v1.5's defining feature is its fused-CUDA performance.

## 6. SuperGrok v1.1

SuperGrok v1.1 lives in `grokking_optimizers/supergrok11.py` and is functionally a sibling of v1.5 with one structural change: the gating term that controls how much of the slow gradient is mixed into the update is no longer derived from a sigmoid on training accuracy. It is instead derived from the cosine similarity between the smart gradient (the meta-net's output) and the slow momentum buffer, all per-parameter, and computed by a dedicated GPU reduction kernel. The motivation is that training accuracy is a coarse signal and is the same for every parameter; the cosine similarity is a per-parameter local signal that captures whether the smart gradient is currently aligned with the slow momentum, and is therefore a more granular trigger for amplifying the slow-gradient term.

The cosine gate is computed by running a fused reduction across all N elements of a parameter. The reduction simultaneously accumulates three quantities: the dot product of smart-gradient and momentum, the squared norm of the smart gradient, and the squared norm of the momentum. The reduction is implemented with warp-shuffle butterflies inside each warp and a single atomic-add per warp into global accumulators, which avoids shared-memory bottlenecks. Once the three sums are available, the cosine similarity is `dot / (norm_sg * norm_mu + epsilon)`, and the gate is a temperature-scaled sigmoid of that cosine. The temperature defaults to five, which is a moderately sharp sigmoid.

The remainder of the step is essentially v1.5: the same meta-net (the same two-input two-layer MLP), the same Adam moments, the same decoupled weight decay, the same SAM perturbation pattern, and the same fused full-step kernel pattern that keeps the smart gradient register-resident. The fused kernel receives `lamb_eff = ramp * gate * base_lambda` as a precomputed scalar.

There is also a `meta_step` method that, on a configurable interval (every five steps by default), performs a brief optimizer step on the meta-net's weights using a small validation batch, providing a lightweight bilevel update.

Like v1.5, v1.1 has no full Python fallback. The compiled extension is required.

The reason both v1.5 and v1.1 still exist alongside v2 is partly historical and partly empirical: v2 is more capable but also far heavier. For smaller models or for grokking experiments where the per-step overhead would dominate training time, v1.5 and v1.1 deliver most of the benefits at a fraction of the cost. The design trade-off they encode is between a learned, sequence-aware per-element function (v2) and a learned, point-wise per-element function (v1.5/v1.1) — and there is no universal winner.

## 7. GrokAdamW

GrokAdamW lives in `grokking_optimizers/grokadamw.py`. It is the simplest grokking-aware optimizer in the suite: it is AdamW augmented with an exponential moving average of the gradient and a multiplicative amplification of persistent gradient directions.

The state per parameter is three FP32 vectors: the standard `exp_avg` and `exp_avg_sq` of Adam, plus a slow-gradient EMA called `ema`. At each step the EMA is updated by a convex combination of the previous EMA and the current gradient, with the EMA decay parameter alpha defaulting to zero point nine eight. This is a high decay value, so the EMA is a slow, low-frequency view of the gradient — it tracks the persistent component while filtering out noisy fluctuations.

The amplified gradient is then formed as the current gradient plus lambda times the slow EMA. Lambda defaults to five. The intuition is that the slow gradient is a clean estimate of where the model wants to go in the long run; mixing more of it into the current step accelerates motion in directions that are consistently informative across many steps, which is precisely the kind of low-frequency persistent signal that drives the grokking transition. Standard Adam is then applied with this amplified gradient. Decoupled weight decay is applied as a multiplicative shrinkage on the parameter before the Adam update.

The fused kernel `grokadamw_fused_step` runs all of this in a single launch per parameter: load the gradient, update the EMA, compute the amplified gradient, update the two Adam moments, apply weight decay, perform the Adam step, store everything back. It uses non-temporal loads and stores for the optimizer state to avoid polluting the L2 cache, and float-four vectorized loads when the parameter is FP32 and aligned. There is also a quantized variant in `grokadamw_kernels.cu` (the `_q3` kernel) that stores `exp_avg` as INT8 with a per-block FP32 scale (block size eight) and stores `exp_avg_sq` and `ema` as BF16 with stochastic rounding. The stochastic rounding uses a hash-based PRNG keyed on the step counter and element index, which is deterministic per step but produces unbiased rounding decisions. The Q3 variant cuts optimizer-state memory roughly in half with negligible accuracy impact.

The hyperparameters are: learning rate one millith, betas zero point nine and zero point nine eight, epsilon one tenth-millionth, weight decay one, alpha zero point nine eight, lambda five, gradient clipping at one. There is also a learnable per-layer beta-one gamma factor that decays beta-one as the layer index increases — a per-layer adjustment that gives deeper layers more inertia.

There is no Python fallback in the optimizer step itself; the compiled extension is required. There is, however, a CPU implementation that is part of the `_ops` extension on CPU-only builds, so the optimizer works end-to-end on CPUs.

## 8. NeuralGrok

NeuralGrok lives in `grokking_optimizers/neuralgrok.py`. It replaces the fixed EMA-based amplification of GrokAdamW with a learned MLP amplifier. The amplifier is a small two-or-three-layer MLP (defaulting to three layers with hidden dimension one hundred twenty-eight) that takes a single scalar input — the magnitude of the current gradient — and produces a single scalar multiplicative gain. The amplified gradient is the original gradient times (alpha times the amplifier output plus beta), where alpha and beta are scalar hyperparameters that control the strength and offset of the modulation (defaults are ten and four).

The state per parameter is two FP32 vectors: `exp_avg` and `exp_avg_sq`. The amplifier's own weights are global, not per-parameter, and are stored on the optimizer object. The amplifier is trained in inner steps interleaved with the main optimizer steps; the inner-step count defaults to one.

The fused kernel `neuralgrok_fused_step` runs the amplifier inference and the Adam step in one launch. The amplifier weights are extracted by a Python helper that pulls out the first and last layer's weights and biases — middle layers are not used in the fused kernel, which keeps the per-thread cost bounded. The amplifier weights are loaded into shared memory cooperatively by the threads in each block, and each thread evaluates the (small) MLP per its own gradient element. The amplified gradient is held in a register and immediately fed into the Adam update, in the same fused-full-step pattern as v1.5 and v1.1. There are templated specializations for hidden dimensions sixteen, thirty-two, sixty-four, and one hundred twenty-eight that allow the compiler to fully unroll the inner loops.

The intent is that the amplifier learns a function from gradient magnitude to gain that suppresses noise (low-magnitude gradients get small gains) and emphasizes signal (high-magnitude gradients get gains close to one or moderately larger). Training the amplifier jointly with the model lets it adapt to whatever the gradient distribution looks like, rather than committing to a fixed nonlinearity in advance.

The hyperparameters are: learning rate one millith, betas zero point nine and zero point nine eight, epsilon one tenth-millionth, weight decay one, alpha ten, beta four, num-layers three, hidden-dim one hundred twenty-eight. The amplifier is trained either by a separate inner optimizer or via bilevel update; the optimizer constructor accepts an external optimizer for the amplifier or constructs an Adam by default.

## 9. Prodigy

Prodigy lives in `grokking_optimizers/prodigy.py`. It is a self-tuning Adam variant that estimates the optimal learning rate from the cumulative parameter-space distance traveled, eliminating the need to tune the outer learning rate by hand. The standard advice is to set the outer learning rate to one and let Prodigy's internal `d_lr` factor do all the work.

The state per parameter is four vectors: `exp_avg`, `exp_avg_sq`, the standard Adam moments, plus an additional accumulator `s` and the parameter's initial value `param_init`. The accumulator `s` is itself a slowly-decaying EMA of distance-weighted squared gradients, and `param_init` is a snapshot of the parameter at the moment Prodigy was attached to it (or at the moment the optimizer's state was reset).

The adaptive learning-rate scalar `d_lr` is computed once per step by a global reduction across all parameters. The reduction simultaneously accumulates two quantities: a numerator equal to the sum over all elements of (gradient times the parameter's distance from its initial value), and a denominator equal to the sum over all elements of `s`. The new `d_lr` is the square root of (numerator divided by denominator plus epsilon). Intuitively, the numerator estimates how much "useful progress" the model has made (gradients aligned with the direction of travel), and the denominator is a normalization that scales the result into a learning-rate-like quantity. Prodigy then applies an Adam step using `lr * d_lr` as the effective learning rate, and progressive weight decay using `lr * d_lr * weight_decay` as the effective decay rate.

The reduction kernel `prodigy_dlr_reduce_kernel` uses warp-shuffle reductions to accumulate the numerator and denominator within each warp, followed by a single atomic-add per warp into global accumulators. This is the standard fast-reduction pattern. The fused step kernel runs the moment updates, the new `s` update, and the parameter update in one launch using the freshly-computed `d_lr`.

There is no Python fallback in the optimizer's hot path; the compiled extension is required. CPU builds include a CPU implementation that completes the round-trip.

The hyperparameters are: learning rate (recommended at one for auto-tuning), betas zero point nine and zero point nine nine nine, epsilon one tenth-millionth, weight decay one. Prodigy is particularly useful for heterogeneous models where different parameter groups need very different learning rates — the auto-tuned `d_lr` adapts on the fly.

## 10. Grokfast

Grokfast lives in `grokking_optimizers/grokfast.py`. It is the simplest grokking-aware optimizer in the suite — even simpler than GrokAdamW. Whereas GrokAdamW computes an EMA of the gradient and amplifies along that EMA direction with a tunable lambda, Grokfast does essentially the same thing but with a lighter touch: an EMA of the gradient at decay `grokfast_alpha` (default zero point nine eight), then an amplified gradient equal to the original gradient plus `grokfast_lamb` times the EMA (default lambda is two).

The state per parameter is three FP32 vectors: `ema`, `exp_avg`, and `exp_avg_sq`. The fused kernel is `grokfast_fused_ema_adam_step`, which loads the gradient, updates the EMA, computes the amplified gradient (held in a register), updates the two Adam moments, applies decoupled weight decay, performs the Adam step, and writes everything back, all in one launch. The amplified gradient never touches global memory, which is again the register-resident pattern that saves a global-memory round-trip relative to a two-kernel implementation.

The hyperparameters are: learning rate one millith, betas zero point nine and zero point nine eight, epsilon one tenth-millionth, weight decay one, grokfast-alpha zero point nine eight, grokfast-lamb two. The kernel uses non-temporal loads and stores for the optimizer state and float-four vectorized loads when alignment permits. Like GrokAdamW it has architectural variants, including templated launchers for FP32, FP16, and BF16 parameter precisions.

The intuition behind Grokfast is the same as GrokAdamW's, but the simpler mixing rule and the smaller hyperparameter surface tend to make it a better baseline for ablations: any improvement attributable to grokking-aware mixing should show up clearly here without confounders. In practice Grokfast is often used as a sanity-check baseline in grokking experiments, and the fused kernel is fast enough that it is also a viable production optimizer in its own right.

## 11. Lion

Lion lives in `grokking_optimizers/lion.py`. It is the EvoLved Sign Momentum optimizer — a sign-based Adam alternative discovered through symbolic search. Lion is unusual in that the magnitude of every parameter update is uniform (it equals the learning rate), so the optimizer behaves like a constant-magnitude trust-region method that picks only the direction. This makes Lion remarkably stable across very different parameter scales and is one reason it works well for fine-tuning large pretrained models.

The state per parameter is one FP32 vector: a momentum buffer `exp_avg`. At each step, an interpolated direction is computed as a convex combination of `beta1` times the current momentum and `(1 - beta1)` times the current gradient. The parameter update is `lr` times the sign of that interpolated direction, plus a decoupled weight-decay term `lr * weight_decay * param`. The momentum buffer is then updated with a different beta (`beta2`, defaulting to zero point nine nine) by a standard EMA on the gradient. Note that Lion uses two separate betas for the interpolation and the momentum update, which is an unusual choice that gives the algorithm its peculiar robustness.

The fused kernel `lion_fused_step` runs all of this in one launch using the hardware `copysignf` intrinsic to extract the sign without a branch. The kernel uses non-temporal loads and stores for the momentum and float-four vectorization where the parameter is FP32 and aligned. There is also a multi-tensor variant that fuses many small parameter tensors into a single kernel launch via a two-dimensional grid (one row of blocks per parameter), eliminating per-parameter kernel-launch overhead — a substantial win for transformers with hundreds of parameter tensors.

The hyperparameters are: learning rate three ten-thousandths, betas zero point nine and zero point nine nine, weight decay three. Lion's recommended learning rate is roughly an order of magnitude smaller than Adam's because the sign-based update has unit magnitude per element rather than gradient-scaled magnitude.

## 12. LookSAM

LookSAM lives in `grokking_optimizers/looksam.py`. It is AdamW interleaved with a periodic sharpness-aware perturbation step rather than every-step SAM. Standard SAM doubles the cost of every training step (one forward-backward pass at the original parameters, one at perturbed parameters). LookSAM instead performs the perturbation only every `k` steps (default five) and reuses the cached SAM direction in between, amortizing the SAM cost.

The state per parameter is three FP32 vectors: `exp_avg`, `exp_avg_sq`, and a cached `sam_direction`. Regular steps perform a standard fused AdamW update via `fused_adamw_simple_step`. SAM steps perform a perturbation, compute a sharpness gradient, and adjust the gradient direction by interpolating between the original and the sharpness-aware direction with a configurable alpha (default zero point seven).

The kernels in `looksam_kernels.cu` include a two-norm reduction kernel that computes the squared norms of the gradient difference and of the gradient itself in a single pass, using the same warp-shuffle reduction pattern as Prodigy. There is also a fused direction-adjust kernel that combines the direction update with the gradient adjustment, keeping the direction vector register-resident.

The hyperparameters are: learning rate one millith, betas zero point nine and zero point nine eight, epsilon one tenth-millionth, weight decay one, rho zero point zero five (the SAM perturbation radius), k of five (SAM step frequency), alpha zero point seven (the direction interpolation weight). LookSAM gives most of SAM's generalization benefit at roughly 1.4× the cost of AdamW rather than 2×.

## 13. Muon

Muon lives in `grokking_optimizers/muon.py`. It is a dual optimizer: it applies Newton-Schulz orthogonalization to two-dimensional weight matrices' momentum buffers and uses standard AdamW for one-dimensional parameters such as biases and norm scales.

For two-dimensional parameters, the state is a single momentum buffer. At each step, the momentum is updated by a standard EMA on the gradient. The momentum buffer is then treated as an initial approximation to an orthogonal matrix. Newton-Schulz iteration is applied: the matrix is repeatedly transformed by an iteration that drives it toward orthogonality. A single iteration replaces X with `(3X - X * X^T * X) / 2`, which is the matrix analogue of a Newton iteration on the equation `X * X^T = I`. After a fixed number of iterations (default five), the resulting near-orthogonal matrix is the search direction. The parameter update is `lr` times that direction, plus a decoupled weight-decay term.

For one-dimensional parameters, Muon uses standard AdamW with its own (separate) hyperparameters: `adamw_lr` defaulting to one millith, `adamw_betas` of zero point nine and zero point nine eight, and `adamw_eps` of one tenth-millionth. Muon's own learning rate is much higher (default zero point zero two) because the orthogonalized direction has uniform spectral norm one.

The kernels are in `muon_kernels.cu`. A momentum-and-normalize kernel updates the buffer and divides by its Frobenius norm. The Newton-Schulz inner iteration is performed by a combination of cuBLAS matmul calls (for the matrix products `A @ X` and `A @ A @ X`) and a custom combine kernel that does the linear combination `a*X + b*AX + c*AAX` with hand-tuned coefficients. The final iteration's combine and the parameter update are fused into a single kernel that keeps the orthogonalized direction register-resident.

There are architecture-specific variants in `csrc/cuda/sm_80/muon_sm80.cu` and `csrc/cuda/sm_90/muon_sm90.cu` that exploit the larger shared memory and better cuBLAS dispatch on Ampere and Hopper. The HIP path uses rocBLAS for the matrix products on AMD.

## 14. Cross-cutting Python infrastructure

A handful of Python modules in `grokking_optimizers/` provide shared functionality used by all eleven optimizers.

**`dispatch.py`** is the runtime hardware-detection module. It imports cleanly without requiring any GPU and exposes a set of small functions that report what the host actually has. `get_gpu_vendor` returns `'nvidia'`, `'amd'`, or `'none'`. `get_gpu_arch` returns the SM number (e.g., seventy-five, eighty, ninety, one hundred for NVIDIA) or the CDNA architecture number (ninety, ninety-four, one hundred twenty for AMD). `get_backend` returns `'cuda'`, `'hip'`, or `'cpu'`. `get_warp_size` returns thirty-two for NVIDIA and sixty-four for AMD CDNA. There are tier helpers (`get_arch_tier`, `get_amd_tier`) that return symbolic names like `'blackwell'`, `'hopper'`, `'ampere'`, `'cdna4'`, `'cdna3'`, `'cdna2'`, or `'generic'`. There are feature predicates (`supports_bf16`, `supports_fp8`, `supports_tf32`, `supports_tma`, `supports_block_clusters`, `supports_matrix_cores`, `supports_nvfp4`) for use in dispatch decisions. There is an environment-variable override `FORCE_ARCH` that lets tests run code paths for architectures the test machine does not actually have, by lying about the SM number; the kernels themselves still need to be compiled in.

**`quantization.py`** centralizes the precision-mode policy. The `PrecisionConfig` class holds three settings: projection precision (used for the Mamba/PEER projection matrices in v2), expert weight precision (used for the expert MLP weights), and scan state precision (always FP32 because the state accumulation is numerically delicate). Projection precision is selectable from `'fp32'`, `'tf32'`, `'bf16'`, `'fp8'`, `'mxfp4'`, `'nvfp4'`, or `'auto'`; the auto setting picks FP8 on Hopper and Blackwell, BF16 on Ampere, FP32 on older hardware. Expert precision is selectable from `'fp32'`, `'int8'`, `'int4'`, or `'auto'`; auto picks INT8. The module provides `convert_projection_weights` and `convert_expert_weights` helpers that take an FP32 weight tensor and produce a quantized tensor plus the scales or zero-points required for dequantization. There is also an experimental dynamic-precision mode that monitors gradient norm stability and progressively lowers precision as training stabilizes, reverting to higher precision if instability is detected.

**`cuda_graph_optimizer.py`** wraps any optimizer in a CUDA graph for kernel-launch-overhead reduction. The wrapper, `CUDAGraphOptimizer` (with a SuperGrok-v2-specific subclass `CompiledSuperGrok2`), runs the wrapped optimizer eagerly for a configurable number of warm-up steps (default three), captures the next step as a CUDA graph, and replays the graph thereafter. The wrapper allocates static parameter-gradient buffers, swaps gradient pointers to those static buffers during capture, and at replay copies the current gradients into the static buffers, runs the graph, and lets the parameter updates flow back into the actual parameter tensors. The wrapper invalidates the graph automatically when the caller passes any keyword arguments to `step` (which would imply hyperparameter changes), and it provides an explicit `invalidate` method for cases where invalidation is needed between calls. CUDA graphs deliver roughly a two-to-three-times speedup on small models and one-and-a-half on large models, where launch overhead is a smaller fraction of the total step time.

**`distributed.py`** holds DDP and FSDP utilities. There are setup helpers (`setup_distributed`, `cleanup_distributed`) that wrap torchrun-style initialization. There are query helpers (`get_rank`, `get_world_size`, `is_main_process`). There is a state-broadcasting helper (`broadcast_optimizer_state`) used to align ranks at the start of training. There is a model-wrapping helper (`wrap_model_ddp`). And there are private helpers used by SuperGrok v2 itself: `_is_distributed`, `_allreduce_meta_grads`, `_allreduce_expert_counts`, `_sync_mamba_states`, `_gather_full_grad_fsdp`, and the public `exclude_meta_net_from_fsdp` that marks the meta-net to remain replicated under FSDP rather than sharded.

**`jit/`** is a directory of JIT specializers that, when available, generate hardware-tuned kernels at runtime and cache them in `~/.cache/supergrok2/`. There is a base `KernelSpecializer` class plus a `ModelConfig` dataclass; concrete subclasses for CUDA, HIP, TPU (via Pallas), and CPU; and a set of helper modules for shared-memory layout optimization, tile-size selection, GCN wavefront scheduling, and PTX instruction scheduling. The JIT path is optional; SuperGrok v2 attempts to instantiate a specializer in a try/except block and falls back to the pre-compiled kernels in `_ops` if anything goes wrong. In practice the pre-compiled kernels are sufficient for almost all use cases; the JIT path is a future-proofing mechanism for unusual model configurations.

**`__init__.py`** is the public surface of the package. It exports all eleven optimizers, all four meta-net classes (Mamba3PEERMetaNet, Mamba3ScanBlock, MiniGRU, SharpnessMetaNet), the wrappers (CompiledSuperGrok2, CUDAGraphOptimizer, OverlappedOptimizer, PipelinedOptimizer, GradientHookOptimizer, AsyncSuperGrok2, MoEAwareSuperGrok2), the distributed helpers, the dispatch helpers, the precision config class, and three boolean flags (`_HAS_OPS`, `_HAS_CUDA`, `_HAS_CPU_OPS`) that downstream code can check to decide what code paths are available.

## 15. The C++/CUDA/HIP common layer

The native side of the codebase is roughly sixty thousand lines across ninety-eight source files, organized so a single source file can compile under both CUDA and HIP, with architecture-specific specializations under their own subdirectories. Everything bottoms out on a small set of shared headers in `csrc/common/`.

**`platform.h`** is the universal CUDA-versus-HIP abstraction. It detects which backend is in use at compile time by checking for `__CUDACC__` versus `__HIPCC__` and sets a global `GROK_CUDA=1` or `GROK_HIP=1`. It pins down warp-size differences: CUDA always has thirty-two-lane warps; HIP uses the `__AMDGCN_WAVEFRONT_SIZE__` macro, which is sixty-four on CDNA hardware (MI200, MI300X) and thirty-two on RDNA. Macros remap the per-vendor intrinsics into a single name: `SHFL_DOWN` becomes `__shfl_down_sync` with explicit masks on CUDA and the unmasked `__shfl_down` on HIP (CDNA lanes are implicitly synchronized); `FAST_SINCOSF` maps to the single-instruction `__sincosf` on CUDA and the standard `sincosf` on HIP; `LDG` becomes `__ldg` on CUDA (a hint to fetch through the read-only cache) and a plain dereference on HIP (where the GCN compiler manages this automatically); `FULL_WARP_MASK` is `0xFFFFFFFF` on CUDA and zero on HIP. There are stream-type aliases (`GpuStream_t`), error-checking macro aliases, and a `cub`-versus-`hipcub` namespace alias so CUB calls compile on either backend through rocPRIM. The header also defines non-temporal load and store helpers that bypass L2 cache pollution: on Ampere and later, these emit inline PTX `ld.global.nc` for non-coherent loads and `st.global.wt` for write-through stores; on HIP, they fall back to `__builtin_nontemporal_load` and `__builtin_nontemporal_store`. Both float and float-four variants are provided. Finally there are AMD-only occupancy-control attributes (`GROK_WAVES_PER_EU`, `GROK_FLAT_WORK_GROUP_SIZE`) that map to no-ops on CUDA.

**`types.h`** declares the compile-time constants that bound every kernel's inner dimensions and the `Affine2x2` struct used by the parallel scan. The constants are: maximum state dimension thirty-two, maximum inner dimension thirty-two, maximum model dimension sixteen, maximum GRU hidden dimension eight, maximum expert hidden dimension sixteen, maximum top-K of four. The scan-related constants are: parallel-scan block size of five hundred twelve threads, parallel-scan threshold of two hundred fifty-six elements (below which the sequential scan is preferred), and GEMM-precompute threshold of one thousand twenty-four elements (above which the projection precomputes are routed through cuBLAS rather than a custom kernel). The `Affine2x2` struct holds four floats for a two-by-two matrix and two floats for a two-element bias, six floats total. There is a portable C++ `affine_combine` function that does the obvious matrix-times-matrix-plus-vector composition; the high-performance PTX version of the same operation lives in `ptx_intrinsics.cuh`.

**`ptx_intrinsics.cuh`** holds inline-PTX implementations of the hot-path operations. The most-used is `affine_combine_ptx`, which performs the Affine2x2 composition with twelve fused multiply-adds arranged in three independent waves so the GPU's dual-issue FMA pipelines stay full; the resulting throughput is roughly four times that of the naive C++ version. There is a `softplus_ptx` that computes `log(1 + exp(x))` in roughly two cycles by composing `ex2.approx` and `lg2.approx` plus a branchless saturation predicate via `selp`. There is a `fast_exp_ptx` that computes `exp(x)` in a single cycle via `ex2.approx` after pre-multiplying by `log2(e)`. There is a `stochastic_round_ptx` that performs unbiased stochastic rounding by comparing the fractional part of the input against a uniform random sample from the lane's pseudo-random bits, using `cvt.rmi` and `selp` to avoid any branching. And there is a `gru_gates_ptx` that computes a pair of independent sigmoids (the GRU's update and reset gates) with their exponentials interleaved so both FMA pipelines are filled simultaneously. All of these have safe HIP fallbacks that use the standard math library; the PTX paths are a CUDA-only optimization.

**`utils.cuh`** holds device-side utility functions: `warp_reduce_sum` for floating-point reductions across a warp using `SHFL_DOWN`, a hash-based PRNG `hash_prng` keyed on (step, element) for stochastic rounding, the BF16 and INT8 stochastic-rounding helpers, plus more PTX-backed helpers (`fast_rsqrt_nr` for Newton-Raphson-refined reciprocal square root, `ptx_fma`, `ptx_exp2`, `ptx_log2`, `ptx_expf`, `ptx_tanhf`, `ptx_sigmoidf`). There is a templated expert-MLP forward helper (`ptx_expert_mlp_forward`) that the compiler can fully unroll, and an INT8 stochastic-rounding helper that uses PTX `prmt.b32` byte-permutation for fast bit extraction.

**`ops.h` / `ops.cpp`** are the C++ binding layer that PyTorch sees. The header declares roughly seventy-nine kernel launchers — one per fused-step entry point per optimizer, plus the various reductions, scans, backward kernels, distributed-scan helpers, MoE kernels, and architecture-specific dispatch entry points. The implementation file is the high-level glue: each Python `step` call routes through one of these C++ functions, which check the device, decide whether the parameter is large enough to warrant the parallel scan or the cuBLAS GEMM precompute, dispatch to the appropriate kernel launcher, and on CPU fall back to PyTorch ATen operations. The CPU fallback is intentionally simple — it is correct but not fast — and is gated by `WITH_CUDA` and `WITH_HIP` macros.

**`quantization.h`** declares the `PrecisionMode` enum (FP32, TF32, BF16, FP8 E4M3, INT8 symmetric, INT4 GPTQ-style, MXFP4) and provides device-side dequantization helpers for INT8, INT4, and MXFP4. INT8 is symmetric with a per-tensor scale; INT4 is GPTQ-style with per-group scales and zero-points and two values packed per byte; MXFP4 is OCP-microscaling FP4 E2M1 with one shared eight-bit exponent per thirty-two-element block. There is a small lookup table for FP4 magnitudes.

**`dispatch.h`** is the C++ side of the architecture-detection logic. It enumerates NVIDIA tiers (generic for sm_70 and sm_75, Ampere for sm_80 through sm_89, Hopper for sm_90, Blackwell for sm_100) and AMD tiers (generic for gfx908 through gfx942, CDNA4 for gfx950). It exposes `get_sm_arch` which uses `cudaGetDeviceProperties` at runtime and respects the `FORCE_ARCH` environment variable for testing. It declares the `StatePrecision` and `ExpertPrecision` enums used by the SuperGrok v2 kernels.

## 16. SuperGrok v2 forward kernels

The forward path lives in `csrc/cuda/generic/supergrok2_mamba_peer_kernels.cu`. The pipeline runs in five stages, each of which is a separate kernel (or, for some sizes, a sequence of cuBLAS GEMMs).

The first stage is **input projection and sort-key computation**. A small kernel (`input_proj_sort_kernel`) walks each parameter's gradient tensor in parallel, projects each (gradient, sharpness) pair through a learned linear layer to a `d_model`-dimensional embedding, and simultaneously emits the absolute value of the gradient as a sort key. The sort key is paired with an identity permutation index. NaN and infinity are clipped to zero in this kernel to prevent propagation through the rest of the pipeline. After this kernel, a Thrust radix sort orders the projected tensor and the index permutation by the sort keys, so that the highest-magnitude gradient elements come first in the sorted "sequence" that the scan will consume.

The second stage is **parallel precomputation of the scan-time-dependent quantities**. A kernel (`mamba3_parallel_precompute_kernel`) processes all timesteps in parallel, since the per-timestep projections (the x-branch, the z-gate, the dt timescale, the B input modulation, the C output modulation) depend only on the local input and not on the recurrent state. This is a substantial parallelism win because it lets the subsequent scan kernel work without redundant projection computation. For very large parameters (N greater than or equal to one thousand twenty-four), this stage is replaced by `bilevel_precompute_gemm`, which uses cuBLAS `torch::mm_out` calls for the projection matrix multiplies and then a small follow-up kernel (`softplus_bias_kernel`) to add the bias and apply softplus to the dt projection. The cuBLAS path is faster on big tensors because it lights up the tensor cores; the custom path is faster on small tensors because it avoids cuBLAS dispatch overhead.

The third stage is **the Mamba-3 selective scan itself**. There are two kernels for this. For small N (less than two hundred fifty-six elements), a sequential scan kernel (`mamba3_scan_kernel`) walks the timesteps in order, with sixteen threads cooperating per parameter and using shared memory to share the x-branch across timesteps for dt projection. The recurrence at each timestep is a trapezoidal discretization (the canonical bilinear transform of a continuous-time linear ODE) applied to a state vector that has been rotated by paired RoPE — that is, even/odd dimensions of the state are treated as the two coordinates of a complex number that gets rotated by a learned per-pair frequency at each timestep. The state then receives an input contribution gated by B and modulated by dt. The output at each timestep is the gated state via C, plus a SiLU gating against z, plus a learned skip from D times x. The kernel uses `softplus_ptx` for the dt activation, `FAST_SINCOSF` for the RoPE rotation, and `fast_exp_ptx` everywhere an exponential is needed. There is a reverse flag that drives the loop backward for the bidirectional pass.

For large N (greater than or equal to two hundred fifty-six), the kernel is replaced by `mamba3_parallel_scan_kernel`, which implements the Blelloch parallel prefix scan over Affine2x2 transforms. The key insight is that the recurrence `h[t] = A_bar[t] * RoPE_rotate(h[t-1]) + B_bar[t] * x[t]`, after splitting the state into RoPE-paired even/odd dimensions, is exactly an affine map on a two-dimensional vector — that is, a two-by-two matrix times the previous state plus a two-element bias. Affine maps are associative under composition, and therefore amenable to parallel prefix scan. The kernel runs in three phases. In the first phase, each thread sequentially scans a chunk of timesteps, accumulating the composition of all the per-timestep affine transforms into a single summary affine. In the second phase, the per-thread summaries are combined using a Blelloch up-sweep and down-sweep to produce, for each thread, the exclusive prefix of all summaries before it. In the third phase, each thread re-scans its chunk, applying its prefix to each per-timestep state and accumulating the C-projected state contributions into the output. The `affine_combine_ptx` intrinsic is what makes this fast — twelve FMAs per composition in three pipelined waves. There is a final SiLU gating and skip-connection pass at the end.

The fourth stage is **the fused element-wise step**, which combines the GRU update, the four-headed PEER routing, the expert MLP forward pass, and the Adam update into a single kernel called `fused_elem_step_kernel`. This is where most of the hot per-element work happens. Each thread processes one gradient element. It loads the forward and backward Mamba scan outputs for this element, runs an output projection from `d_inner` to `d_model` to get two context vectors, loads the previous GRU state via a non-temporal load, computes the GRU update using `gru_gates_ptx` for the sigmoid pair and tanh for the candidate, writes the new GRU state via a non-temporal store, builds a query vector for each PEER head from the new GRU state plus the two contexts plus the gradient and sharpness, scores against twelve product keys per half via dot products with `LDG`-cached weight loads, takes top-K (one per half for hard routing in this kernel), maps the resulting expert index to the expert weights in shared memory, runs the two-layer expert MLP with ReLU, accumulates the weighted output across heads, optionally increments a per-expert activation counter via atomic add, computes the smart gradient as the original gradient plus the rescaled meta-net output, computes the effective gradient as the smart gradient plus lambda times the slow EMA, runs the Adam moment updates, and applies the parameter update with decoupled weight decay. All of the meta-net weights — GRU weights and biases, PEER query weights and product keys, expert MLP weights — are cooperatively loaded into shared memory at the top of the kernel. The shared-memory budget is roughly eight and a half kilobytes per block, well below the per-SM limit even on the smallest supported hardware.

The fifth stage is the slow EMA update on the `mus` vector and the bookkeeping (bias correction factors, ramp factor, gate signal, effective weight decay) that the Python side computes per step and passes in as scalars. Most of these scalars are computed once per optimizer step on the host and passed by value to all the kernels, avoiding redundant work and unnecessary device-host synchronization.

## 17. SuperGrok v2 backward kernels

The backward path lives in `csrc/cuda/generic/supergrok2_mamba_peer_backward_kernels.cu` and is required only for bilevel meta-net updates — the regular optimizer step does not need it because the meta-net's contribution to the parameter update is treated as a fixed function of the gradient. The backward path is what allows training the meta-net's own weights using a validation loss.

The first stage is **bilevel precomputation**. This is essentially the same as the forward parallel precompute, with the same projection-matrix multiplies and softplus-bias kernel. For N greater than or equal to one thousand twenty-four it routes through cuBLAS via `bilevel_precompute_gemm`; for smaller N it uses the custom kernel `bilevel_precompute_kernel`. The output is the same set of pre-projected x-branch, z-gate, dt, B, and C tensors that the forward path used.

The second stage is **forward replay with state checkpointing**. The kernel `mamba3_parallel_scan_fwd_save_kernel` (or its sequential sibling for small N) runs the same Blelloch parallel scan as the forward path, but additionally writes selected intermediate hidden states to a `saved_states` buffer for use during backprop. The selection is governed by `checkpoint_interval`, which defaults to one but can be raised. With checkpoint_interval one, every state is saved (full memory cost, no recomputation). With checkpoint_interval thirty-two or two hundred fifty-six, only every thirty-second or every two hundred fifty-sixth state is saved, and intermediate states are recomputed from the nearest saved checkpoint during the backward pass. The trade-off is straightforward: with checkpoint interval C, memory usage is roughly N divided by C times the per-state size, and backward compute increases by a factor proportional to C because the missing states must be reconstructed by short forward-mode passes. With C of 32 the memory savings are roughly ninety-seven percent and the backward overhead is about two times.

The third stage is **the backward scan itself**, implemented by `mamba3_scan_backward_kernel`. The kernel walks the timesteps in reverse, holding the saved states and the gradient `d_scan_output` from downstream. At each timestep, it backpropagates through the SiLU gating (computing the gradient of the output with respect to z), through the C projection (accumulating gradients of C and accumulating the contribution to the state gradient), through the trapezoidal-discretized affine recurrence (computing gradients of A_bar, B_bar, the RoPE rotation angles, and the state at the previous timestep), through the dt projection, through the B projection, and through the input projection. Most of the weight-gradient accumulations use shared-memory accumulators per block, then atomically flush to global memory at the end of the block — this is two hundred fifty-six times fewer atomicAdd contention events than per-element atomic adds. The per-element gradient with respect to `x_sorted` is also computed and propagated upstream. There is a two-pass approach for the C-projection backward: the first pass computes per-state d_C reductions via warp shuffles and stores them in a buffer, and a second pass uses a single backward GEMM (cuBLAS) on the buffer to compute d_C_proj_W. This avoids the much larger atomic-contention cost of the naive backward.

The fourth stage is the **input-projection backward** (`input_proj_backward_kernel`), the **GRU backward** (`gru_backward_kernel`), and the **PEER and expert backward** (`expert_peer_backward_kernel`). The input-projection backward is straightforward: for each element, accumulate the outer product of the upstream gradient with [gradient, sharpness] into the projection weight gradient, with a block-local shared-memory accumulator that flushes once per block. The GRU backward unrolls the gate logic carefully, computing gradients with respect to z, r, h_tilde, h_old, and accumulating gradients into the GRU's three weight matrices and three biases via shared-memory accumulators. The PEER backward is a two-pass procedure because the softmax over the top-four routing weights couples all four experts' gradients together — the first pass accumulates dot products needed for the softmax-backward correction, and the second pass uses those dot products to compute gradients with respect to the expert MLP weights, the product keys, and the per-head query projection weights.

The fifth stage is the **output-projection backward** (`out_proj_backward_kernel`), which is a simple per-element outer-product accumulation just like the input-projection backward.

All of these kernels are designed to be call-compatible with PyTorch autograd via custom `Function` definitions on the Python side, but in practice they are called directly by `_ops.supergrok2_bilevel_backward` which receives the saved forward state and the upstream gradient, runs all the backward kernels in sequence, and returns gradient tensors for every meta-net weight. The bilevel meta-step in Python takes those gradients, optionally all-reduces them across DDP ranks, and applies them through a separate meta-optimizer (typically a small Adam).

## 18. SuperGrok v1.5 and v1.1 kernels

The v1.5 kernels live in `csrc/cuda/generic/supergrok15_kernels.cu`, which is roughly seven hundred sixty lines and contains five named kernels plus templated specializations.

The first kernel is `fused_mu_metanet_kernel`. It takes the gradient and sharpness vectors and the slow-EMA `mu` vector and the meta-net's MLP weights, and produces a smart-gradient vector. Each thread handles one element. It updates the slow EMA in place, then evaluates the two-layer MLP per-thread on the (gradient, sharpness) pair, with the MLP weights cooperatively loaded into shared memory by all the threads in the block. The activation is a fast GELU approximation (a sigmoid-based form), and the output is added back to the gradient through a learned skip connection scaled by the rescale parameter. This kernel is the per-element meta-net forward in isolation; in production it is fused with the next kernel.

The second kernel is `fused_adam_decay_kernel`. It takes the smart gradient (or the original gradient) plus the slow EMA `mu` and the Adam moments, and runs the Adam update with progressive decoupled weight decay. It uses `fast_rsqrt_nr` for the reciprocal square root denominator, non-temporal stores for the optimizer state, and float-four vectorization on the FP32 fast path. It also applies a sigmoid-gated lambda factor that controls how much of the slow EMA is mixed into the effective gradient.

The third kernel is `sam_perturb_kernel`, a small per-element kernel that perturbs the parameters in the direction of the gradient, scaled by `rho / (global_grad_norm + epsilon)`. The fourth kernel is `sharpness_restore_kernel`, which simultaneously computes the sharpness vector (the absolute difference between the perturbed-point gradient and the original gradient) and restores the parameters from a backup buffer. These two are the SAM machinery; they fire only on SAM steps, not every step.

The fifth and most important kernel is `fused_supergrok15_full_step_kernel`. This is the production hot path. It fuses kernels one and two: each thread reads the gradient and sharpness, evaluates the meta-net MLP, holds the smart gradient in a register, immediately consumes that register value to update the Adam moments, applies decoupled weight decay, and writes back the parameter update. Because the smart gradient never touches global memory, this kernel uses roughly half the bandwidth of the obvious two-kernel implementation. Throughput improves by twenty to thirty percent on bandwidth-bound workloads. The kernel is templated on the MLP hidden dimension so the compiler can fully unroll the MLP inner loops; there are explicit specializations for hidden dimensions sixteen, thirty-two, sixty-four, and one hundred twenty-eight, with a fallback that uses partial unrolling for non-standard sizes.

The v1.1 kernels live in `csrc/cuda/generic/supergrok11_kernels.cu`, roughly eight hundred sixty lines. The structure mirrors v1.5: a fused_mu_metanet kernel, a fused_adam_decay kernel, and a fused full-step kernel. The difference is the gating: v1.1 also has a `cosine_gate_reduce_kernel` that performs a fused three-quantity reduction (the dot product of smart gradient and slow EMA, the squared norm of the smart gradient, and the squared norm of the slow EMA) using warp-shuffle butterflies and one atomic-add per warp into global accumulators. There is also a `compute_cosine_gate_fused` C++ helper that wraps the reduction in an ATen operation and computes the temperature-scaled sigmoid of the cosine similarity. The result is a per-parameter scalar that replaces the per-step training-accuracy sigmoid as the gating term in the full-step kernel.

Both v1.5 and v1.1 fused kernels use the same patterns: cooperative shared-memory weight loading at the start of the kernel, register-resident smart gradient through the entire step, non-temporal optimizer-state I/O, float-four vectorization on the FP32 path. The kernels are written generically against the `platform.h` macros so they compile cleanly under HIP without modification; the only architecture-specific adaptation is the warp-size-aware reduction in v1.1's cosine reduce kernel.

## 19. Other optimizer kernels

The eight other optimizers each have their own kernel file in `csrc/cuda/generic/`. Each file follows a similar pattern: a fused step kernel for the common case, plus reduction kernels for global statistics where they are needed.

**`grokadamw_kernels.cu`** has `fused_grokadamw_step_kernel`, which runs the EMA update, the gradient amplification, the Adam moments update, the decoupled weight decay, and the parameter update in a single launch. It uses non-temporal I/O for the optimizer state and float-four vectorization on the FP32 path. There is also a quantized variant `fused_grokadamw_step_q3_kernel` that stores `exp_avg` as INT8 with per-block scales (block size eight) and stores `exp_avg_sq` and `ema` as BF16 with stochastic rounding via `hash_prng`. The Q3 variant cuts optimizer-state memory roughly in half with negligible accuracy impact and has been validated by the training-aware tests in `tests/test_training_aware.py`.

**`neuralgrok_kernels.cu`** has `fused_neuralgrok_amplifier_kernel` (runs the amplifier MLP inference per element with weights in shared memory) and `fused_neuralgrok_full_step_kernel` (the fused full-step that keeps the amplified gradient register-resident). There are templated specializations on the amplifier hidden dimension for full unrolling.

**`prodigy_kernels.cu`** has `prodigy_dlr_reduce_kernel` (the global reduction that produces the new `d_lr` from a numerator and denominator using warp shuffles plus one atomic per warp) and `fused_prodigy_step_kernel` (the per-element fused step that updates `s`, the two Adam moments, and the parameter using the freshly computed `d_lr`).

**`grokfast_kernels.cu`** has `fused_grokfast_ema_kernel` (the standalone EMA update used in some non-fused paths) and `fused_grokfast_adam_kernel` (the production fused full-step that keeps the amplified gradient register-resident).

**`lion_kernels.cu`** has `fused_lion_step_kernel`, which runs the Lion update — an interpolated direction, sign extraction via `copysignf`, parameter update with decoupled weight decay, and momentum-buffer EMA — in a single launch. There is a multi-tensor variant for fusing many small parameter tensors.

**`looksam_kernels.cu`** has `looksam_norm_reduce_kernel` (a fused two-norm reduction that computes both the squared norm of the gradient difference and the squared norm of the gradient itself), `looksam_direction_kernel` (the direction-vector update), and `looksam_direction_adjust_fused_kernel` (the fused full-step that keeps the SAM direction vector register-resident).

**`muon_kernels.cu`** has `muon_momentum_normalize_kernel` (updates the momentum buffer and divides by its Frobenius norm), `muon_ns_combine_kernel` (the linear combination `a*X + b*A*X + c*A*A*X` for one Newton-Schulz iteration; the matrix products `A @ X` and `A @ A @ X` are computed by separate cuBLAS calls), and `muon_ns_combine_update_fused_kernel` (the fused final iteration plus parameter update that keeps the orthogonalized direction register-resident).

There is also a `multi_tensor_optimizer_kernels.cu` that fuses many per-parameter optimizer steps into a single kernel launch using a two-dimensional grid where the y-axis selects the parameter and threads in each row iterate over elements with grid-stride loops. The supported optimizers in the multi-tensor path are GrokAdamW, Lion, Grokfast EMA, and the Prodigy step. The pointer-packing for parameters happens once on the host into a small device tensor that is then read by the kernel, so the dispatch overhead is constant rather than linear in the parameter count. For transformers with hundreds of parameter tensors this saves hundreds of milliseconds per step in launch overhead.

A companion file `multi_tensor_prepare.cu` fuses the per-step preparation work — gradient norm computation, gradient clipping, NaN/Inf replacement, bias correction factors, per-parameter scalars — into a single kernel that does a parallel reduction within each block (one block per parameter) so all of the per-parameter scalars come out of one launch.

## 20. Supporting kernels — MoE, multi-tensor, distributed scan, quantization

There is a substantial body of supporting kernels for cases that go beyond the per-parameter optimizer step.

**Mixture-of-experts kernels** live in `moe_deep_kernels.cu` and target models that already use sparse expert routing for their forward pass. The optimizer can be made aware of which experts are active per micro-batch and avoid running the meta-net on inactive expert weights entirely. The kernels include `moe_dynamic_expert_load_kernel` (determines active experts based on gate logits and dynamically loads only their weights into shared memory), `moe_dynamic_expert_fwd_kernel` and `moe_dynamic_expert_bwd_kernel` (forward and backward passes through the dynamically loaded subset), `moe_filter_active_params_kernel` (compacts the parameter index list to only the active experts' parameters), `moe_scan_compacted_kernel` (runs the Mamba scan only on the compacted subset), `moe_scatter_results_kernel` (scatters results back to full parameter positions), `moe_count_expert_activations_kernel` (atomicAdd per expert for activation counting), `moe_compute_load_balance_loss_kernel` (auxiliary loss to drive uniform expert utilization), and `moe_apply_frequency_scaling_kernel` (per-expert learning-rate scaling by activation frequency). For models with a hundred or more experts, dynamic loading reduces global-memory bandwidth and shared-memory pressure by ninety percent or more compared with naively loading all experts.

**Distributed scan kernels** live in `distributed_scan_kernels.cu` and implement the multi-GPU version of the Mamba-3 scan using a chunked Blelloch algorithm. Each GPU runs a local Blelloch scan on its chunk via `mamba3_scan_local_with_summary_kernel` and produces a single Affine2x2 summary representing the composition of all of its per-timestep transforms. The summaries are gathered on rank zero, which runs a small prefix scan over them via `scan_summary_prefix_kernel` to produce per-GPU prefix corrections. Each GPU then applies its prefix to its local scan via `mamba3_apply_scan_prefix_kernel`. The total communication is roughly two Affine2x2 summaries per GPU per scan, which is six floats per GPU — a tiny amount of traffic compared with the volume of state being scanned. Efficiency is roughly seventy percent at four GPUs.

**Quantization kernels** live in `csrc/quantization/quantization_kernels.cu` and provide the device-side quantization and dequantization routines for FP8 E4M3, INT8 symmetric, INT4 GPTQ, and MXFP4. The FP8 quantization is a two-phase kernel: phase one performs a warp-shuffle reduction within each warp followed by an atomic-max into a global accumulator to find the absmax; phase two rescales by `absmax / 448.0` (where 448 is the maximum representable FP8 E4M3 value), quantizes element by element with float-four vectorization, and writes uint8 outputs and FP32 scales. The INT8 symmetric path is similar but with limit one hundred twenty-seven and signed output. The INT4 GPTQ path is group-wise, with one group_size (default thirty-two) per group of elements and asymmetric scales and zero-points; the elements are packed two per byte. The MXFP4 path is per-block (block size thirty-two) and stores one shared exponent per block plus four-bit FP4 magnitudes; the FP4 magnitudes use the OCP-microscaling lookup `{0, 0.5, 1.0, 1.5, 2.0, 3.0, 4.0, 6.0}` with a separate sign bit. The dequantization helpers in `csrc/common/quantization.h` are used inline by the optimizer kernels — for example, the SuperGrok v2 expert MLP forward pass dequantizes the expert weights from INT8 or INT4 on the fly in shared memory, with the per-block scale also kept in shared memory.

There are also a number of small utility kernels — non-temporal copy kernels, RMSNorm, fused activations — that are used in various places throughout the codebase. They are not optimizer-specific but are part of the same fused-CUDA toolbox.

## 21. Architecture-specific kernel tiers

Beyond the generic kernels in `csrc/cuda/generic/`, there are dedicated subdirectories for hardware-specific specializations. Each tier extends or replaces specific kernels from the generic set; the dispatch logic in `dispatch.h` and `dispatch.py` picks the highest-tier specialization compatible with the host hardware at runtime.

**Ampere (sm_80)** lives in `csrc/cuda/sm_80/`. The headline optimization is `cp.async`, the asynchronous global-to-shared memory copy instruction introduced on Ampere. The Mamba scan kernels are reimplemented in a double-buffered pattern: while processing timestep t with one shared-memory buffer, the next timestep's data is asynchronously prefetched into a second buffer. This overlaps the multi-hundred-cycle global-memory latency with the scan's own compute, hiding roughly half of the memory stall time on bandwidth-bound configurations. The files are `supergrok2_scan_sm80.cu` (sequential scan with cp.async double-buffering), `supergrok2_backward_sm80.cu` (backward scan), `supergrok2_fused_elem_sm80.cu` (the per-element step kernel with cp.async-prefetched expert weights), `metanet_optimizers_sm80.cu` and `metanet_cpasync_variants_sm80.cu` (optimizer kernel templates for the meta-net optimizers with cp.async variants), and `muon_sm80.cu` (Muon for Ampere, with TF32 GEMMs via cuBLAS for the Newton-Schulz matrix products). The Ampere tier also opts into TF32 for projection matrix multiplies; cuBLAS handles this transparently.

**Hopper (sm_90)** lives in `csrc/cuda/sm_90/`. The headline optimization is FP8 E4M3 projection precompute. For large parameters (N greater than or equal to four thousand ninety-six), the projection matrix multiplies are routed through cuBLAS with FP8 inputs and FP32 accumulation, using a device-side absmax computation to set the scale (so there is no host-device synchronization). Hopper's FP8 tensor cores deliver about nine hundred TFLOPS in FP8 versus four hundred fifty TFLOPS in BF16 on the H100, so the speedup is roughly two times for the projection step. The files are `supergrok2_scan_sm90.cu` (FP8 precompute integrated with scan), `supergrok2_backward_sm90.cu` (backward), `supergrok2_warp_specialized_sm90.cu` (uses Hopper's distributed shared-memory feature plus warp specialization, where one warp produces by loading global data and another consumes by computing), `metanet_optimizers_sm90.cu` (Hopper-optimized optimizer kernels), and `muon_sm90.cu`. There is a code comment that explicitly notes TMA is *not* used for the scan because the scan's per-timestep access pattern (scattered reads indexed by sort permutation) is poorly suited to TMA's bulk-copy descriptor model.

**Blackwell (sm_100)** lives in `csrc/cuda/sm_100/`. This tier is the most recent and the most conservative. There is `supergrok2_sm100.cu`, `supergrok2_precompute_sm100.cu`, and `supergrok2_scan_sm100.cu`. The intent is to take advantage of Blackwell's TMA bulk-async copies (more efficient than cp.async for large rectangular blocks) and native FP4 tensor cores (eight times more elements per instruction than FP32). In practice, the present code uses TMA for bulk copies of expert weight blocks and a small amount of FP4 expert kernel scaffolding, but most heavier Blackwell features — TMEM (on-chip tensor memory) and the new MMA.2SM intrinsics — are honestly delegated back to the Hopper FP8 path with comments documenting the deferral. This is the pragmatic position: the Hopper path is competitive on Blackwell because Blackwell has higher absolute throughput at every precision; specializing further requires more validation than has been done so far.

**AMD CDNA2 (gfx90a, MI250)** lives in `csrc/hip/cdna2/`. CDNA2 has wavefront-sixty-four warps and uses the MFMA (matrix fused multiply-accumulate) family of instructions. The kernels here are essentially the generic kernels with explicit warp-size-sixty-four awareness in the reduction patterns and shared-memory-layout adjustments to fit the eight-megabyte L2 of MI250.

**AMD CDNA3 (gfx942, MI300X)** lives in `csrc/hip/cdna3/`. The headline optimization is BF16 MFMA projections — the projection matrix multiplies use BF16 inputs and FP32 accumulation, which on CDNA3 dispatches through rocBLAS to the `MFMA_F32_32x32x8_BF16` instruction, roughly twice the throughput of the FP32 MFMA. CDNA3 also has a much larger L2 (two hundred fifty-six megabytes), enough that meta-net weights are essentially permanently resident across optimizer steps.

**AMD CDNA4 (gfx950, MI350X)** lives in `csrc/hip/cdna4/`. CDNA4 has hardware-native FP4 E2M1 matrix multiply (`mfma_f32_32x32x8_fp4`), hardware-native FP6 E3M2 for state compression, two-out-of-four structured sparsity acceleration, and twelve hundred-eighty compute units with two hundred eighty-eight megabytes of L2. The kernel set in `cdna4_kernels.hip.cpp` includes FP4 expert kernels (`cdna4_fp4_expert_load`, `cdna4_fp4_expert_fwd`, `cdna4_fp4_expert_bwd`, `cdna4_fp4_quantize_experts`), FP6 state kernels (`cdna4_fp6_state_pack`, `cdna4_fp6_state_unpack`, `cdna4_fp6_adam_step`, `cdna4_fp6_lamb_step`), 2:4 sparsity helpers (`cdna4_sparse24_select`, `cdna4_sparse24_apply_mask`, `cdna4_sparse24_project`, `cdna4_sparse24_densify`), and fused combinations (`cdna4_fp4_sparse24_fused_expert`, `cdna4_supergrok15_full_step`). Like the Blackwell path, CDNA4 is deliberately conservative — many of these kernels are scaffolded but presently delegate to the next-lower tier when invoked, with the FP6 and FP4 paths gated behind explicit precision requests.

The dispatch policy is a fallback chain: if the requested kernel is not available on the host, dispatch falls back to the next-lower tier. Blackwell falls back to Hopper; Hopper falls back to Ampere; Ampere falls back to the generic CUDA path. CDNA4 falls back to CDNA3, which falls back to the generic HIP path. Every fallback step is either a real specialization or a documented delegation; nothing is silently dropped.

## 22. Algorithmic deep dives

A handful of algorithmic ideas underpin most of the codebase's performance. They are worth understanding in their own right because they recur across multiple kernels.

**The Affine2x2 representation of the Mamba recurrence.** The Mamba-3 selective scan has a recurrence of the form "the new hidden state is the discretized state-transition matrix times the rotated previous state plus the input modulation," all per timestep. After splitting the state into RoPE-paired even/odd dimensions, this recurrence is precisely an affine map on a two-dimensional vector — that is, a two-by-two matrix times the previous state plus a two-element bias. The RoPE rotation is folded into the matrix, the trapezoidal discretization of the state-transition is folded into the matrix, and the input contribution is folded into the bias. Affine maps are associative under composition: composing two of them gives another affine map whose matrix is the product of the matrices and whose bias is the right matrix times the left bias plus the right bias. This associativity is what makes the parallel scan possible, because parallel prefix scans require an associative operator. The struct used everywhere is six floats: four for the matrix and two for the bias.

**The twelve-FMA composition.** Composing two Affine2x2 transforms requires a two-by-two matrix multiplication (eight FMAs) plus a two-element matrix-times-vector plus vector add (four FMAs), for twelve FMAs total. In the inline-PTX intrinsic `affine_combine_ptx`, those twelve FMAs are arranged in three independent waves: the first wave issues four FMAs that have no dependencies on each other (so they fill the dual-issue FMA pipelines), the second wave issues four FMAs that depend on the first wave's outputs plus the two FMAs that begin the bias accumulation, and the third wave issues the two final FMAs that complete the bias. The total latency is roughly ten cycles versus forty or more for the naive C++ version, which is enough of a difference that the parallel scan would not beat the sequential scan without it.

**The Blelloch parallel prefix scan.** The Blelloch algorithm is a two-phase parallel prefix scan that requires an associative operator. The first phase is the up-sweep: starting from a leaf array of length N, pairs of adjacent elements are combined into single elements at successive strides of 1, 2, 4, …, until a single root element remains, holding the composition of the entire array. The second phase is the down-sweep: starting from the root with an identity element, the algorithm walks back down the tree distributing prefix elements to each leaf, so that each leaf ends up holding the exclusive prefix (the composition of all elements before it). The total work is O(N) and the depth is O(log N). In the SuperGrok v2 scan, each leaf is the chunk-summary affine of one thread; each combine is one `affine_combine_ptx` call. The kernel uses the warp-size-aware optimization of skipping `__syncthreads()` for strides smaller than the warp size, since lanes within a warp are implicitly synchronized.

**Bilevel checkpointing.** The bilevel meta-net update requires backpropagation through the entire forward scan, which would naively require storing the full hidden-state trajectory — N timesteps times d_inner times d_state floats per parameter. For a hundred-thousand-element parameter with d_inner sixteen and d_state thirty-two, that is twenty gigabytes per parameter. Bilevel checkpointing stores hidden states only every C timesteps, where C is the `checkpoint_interval` (typically thirty-two or two hundred fifty-six). The intermediate states are reconstructed during the backward pass by short forward-mode replay from the nearest checkpoint. Memory savings scale with C; backward compute increases by a factor proportional to C. With C of two hundred fifty-six, memory drops to roughly one-two-hundredth of the naive cost (about ninety-seven percent savings) while backward compute roughly doubles. The trade-off is governed by the optimizer's `bilevel_checkpoint_interval` argument.

**PTX hot-path intrinsics.** The PTX intrinsics in `ptx_intrinsics.cuh` exist because the standard math library's implementations of `softplus`, `exp`, `tanh`, `sigmoid`, and friends are multi-cycle implementations that include exact rounding and special-case handling. The optimizer's use of these functions is in places where one or two ULPs of error are acceptable (the values are state EMAs and gating signals that get averaged over many steps), so the fast PTX approximations are perfectly fine and dramatically faster. `ex2.approx` is a one-cycle approximation of two-to-the-x. `lg2.approx` is a one-cycle approximation of log-base-two. `rcp.approx` is a one-cycle approximation of reciprocal. The `softplus_ptx` composes `ex2.approx` and `lg2.approx` for two-cycle softplus; `fast_exp_ptx` is one-cycle exp via `ex2.approx`; `gru_gates_ptx` interleaves two independent sigmoids so both pipelines stay full. The naive standard-library equivalents would be six to sixteen cycles each.

**Non-temporal I/O.** Optimizer state — the Adam moments, the slow EMA, the GRU hidden state, and so on — is read once per step, updated, written once per step, and then not touched again until the next step. This access pattern interacts poorly with the L2 cache because the state ends up evicting more useful data (model weights, scan outputs) that *will* be reused within the same step. The `stream_load` and `stream_store` helpers in `platform.h` use PTX `ld.global.nc` and `st.global.wt` on Ampere and later to bypass the L2 cache entirely, which leaves the cache free for the data that benefits from caching. On HIP, the same pattern uses `__builtin_nontemporal_load` and `__builtin_nontemporal_store`.

**Register-resident smart gradient.** Several of the fused kernels — v1.5, v1.1, NeuralGrok, Grokfast, and Muon's final iteration — share a pattern. The intermediate "smart gradient" or "amplified gradient" or "orthogonalized direction" that comes out of the meta-net or amplifier is held in a CUDA register variable and immediately consumed by the Adam (or analogous) update, in the same kernel, on the same thread. This avoids an entire global-memory round-trip — N writes plus N reads — that the obvious two-kernel implementation would incur. It is one of the largest single-source bandwidth wins in the codebase. Throughput goes up by roughly twenty to thirty percent on bandwidth-bound configurations, which is most of them.

## 23. JAX/TPU implementation

A parallel JAX implementation of the entire optimizer suite lives in `supergrok2_jax_tpu/`. It is structured very differently from the PyTorch path because JAX is functional and JIT-compiled, and because XLA handles many of the low-level scheduling concerns that the CUDA code addresses by hand.

The directory contains eleven core modules. `supergrok2_jax.py` is the main optimizer loop with named-tuple state classes. `mamba3_peer_metanet_jax.py` is the meta-net architecture. `scan.py` is the Mamba-3 bidirectional scan, implemented via `jax.lax.associative_scan` with an associative binary operator that composes Affine2x2 transforms — the same algorithmic insight as the CUDA path, but in roughly forty lines instead of five hundred. `gru.py` is the per-element mini GRU. `peer.py` is the multi-head PEER router and the expert MLP. `bilevel.py` is the bilevel update, which simply uses `jax.grad` to backpropagate through the meta-net forward; no custom backward kernels needed. `pallas_kernels.py` is a set of optional Pallas custom kernels (Pallas is JAX's kernel-authoring layer for TPU) that fuse the scan with the GRU and PEER, with graceful fallbacks to pure JAX if Pallas APIs change. `sharding.py` is data-parallel sharding utilities. `simple_optimizers_jax.py` is the eight non-meta-net baselines (GrokAdamW, Lion, Grokfast, Prodigy, Muon, LookSAM). `metanet_optimizers_jax.py` is the simpler meta-net optimizers (SuperGrok v1.5, v1.1, NeuralGrok). `quantization_jax.py` is INT8 symmetric quantization. `bridge.py` is PyTorch-to-JAX weight conversion plus test-vector export.

The Mamba-3 scan in JAX uses `jax.lax.associative_scan` with a hand-rolled combine operator. The combine takes two Affine2x2 transforms and produces their composition, which by associativity is order-invariant. XLA compiles the scan to use the systolic array efficiently on TPUs and the tensor cores efficiently on GPUs without further intervention. The bidirectional scan is two such calls, one in each direction; the forward and backward Mamba states are concatenated for downstream consumption.

The PEER routing has two variants, one for inference (hard routing via argmax) and one for training (soft routing via softmax over the top-K). The hard variant is used during normal optimizer steps for efficiency; the soft variant is used during bilevel updates because the softmax-backward couples the gradients of all four experts and is needed for proper meta-gradient flow.

The Pallas kernels are an optional acceleration layer. `pallas_affine_scan` tiles the scan into one-hundred-twenty-eight or two-hundred-fifty-six-element blocks (matching the v4/v5 versus v6e MXU width) and stitches them with a cross-tile prefix scan; the matrices stay in VMEM so there are no HBM round-trips within a block. `pallas_fused_gru_peer` fuses the GRU update, the PEER product-key routing, and the expert MLP forward into a single Pallas kernel, again keeping intermediates in VMEM. `vmem_persistent_expert_mlp` uses Pallas's `eviction_policy="none"` to keep expert weights resident in VMEM across multiple input tokens on v5p and v6e (which have one hundred ninety-two megabytes of VMEM, enough that even the full one-hundred-forty-four-expert pool fits comfortably). All Pallas calls are wrapped in try/except blocks; if the Pallas API has changed in a way the code can't handle, it falls through to the pure-JAX path.

TPU version detection is automatic. The function `detect_tpu_version` inspects `jax.devices()[0].device_kind` and returns one of `"v4"`, `"v5e"`, `"v5p"`, or `"v6e"`. The result is used to pick optimal tile sizes and VMEM policies. Multi-host setups initialize via `jax.distributed.initialize` reading the standard TPU pod environment variables.

The bilevel update is dramatically simpler than its CUDA counterpart. There is no custom backward kernel. The meta-net forward is a pure JAX function; backpropagation is handled by `jax.grad`, which produces meta-gradients via XLA's automatic differentiation. XLA may apply its own automatic activation checkpointing if the meta-net's forward is large enough to spill, but for this size meta-net it generally is not.

Compared to the PyTorch path, the JAX implementation has some functional differences. SAM is partially integrated — the sharpness field exists in the per-parameter state but the SAM perturbation is not fully wired into the main SuperGrok2 loop in the JAX path. Bilevel checkpointing is not explicitly implemented; XLA's automatic rematerialization is what handles activation memory. Quantization is INT8-only in JAX; the FP8, INT4, MXFP4, and FP6 paths are PyTorch-only. Expert load balancing is rudimentary — expert counts are tracked but no auxiliary loss is applied, and hard routing uses argmax which can lead to expert imbalance in long runs. These are gaps relative to the CUDA path; they are acknowledged in the test suite (`tests/test_supergrok2_jax.py`) and the JAX-specific README sections.

The test suite is twenty-two tests (`tests/test_supergrok2_jax.py`, named J1 through J22), covering the associative-scan correctness, the GRU and PEER components, the full meta-net forward, optimizer steps, bilevel gradient flow, JIT compilation and caching, INT8 quantization round-trips, sharding, pytree compatibility, cross-framework agreement with PyTorch via deterministic test vectors, all the simple optimizers, and the simpler meta-net optimizers. The tests are runnable on a single TPU device or on a CPU host without a TPU (using the CPU JAX backend).

**`test_jax_matrix.py`** runs the same cross-optimizer correctness matrix as the PyTorch test but for the JAX implementations. It covers all ten of the JAX optimizers (GrokAdamW, Lion, Grokfast, Prodigy, Muon, LookSAM, SuperGrok v1.5, v1.1, NeuralGrok, and SuperGrok v2) and verifies parameter changes and the absence of NaN.

**`test_amd_hip.py`** validates AMD-specific behavior: that the generic CUDA kernels do not contain raw CUDA calls (they use `platform.h` macros instead); that AMD-tier detection via `FORCE_ARCH` and `get_amd_tier` works correctly; that `PrecisionConfig` auto-selection picks BF16 for CDNA2 and CDNA3; that `get_amd_label` returns correct GPU labels; that GCN architecture parsing handles MI100, MI250, and MI300X correctly; and that the wavefront-sixty-four sync-skip logic is correct.

**`test_new_features.py`** tests recent performance optimizations: float-four vectorized GrokAdamW kernels with alignment fallback; the `OverlappedOptimizer` distributed wrapper; INT8 and PowerSGD gradient compression; the Pallas scan fallback for JAX; the interleaved states layout; sparse gradient handling with mask inference; and the partial CUDA-graph optimizer.

**`test_training_aware.py`** tests training-stability and precision behavior: that non-temporal `stream_load` and `stream_store` produce correct numerical results; that the Q3 (quantized) state for GrokAdamW produces valid training (no NaN, loss decreases); that the Q3 state matches the FP32 update direction with cosine similarity above zero point ninety-nine; that stochastic rounding is unbiased; that there are no `.item()` calls in the hot path (no host-device sync); that `PipelinedOptimizer` is equivalent to the standard step; and that the training benchmark script runs without error.

The test suite as a whole is comprehensive but has one notable gap that `ANALYSIS.md` calls out: there is no explicit "fused CUDA kernel versus Python fallback bitwise/numerical agreement" test. The numerical equivalence is implicitly covered by `test_supergrok2.py` 12B (sequential-vs-parallel scan) and `test_cpu_fallback.py` (Python fallback correctness against expected mathematical behavior), but a direct fused-versus-Python diff would catch a specific class of bugs that the current tests can miss.

## 25. Benchmarks

The `benchmarks/` directory contains three benchmark scripts.

**`benchmark_supergrok2.py`** is the main step-time and memory benchmark. It exercises a sequence of model sizes — tiny (hidden thirty-two, output ten), small (sixty-four), medium (one twenty-eight), large (two fifty-six), extra-large (five twelve) — and times the optimizer step for each. The metrics it reports are step time in milliseconds (using CUDA events for GPU timing and `time.perf_counter` for CPU timing), peak GPU memory in megabytes broken down by category (model parameters, optimizer states, meta-net weights), and throughput as parameters per second. It runs every one of the eleven optimizers plus a baseline AdamW for comparison. The benchmark uses a ten-step warmup followed by a hundred-step timed run. The same model initialization, the same input data (a thirty-two-element batch), and the same random seed are used across all optimizers, which makes the throughput comparison fair on a per-optimizer basis. Wall-clock comparisons across different optimizer architectures are unavoidably influenced by their inherent compute differences (SuperGrok v2 with its meta-net does more work per step than vanilla Lion), but the breakdowns make the comparison interpretable. Flags include `--optimizer` for single-optimizer runs, `--model-size`, `--include-bilevel`, `--per-tier` for cross-FORCE_ARCH runs, and `--verbose` for memory breakdowns.

**`autotune.py`** is a per-GPU profiling utility that tries different kernel-launch configurations and precision options and caches the results to `~/.cache/supergrok/autotune_{gpu_key}.json`, where the GPU key is a hash of device name plus SM version plus total memory. The cached results are used by subsequent runs to pick an optimal configuration without redoing the profiling. The autotuner profiles scan-block-size throughput (subject to the limitation that `PSCAN_BLOCK` is a compile-time constexpr, so changing it requires rebuilding the extension — the script reports this limitation), projection-precision comparisons (FP32 vs TF32 vs BF16 vs FP8 vs MXFP4 where available), and memory footprint. Flags include `--dry-run` (just report the GPU key), `--force` (re-profile even if cached), and `--verbose`.

**`training_benchmark.py`** is an end-to-end training benchmark that runs the optimizers on a small grokking-style task and reports loss and accuracy curves over time. The intent is to compare convergence speed and memory efficiency across optimizers in a more realistic setting than per-step microbenchmarks.

The benchmark suite has a clear strength and a clear weakness. The strength is that the per-step infrastructure is fair: same init, same data, same seed, exclusive GPU access, multi-GPU round-robin spawning so simultaneous benchmarks do not contend, multiple seeds with mean and standard deviation bands. The weakness, which `ANALYSIS.md` Section 3 calls out, is that the SuperGrok optimizers do extra work per step (the meta-net forward pass, the SAM perturbation steps, the bilevel updates) that the simpler optimizers do not, and that some of the SuperGrok optimizers use validation data during training (via the bilevel meta-update) while the simpler optimizers do not. These are not issues with the benchmark code per se; they are inherent to the optimizers being compared. The benchmark reports throughput as parameters per second, which controls for model size but not for per-step compute differences. A fairer comparison would isolate the SAM contribution by including a standalone SAM or GSAM baseline; the analysis document recommends adding this.

## 26. Code generation

The `codegen/` directory holds Python scripts that generate some of the architecture-specific kernel variants from a YAML specification. The generated files are checked into the repository (under `csrc/cuda/generated/` or similar paths picked up by `setup.py`); the codegen scripts are development-time aids, not invoked at build time.

**`generate_kernels.py`** generates the GrokAdamW Q3 kernel variants — the INT8 per-block-quantized exp-avg with BF16 stochastic-rounded exp-avg-sq and ema. It produces both scalar and float-four vectorized variants, and uses a hash-based PRNG for stochastic rounding. It also generates the absmax-scale computation kernel for quantization and the Muon update kernel with non-temporal I/O.

**`generate_sg2_kernels.py`** generates SuperGrok v2 kernel variants for Ampere and Hopper tiers. It is template-driven from `kernel_specs.yaml`, which lists the optimizer specs along axes such as scalar-vs-vec4, FP32-vs-quantized state, dense-vs-MoE-sparse. It produces output files for `sm_80` (with `cp.async`) and `sm_90` (with FP8 E4M3 projections). The intent is to keep the various kernel permutations in sync without manually maintaining each one.

**`kernel_specs.yaml`** is the configuration. It lists more than twelve optimizer specs (GrokAdamW, Lion, Grokfast, Prodigy, LookSAM, Muon, SuperGrok v1.5, v1.1, v2, NeuralGrok, plus a few internal helpers). Each spec defines the optimizer's per-element update math, its state variables and quantization formats, its per-step scalars, and its integration with the Adam-style step. There are template placeholders for state-load, state-store, parameter-load, parameter-store, gradient-store, and various extras. Each optimizer spec produces sixteen variants on the GPU side (four axes of two states each) plus two CPU variants.

**`common_macros.j2`** is a Jinja2 template file containing macros used across the generated kernels — synchronization patterns, warp-reduction patterns, memory-access patterns, and so on.

The codegen layer is what makes it tractable to maintain dozens of kernel variants across multiple optimizers, multiple precisions, and multiple architectures. The alternative — hand-writing each variant — would either explode the codebase to tens of thousands more lines or, more likely, lead to drift between variants where one variant gets a fix and the others do not. As it stands, generated files have a banner comment indicating they were generated and should not be edited directly; bug fixes go into the YAML or the generator.

## 27. Build system

`setup.py` at the repo root drives the build. It detects the backend by checking `torch.version.hip` (which is non-None on ROCm builds of PyTorch) and the availability of CUDA. It also honors a `FORCE_CUDA=1` environment variable that lets one build the CUDA extension without a physical NVIDIA GPU on the host (useful in CI containers).

On the CUDA path, the build picks up the eighteen generic source files (the optimizer kernels plus the supporting kernels for distributed scan, MoE, and quantization), plus the architecture-specific sources — six files for sm_80, five for sm_90, three for sm_100 — plus auto-detected generated kernel variants under `csrc/cuda/generated/`. The compile flags are `-O3 --use_fast_math -std=c++17 --expt-relaxed-constexpr` plus `-gencode` flags for sm_70, sm_75, sm_80, sm_86, sm_89, sm_90, and sm_100. The `TORCH_CUDA_ARCH_LIST` environment variable can override the SM list. The CPU sources are also compiled and linked (so the resulting extension contains both GPU and CPU code paths and can fall back to CPU even on a CUDA build).

On the HIP path, the build picks up the same eighteen generic source files plus CDNA-specific sources for gfx90a (CDNA2), gfx942 (CDNA3), and gfx950 (CDNA4). The compile flags are similar but with `--offload-arch=gfx908,gfx90a,gfx942,gfx950` and `-DWITH_HIP`. The `--offload-arch` flag embeds the GPU ISA for each listed architecture in the resulting fat binary; HIP picks the right kernel at runtime based on the host's actual GPU. The `csrc/hip/` directory contains a `README_HIP.md` with notes on wavefront-sixty-four-specific tuning.

On the CPU-only path, the build picks up `csrc/cpu/` sources including a SIMD-optimized layer that uses AVX-512 on x86_64 and NEON on ARM64. The compile flags are `-O3 -std=c++17 -fopenmp -ffast-math -funroll-loops`, plus `-march=native` to get the available SIMD width. The CPU build is parallelized with OpenMP at the parameter level.

In total the build picks up roughly sixty-seven source files on the CUDA path. Build times are non-trivial (a clean CUDA build for the full architecture matrix is several minutes), but `pip install -e .` does it once and the resulting extension is reused across runs.

- A targeted fix for `_single_param_step` bugs in Muon, Prodigy, and GrokAdamW.
- A hardening fix for AMD `gcnArchName` parsing against potential out-of-bounds reads on three-digit codes.
- A nine-bug fix pass that included an FP32-skip optimization (skipping `.to(kFloat32)` when the tensor is already FP32).
- A wiring pass that connected several previously-dead fused kernels and removed a Python-side AdamW bottleneck.

The trajectory of the project, looking at the last several months of commits, shows a consistent shift from feature work to performance and correctness work. Architecturally, the SuperGrok v2 design (Mamba-3 plus PEER plus GRU plus expert MLPs) was settled some time ago and has not changed structurally since; what has been changing is the hot-path efficiency (kernel fusions, register-resident intermediates, non-temporal I/O, reduction-kernel improvements), the architecture coverage (Hopper FP8, CDNA3 BF16 MFMA, Blackwell and CDNA4 scaffolding), and the bug fix backlog (silent exception swallowing, redundant forward passes, meta-net device placement, `id`-based caching fragility, single-param-step bugs).

The project is in a stable state: there are no known correctness blockers, all eleven optimizers work end-to-end on at least the generic CUDA, generic HIP, and CPU paths, and the JAX/TPU port is feature-comparable for everything except SAM and bilevel checkpointing. The code is production-quality with thorough documentation, comprehensive tests, and an honest-delegation policy in the architecture-specific kernel tiers.

## 29. Known gaps and improvement opportunities

`ANALYSIS.md` Section 8 lists ten further optimization opportunities, ranked by impact and difficulty. They are, paraphrased: fuse SuperGrok v1.1's separate cosine-gate kernel into the full-step kernel (medium impact, easy); fuse NeuralGrok's amplifier with the Adam step (low impact, easy); cache the meta-net weights across optimizer steps to avoid re-uploading them every step (low-to-medium, easy); pre-allocate the scan workspace buffers once instead of allocating per step (low-to-medium, easy); use persistent CUDA streams for kernel launches (very low, easy); skip unnecessary `.to(kFloat32)` calls when the tensor is already FP32 (very low, easy — already done in recent commits for several optimizers); switch the meta-net's MLP from tanh-based GELU to sigmoid-based GELU (low, easy); write a custom cosine-gate reduction kernel rather than going through the existing fused-three-quantity reduction (low, medium); batch Muon's Newton-Schulz iterations across multiple two-dimensional parameters (low, medium); and use CUB segmented sort for the gradient-magnitude sort when many parameters are sorted at once (low, medium).

`ANALYSIS.md` also raises a handful of design concerns. The peak weight decay value is high enough (the sigmoid-scheduled multiplier can multiply the base by twenty, giving an effective weight decay of five which corresponds to a roughly ninety-nine-point-three-percent shrinkage over a thousand steps) that long training runs may need to revisit the schedule to avoid over-shrinking. The training-accuracy threshold for memorization detection is binary (a sharp transition at zero point nine nine five), which can cause the optimizer's gating to flip sharply rather than transition smoothly; a softer threshold may be desirable. The bilevel meta-net update uses validation data, which gives SuperGrok a per-step information advantage that other optimizers do not have; making the comparison fully fair would require either training the meta-net on a held-out partition or reporting the validation-data leakage as a known feature.

The test suite has one notable gap: there is no explicit "fused CUDA kernel versus Python fallback bitwise/numerical agreement" test. The numerical equivalence is implicitly covered by the sequential-vs-parallel scan test and the Python-fallback correctness tests, but a direct fused-vs-Python diff would catch a class of bugs that the current tests can miss.

The Blackwell and CDNA4 architecture-specific paths are scaffolded but conservatively delegate to the next-lower tier for most heavy lifting. Opportunities exist to deepen these tiers — Blackwell TMEM, MMA.2SM, NVFP4 native; CDNA4 native FP4 expert kernels and FP6 state — once the necessary validation work is done. The current state is honest delegation rather than incomplete code.

The JAX/TPU path lacks full SAM integration (the sharpness field exists but the perturbation is not wired), explicit bilevel checkpointing (it relies on XLA's automatic rematerialization), the FP8/INT4/MXFP4/FP6 quantization variants (only INT8 is implemented), and rigorous expert load balancing (counts are tracked but no auxiliary loss is applied). These gaps are smaller than they appear because XLA does much of the work the CUDA path does by hand, but they are gaps nonetheless.

Finally, the documentation has minor staleness — the test-count claim in `ANALYSIS.md` says sixty-seven across six files but the actual count is closer to eighty-two across eight files — and the codegen layer's relationship to `setup.py` is not as visible as it could be (the generated files are checked in, but a reader has to follow the trail).

## 30. Quick reference

A compact table of where to look for what.

The **Python optimizers** are in `grokking_optimizers/` — one file per optimizer plus `dispatch.py`, `quantization.py`, `cuda_graph_optimizer.py`, `distributed.py`, the `jit/` subdirectory, and `__init__.py` for the public surface. The **JAX optimizers** are the parallel implementations in `supergrok2_jax_tpu/`, with the same shape but functional and JIT-friendly.

The **CUDA and HIP kernels** are under `csrc/`. The shared headers live in `csrc/common/` (with `platform.h`, `types.h`, `ptx_intrinsics.cuh`, `utils.cuh`, `ops.h`, `ops.cpp`, `quantization.h`, `dispatch.h`). The generic kernels (compile under both backends via `platform.h` macros) are in `csrc/cuda/generic/`. Architecture-specific kernels are in `csrc/cuda/sm_80/`, `csrc/cuda/sm_90/`, and `csrc/cuda/sm_100/` for NVIDIA, and `csrc/hip/cdna2/`, `csrc/hip/cdna3/`, `csrc/hip/cdna4/` for AMD. Quantization kernels are in `csrc/quantization/`. The CPU fallback is in `csrc/cpu/`.

The **tests** are in `tests/` — eight files. The **benchmarks** are in `benchmarks/` — three files. The **codegen** is in `codegen/` — generator scripts plus YAML spec.

The **build** is in `setup.py` at the repo root; `pip install -e .` does the whole thing.

The **top-level docs** are `README.md` (user-facing, comprehensive) and `ANALYSIS.md` (internal review, bug findings, optimization opportunities). The HIP-specific notes are in `csrc/hip/README_HIP.md`.

The **branch** to develop on for this catch-up effort is `claude/custom-optimizer-analysis-HFYhg`.
